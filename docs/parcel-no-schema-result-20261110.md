# 택배 v2 전송 스키마 없는 반례 요청 결과

사용자 실행 `no-schema-1794277203243-9036abe9`의 [원본 압축과 파일별 해시](acceptance/parcel-no-schema-20261110/manifest.json)를 보존했다. 압축 SHA-256은 `fcd3f3ec2e150be27f45927823a34f6a55c6a463598afbd8dbd9dcad62e59a67`이다. 압축 경로·링크를 검사한 후 필요한 JSON만 읽었고 업로드된 실행 파일은 실행하지 않았다.

기존 일반 검토 응답을 재사용했고 새 SDK 요청은 1회였다. 실제 전송 요청은 고정 후보와 바이트 단위 SHA-256이 같고 `responseJsonSchema`가 없다. 이번에는 모델이 `STOP` 응답을 반환했다. 새 토큰 사용량은 입력 6,111, 출력 1,614, thinking 4,204, 총 11,929로 기록됐다. 이것은 이번 새 응답의 사용량이며 과거 일반 검토 사용량을 중복 합산하지 않는다.

응답은 JSON으로 파싱됐지만 기존 Reviewer 계약을 따르지 않았다. 최상위 필수 `questions` 대신 `userQuestions`가 있고, `storageAudit`의 `evidenceLines`와 `rationale`가 없다. 저장 상태 사례 5건 모두 필수 `state`와 `verdict`가 빠졌다. 실제 처리 순서는 `questions` 배열 누락에서 먼저 중단된다. 저장 규칙 9건 중 6건에는 모델이 `missing`이라고 적었지만, 형식 실패로 정식 검토표/정책 판단이 실행되지 않았으므로 이것을 확정된 기획 결함이나 합격 판정으로 취급하지 않는다. 원문은 그대로 보존했다.

결과 요약의 `outcome: failed`, `challengeCompleted: false`, `formalReviewSaved: false`, `finalApprovalCreated: false`가 맞다. `failure.json`의 HTTP 상태/코드가 `null`인 것은 이번 실패가 제공자 오류가 아니라 **응답 형식의 로컬 검증 실패**이기 때문이다. 원래 프로젝트와 승인은 변경되지 않았다.

이 실실행으로 관련 이력은 기존6+새1=7시도(최초 인증 실패 별도)이며 이번 새 상한도 소진됐다. 같은 명령을 재실행하거나 시작 예약을 지우지 않는다. 다음 보완은 모델 출력 필드 계약을 더 분명하게 유도하고, 고정된 이 실제 응답을 오프라인으로 재생해 실패/보존 경로를 검증하는 것이다. 응답을 조용히 필드 이름만 바꾸거나 필수 상태 판단을 만들어 채워 정식 승인으로 보내서는 안 된다. 추가 유료 시험은 별도 상한과 새 실행 절차가 필요하다.
