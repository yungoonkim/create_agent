## 구현한 흐름

### 1. 추가 질문 답변 후 새 기획 버전

Reviewer가 사용자 판단을 요청하면 `collect-feedback`으로 질문을 수집한다. 기존 질문 뒤에 새 Q-ID를 붙이고, 기존 원문·답변은 덮어쓰지 않는다. 답변이 모두 기록되면 `resume-plan`이 같은 Plan ID의 다음 버전을 생성한다. 예전 Plan/Review는 보존하고 새 검토 통과 후 최종 사용자 승인을 다시 요구한다.

시험에서는 Plan v1의 날짜 경계·수량 질문 → 부분 답변 중 차단 → 전체 답변 → 새 Controller에서 v2 생성 → 새 최종 승인 → 작업 제안까지 확인했다. CLI 프로세스 시험은 Fake 수정 검토를 포함해 v3까지 진행했다.

### 2. Scope 변경 제안·승인·거절

작업 제안 전의 검토된 기획에서 사용자 요청 또는 Reviewer 요청을 수집한다. 기존 Scope와 변경 이유를 모델 문맥으로 전달해 새 Scope를 제안한다. 표시된 변경 요청과 새 Scope 전체를 하나의 명시적 문구로 승인/거절하고, 별도 `resume-plan`으로만 모델을 호출한다.

승인 시 기존 Scope·Plan·승인은 유지하고 더 높은 Scope 버전의 새 Plan을 생성한다. 새 Plan 최종 승인 후 생성된 작업은 새 출처 해시에 연결된다. Reviewer의 범위 위반 변경을 거절하면 기존 승인 Scope에 맞는 수정본을 생성한다. 사용자 제안 변경의 거절은 기존 기획 승인 또는 질문 절차로 돌아간다.

### 3. 반복 한도와 중복 호출 방지

대기 기획 상태·Scope·Plan/Review 해시를 불변 continuation 기준으로 기록한다. 시작 권한을 supervisor에 먼저 저장하고 Planning 결과에 continuationId를 남긴다. 모든 재개는 기존 iterationCount/maxIterations를 유지하며 설정 변경으로 예산을 초기화하지 못한다.

모델 실행이 끝났지만 supervisor 완료 저장만 실패한 경우, ID·Scope·버전이 일치하는 결과를 확인해 기록만 마무리한다. 모델 도중 끊겨 drafting/reviewing이 남았다면 재실행하지 않고 STOP을 보고한다. 이전 결과를 삭제하거나 중복 과금 가능성이 있는 호출을 자동으로 반복하지 않는다.

### 4. 신규 제안 사용량

질문·Scope·작업 제안 호출 종류, 모델, 성공/실패, 제공받은 토큰, 소요 시간을 `supervisor/usage.jsonl`에 기록한다. 기존 Planning 역할의 기록은 유지한다. 잘못된 JSON 응답에도 제공된 토큰은 남기고 원문·응답 본문·공급자 오류 본문·자격 증명은 ledger에 기록하지 않는다. 여기서 성공은 JSON 파싱 성공이며 사용자 승인이나 의미상 적합성 판정이 아니다.

## 아직 확인하지 않은 것

**실제 Gemini의 전체 기획 품질 인수는 실행하지 않았다.** 현재 Cloud 설정에는 자격 증명·outbound identity가 없고 Vertex AI/OAuth 접속 도메인도 허용되지 않았다. 사용자의 로컬 ADC는 이 환경에 공유되지 않는다. 따라서 Cloud에서 `gcloud auth application-default login`을 완료했다고 가정하거나 로컬 자격 증명을 복사하지 않았다.

실행 준비물은 `examples/supervisor-gemini/config.json`과 `request.md`에 만들었다. 이 설정은 Writer/Reviewer 모두 Gemini 3.8 Flash, 새 projectId, 총 검토 예산 5다. 실제 환경에서 호출한 뒤 아래를 인수해야 한다.

1. 로트·수량·저장·날짜 경계를 먼저 질문하는가.
2. 승인 범위 안에서 한국어 기획과 관찰 가능한 완료 조건을 만드는가.
3. 추가 답변·변경 승인/거절을 반영한 새 기획이 과거 요구와 새 결정을 정확히 구분하는가.
4. 작업 지시서가 모든 필수 요구를 충분히 구현할 수 있고 제외 기능을 추가하지 않는가.
5. 실제 응답·버전·승인·사용량 기록을 [전체 테스트 계획](supervisor-test-plan.md)의 결과와 연결할 수 있는가.

실제 개발 팀원 Runtime, 제품 구현, Windows 직접 실행, 작업 제안 이후 변경 이관, 모델 도중 중단 자동 복구, 비용 청구 대조는 이번 검증에 포함하지 않는다. 실제 모델 품질 인수 후 팀원을 하나씩 연결한다.

사용법과 명령은 [지휘자 통합 안내](supervisor-workflow.md), 전체 진행 설명은 [슈퍼바이저 안내서](supervisor-guide.md)에 정리했다.
