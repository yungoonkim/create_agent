# 사용자 검토표·신뢰성 보완의 실제 Gemini 시험 결과

2026-11-09 (Asia/Seoul). 새 식물 물주기 기획과 운동 기록 교정의 **기능 흐름은 확인했다.** 두 후보 모두 최종 승인 대기까지 도달했지만, 근거 의미와 수정 전후 검증 규칙의 명확성에는 보완점이 남았다. 완전한 기획 품질 합격이나 일반 채팅 대비 우위를 입증한 결과는 아니다.

## 이번에 확인한 동작

| 사례 | 실제 진행 | 결과 |
| --- | --- | --- |
| 식물 물주기 | 실제 Writer v1 → 일반 검토 → 반례 검토 | v1 최종 승인 대기, 수정 요청 없음 |
| 개인 운동 기록 | 고의 결함을 넣은 고정 v1 → 실제 일반 검토의 수정 요청 → 실제 Writer v2 → 일반·반례 검토 | Scope v1 유지, v2 최종 승인 대기 |

운동 v1의 마지막 줄에는 “저장이 성공할 때마다 모든 운동 기록을 공개 순위 서버로 자동 전송한다”는 제외 기능을 넣었다. **Reviewer는 이를 critical 범위 위반으로 찾아 1회 수정을 요청했다.** 승인 Scope를 바꾸는 대신 `revise_plan`으로 삭제를 지시했고, Writer 수정본에서는 실행 지시가 없어졌다. 변경 요약에서 삭제 이력을 설명하는 문장은 남아 있지만 외부 전송을 요구하는 기능은 아니다. 최초 운동 v1은 모델이 만든 기획이 아니라 사전에 고정한 교정 시험 입력이다.

실제 요청은 Writer 2회 / Reviewer 일반 3회·반례 2회로 총 **7회**였다. 모든 응답의 종료 사유는 STOP이며 전송 실패·JSON 중단·MAX_TOKENS는 없었다. 운동 v1은 일반 검토에서 수정으로 분기하므로 그 버전의 반례 호출은 없다. 논리적 검토는 3라운드, 수정 요청은 1라운드다. 이번 실모델 실행에서 잘린 응답이 없었으므로 MAX_TOKENS 중단 처리의 실제 재현 성공까지 주장하지 않는다. 그 동작은 기존 오프라인 회귀 검사 근거와 구분한다.

## 원문으로 확인한 것과 남은 문제

기획/Review의 근거 객체 79개에 들어 있는 인용 304개를 현재 버전의 줄과 대조했다. 반복 인용을 포함한 수치이며 모두 일치했다. 두 사용자 검토표도 고정 생산 코드로 읽기 전용 재구성한 결과, 저장된 JSON/Markdown·출처/번들 해시와 일치했다. `getItem` 자체 SecurityError를 손상 JSON과 혼동하지 않고 실제 읽기 예외 문장을 trigger 및 대응 근거로 인용한 것도 확인했다.

그러나 **인용이 진짜라는 것과 판단을 충분히 뒷받침한다는 것은 다르다.** [진행자 감사](acceptance/planning-review-live-20261109/analysis-20261109/manual-audit.json)에 다음 세 항목을 원문 줄과 함께 남겼다.

1. **운동 v2 공통 검증 규칙은 확인 필요:** v1은 로드와 변경 후보 모두에 이름·날짜·분량 1~180·메모·ID/seq 검증을 적용한다고 명시했다. v2는 입력 제한과 일반적인 저장 필드/타입 오류 차단은 적었지만 같은 값 규칙을 양쪽에 적용한다는 연결이 덜 명확하다. 예를 들어 저장된 `minutes: 181`이나 공백 이름을 어떻게 차단하는지 명시하면 좋다. 실제 코드가 잘못 동작한다고 판정한 것이 아니며, Reviewer의 “퇴행 없음”을 원문만으로 완전히 확정할 수 없다는 지적이다.
2. **유효 저장값 trigger의 조건 근거 부족:** 식물 v1 L76/96, 운동 v2 L27/93은 재접속 복원·잠금 후 로드를 설명하지만 전체 스키마/값 검증 통과 조건까지 보여주지는 않는다. 다른 문단의 검증 규칙과 연결 인용이 필요하다. 허위 인용이나 확정된 기능 누락으로 분류하지 않았다.
3. **식물 첫 기획의 수정 해결 근거 분류:** 이전 검토가 없는 v1에서 `revision_resolution=satisfied`의 근거로 최초 사용자 결정을 인용했다. 이는 결정 반영의 근거이며 이전 지적 해결의 근거는 아니다. `not_applicable`이 더 명확하다. 중요도가 낮은 근거 역할 구분 문제로 기록했다.

따라서 최종 진행자 판정은 **기능 흐름 확인·의미 검토 보완점 있음**이다. 기획의 기본 등록·수정·삭제·저장·읽기 오류·동시 탭 선언은 확인됐지만 세부 규칙이 모두 완전하게 보존됐다고 인증하지 않았다. 두 검토표의 ‘반영됨’ 표시는 모델의 문서 판단 그대로 보존하며, 진행자 감사를 덮어써 같은 결과로 만들지 않는다.

## 인증 실패도 함께 보존

## 기록과 검증 범위

원압축 두 개, 원자료 78파일(인증 실패 19 / 후속 59), 사례·실행기·요금표·의존성 잠금 스냅샷, 감사·집계를 [자료 인덱스](acceptance/planning-review-live-20261109/README.md)에 보존했다. 각 압축의 경로/종류·중복 이름·링크를 검사했고 두 원자료 manifest의 76개 해시를 확인했다. 업로드 안의 코드는 실행하지 않았다. 받은 Windows manifest의 Node 버전은 v26.13.0이다.

생산 코드·프롬프트·정책·고정 사례를 이 결과에 맞춰 수정하지 않았다. 타입 검사와 전체 158개 테스트를 재확인하고 [검증 로그](acceptance/planning-review-live-20261109/analysis-20261109/test-output.txt)를 남긴다. 실제 두 후보는 `awaiting_approval`, Scope는 시험 fixture, 최종 승인 레코드는 pending이다. 실제 사용자 최종 승인·제품 구현·브라우저 제품 시험·팀원 실행은 하지 않았다.
