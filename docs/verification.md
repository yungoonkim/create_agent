# STEP 4 — 검증 근거와 재작업 판단

## 1. 목적과 적용 범위

지휘자가 제출된 완료 보고를 실제 파일과 검사 결과에 연결해 판단하는 기능이다. 실제 Worker Agent는 실행하지 않는다. 검증 프로필을 지정한 작업에만 적용하며, 기존 STEP 3의 프로필 없는 수동 작업은 그대로 읽고 실행한다.

기존 작업 정의에 프로필을 자동 추가하거나 과거 검수를 새 검증 결과로 바꾸지 않는다. 새 방식은 별도의 승인된 프로젝트 실행과 작업 초기화에서 선택한다. 작업 정의의 프로필·재작업 한도도 생성 후 불변이다.

## 2. 작업 정의

기존 작업 정의에 다음 두 필드를 추가한다.

```json
{
  "verificationProfile": {
    "commandIds": ["typecheck", "test"],
    "inputFiles": ["tsconfig.json", "test/feature.test.js"]
  },
  "maxReworkAttempts": 2
}
```

- `expectedArtifacts`: 실제로 존재해야 하는 산출물 파일 목록. 기존 필드다.
- `inputFiles`: 검증에 영향을 주는 추가 소스·테스트·설정 파일. 산출물과 함께 크기·SHA-256을 기록한다.
- `commandIds`: 운영자가 지정한 검사 명령 목록의 ID. Worker 보고에서 받은 실행 문자열을 사용하지 않는다.
- `maxReworkAttempts`: 허용할 재작업 횟수, 0~100의 정수. 0이면 첫 품질 실패에서 차단한다.

산출물과 입력은 작업공간 안의 상대 파일 경로여야 한다. 절대 경로, `..`, 작업공간 밖으로 연결되는 심볼릭 링크를 거부한다. 파일 하나의 검사 크기는 최대 8 MiB다. 파일 내용은 저장하지 않고 크기와 해시를 기록한다.

파일 존재는 내용의 정확성을 증명하지 않는다. 입력 목록 밖의 파일 변경은 자동 감지하지 않으므로, 검사에 영향을 주는 소스·테스트·설정을 정확히 선언해야 한다. 아직 Worker 실행 전후의 전체 Git 변경 목록이나 실행 기준 커밋을 자동 수집하지 않는다.

## 3. 운영자 검사 명령 설정

[설정 예제](../examples/development-verification/verification-policy.json)는 TypeScript 검사와 Node 테스트 명령의 템플릿이다. 대상 프로젝트의 실제 파일·도구·테스트 경로에 맞춰 수정해야 한다. 예제의 `src/feature.ts`나 테스트 파일이 제품 구현으로 제공된 것은 아니다.

각 명령은 실행 파일, 인수 배열, 제한 시간으로 구성한다. `node`는 ADTF를 실행 중인 Node 바이너리로 해석한다. Windows에서도 `npm.cmd`를 셸로 실행하지 않고 Node와 실제 JS 진입점을 직접 지정한다. `.cmd`/`.bat` 실행 파일은 지원하지 않는다.

프로세스는 `shell: false`로 실행한다. 인수의 `$()`, 세미콜론 등을 ADTF가 셸 명령으로 해석하지 않는다. 명령당 제한 시간은 1~60,000ms, 기본 로그 한도는 stdout/stderr 합계 16 KiB이며 최대 64 KiB까지 설정할 수 있다. 초과하면 프로세스 종료를 요청하고 검증을 차단한다.

명령 목록은 운영자가 관리한다. 임의의 Worker·모델 출력으로 이 파일을 갱신하지 않는다. 실행 파일과 인수는 증거에 남기므로 비밀정보를 인수에 넣지 않는다. 자식 프로세스에는 PATH·임시 경로 등 최소 환경 변수만 전달하며, 일반적인 토큰 표기는 로그에서 가린다. 이는 완전한 비밀정보 탐지 기능이 아니다.

**이 실행기는 OS 샌드박스가 아니다.** 허용한 실행 파일과 테스트 코드는 해당 호스트 권한으로 동작하고 파일·네트워크에 접근할 수 있다. 신뢰할 검사만 지정하고 환경의 기존 제한을 유지한다. 시간 초과 시 POSIX 프로세스 그룹 또는 Windows taskkill로 종료를 시도한다. 실제 실행 테스트는 Cloud Linux에서 수행했으며 Windows 프로세스 종료 경로를 이 세션에서 직접 실행하지 않았다.

## 4. 실행 흐름

```text
담당자 지정 → 결과 제출 → awaiting_review
    ↓ verify
승인 Plan/Scope와 현재 작업 확인
    ↓
파일·입력 해시 수집 → 허용된 명령 순차 실행 → 파일·입력 재확인
    ├─ passed: 검수 대기 유지, 수동 완료 조건 검수 필요
    ├─ failed: 재작업 가능하면 rework, 한도 소진이면 blocked
    └─ blocked: 환경·설정 차단 상태로 기록
```

`passed`는 설정된 객관적 검사가 통과했다는 뜻이다. 작업의 모든 완료 조건에 대한 최종 검수는 `review` 명령으로 기록한다. 수동 통과를 입력하더라도 현재 시도에 연결된 통과 증거가 없거나, 검증 이후 선언된 파일이 바뀌었으면 승인하지 않는다. 근거가 오래됐으면 현재 상태에서 다시 검증한다.

검증 명령이 산출물이나 선언된 입력을 바꾼 경우에도 이전 제출물의 근거로 승인하지 않도록 `VERIFICATION_INPUT_CHANGED`로 차단한다. 빌드 캐시 등 검사 중 생성·변경되는 파일과 제출 소스의 구분은 프로필 작성 시 정한다.

## 5. CLI

다음 명령은 해당 프로젝트에 승인 기획과 검증 프로필 작업이 이미 초기화돼 있고, 그 작업의 결과를 제출한 뒤 실행한다. 아래 경로는 템플릿이므로 실제 프로젝트에 맞춰 바꾼다.

```sh
npm run development -- verify --config examples/planning-gemini/config.json --task TASK-VERIFIED --workspace managed-project --verification-config examples/development-verification/verification-policy.json --reason "타입 검사와 테스트 근거 수집"
```

`--workspace`는 검사 명령을 실행할 대상 프로젝트 디렉터리다. `--config`, `--workspace`, `--verification-config` 입력 경로는 CLI를 실행한 루트 안에서 해석한다. 프레임워크 소스와 관리 대상 제품 코드를 같은 모듈에 섞지 않는다.

`verify`는 결과 JSON을 출력하고 통과면 종료코드 0, 품질 검사 실패면 1, 환경·설정 차단이면 2를 반환한다. 인수·상태 오류처럼 결과를 수집할 수 없었던 명령 오류는 종료코드 1과 오류 메시지를 반환한다.

통과 근거를 수집한 뒤 모든 완료 조건에 대해 실제 검수한 파일로 `development review`를 호출한다. 실패 시 `development transition --status ready`로 재작업을 허용하고, 다시 담당자를 지정해 새 결과를 제출한다. 명령 형식은 [Development Loop](development-loop.md)를 따른다.

## 6. 근거와 이력

현재 작업의 `evidence`에 다음을 저장한다.

- 프로젝트·작업 ID와 담당자 지정 시도 번호
- 승인 Plan/Scope의 해시, 제출 결과·검증 프로필·운영자 명령 설정의 해시
- 실제 작업공간 경로, 시작·종료 시각
- 선언된 파일별 크기와 SHA-256
- 실행 파일·인수·시간 제한, 종료코드·시그널, 제한된 stdout/stderr, 소요 시간
- 체크별 결과와 전체 `passed`/`failed`/`blocked` 판정

이 내용은 `development/state.json`의 revision 및 변경 전후 이력과 함께 저장된다. 다시 검증하거나 재작업해도 과거 증거는 이력 스냅샷에 보존된다. 별도의 `verification/` 로그 디렉터리가 생성되는 구조는 아니다.

현재 작업·시도·결과·프로필·승인 출처와 맞지 않는 증거는 거부한다. 검증 동안 프로젝트 잠금을 유지해 중복 검사와 상태 변경을 막고, 실행 전후에 승인 출처를 재확인한다. 출처가 바뀌면 수집 결과를 현재 작업에 붙이지 않고 기존 상태를 보존한다. 이 경우 검사 명령 자체는 이미 실행됐을 수 있다.

해시와 참조 검사는 기록의 정합성을 확인하는 기능이다. 로컬 파일에 대한 전자서명이나 악의적인 호스트로부터의 무결성 증명은 제공하지 않는다.

## 7. 횟수와 중단 정책

`attemptCount`는 담당자 지정으로 시작한 시도의 수다. 아직 실제 Agent Runtime을 호출하지 않으므로 Worker API 실행 횟수라고 보고하지 않는다. `reworkCount`는 품질 실패 후 명시적으로 새 작업을 허용한 횟수다.

| 상황 | 처리 | 재작업 예산 |
| --- | --- | --- |
| 보고한 산출물 누락, 검사 종료코드 실패 | rework 또는 한도 차단 | 다음 재작업을 허용할 때 소비 |
| 수동 완료 조건 검수 실패 | 같은 품질 실패 정책 | 다음 재작업을 허용할 때 소비 |
| 명령 시작 실패, 시간·출력량 한도, 접근 불가·경로·설정 문제 | 환경 차단 | 소비하지 않음 |
| 재작업 예산 소진 후 품질 실패 | `verification_limit` 차단 | 상태 초기화로 재개 불가 |

예산 2이면 최초 시도 후 최대 두 번의 품질 재작업을 허용한다. 환경 복구 후 시도를 다시 시작할 수 있으므로 총 시도 수는 품질 재작업 횟수와 다를 수 있다. rework를 수동 blocked로 바꿨다가 pending으로 되돌려도 예산 소비를 건너뛸 수 없다.

새 시도는 이전 결과·검수·증거를 재사용하지 않는다. 한도 차단은 작업 취소만 허용하며 임의 상태 초기화로 우회하지 않는다. 한도나 범위를 바꾸려면 기존 정의를 덮어쓰지 않고 사용자와 새 계획을 결정해야 한다. 자동 Worker 재호출과 무인 재작업 루프는 이번 단계에 포함하지 않는다.

## 8. 다음 개발과의 연결

이 기능은 지휘자의 검수 판단 기반이다. 다음에는 요구 정리·질문·Scope 제안, 작업 분해·지시서, 진행 보고를 통합해 지휘자 하나를 완성한다. 실제 개발·테스트 팀원 Agent는 그 이후 순차적으로 연결한다.

지휘자 전체의 [테스트 계획](supervisor-test-plan.md)은 아직 모두 실행한 상태가 아니다. 이번 구현 검증은 [STEP 4 실행 보고서](step4-report.md)에 별도로 기록한다.
