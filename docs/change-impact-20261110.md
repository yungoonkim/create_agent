# 기획 변경 영향표 1차

사용자가 요청한 다음 작업인 변경 영향표를 구현했다. 두 기획 스냅샷의 실제 원문 변경과 저장된 검토 인용을 연결한다. 목적은 변경 뒤 다시 확인할 요구사항·제약·저장 규칙·확인 사례를 찾는 것이다. 아직 작성하지 않은 선택의 결과를 예측하거나 전체 간접 의존성을 증명하는 도구는 아니다. 새로운 모델 호출이나 승인/실행 결정은 추가하지 않았다.

## 표시하는 정보

- 변경 원문: 직전/현재 기획의 줄 번호와 실제 삽입·삭제·교체 구간. 문자/서식 변경도 포함하며 의미가 달라졌다고 단정하지 않는다.
- 영향 확인 후보: 요구사항의 정상·실패 흐름, 별도 확인 사례, 승인 제약, 저장값의 불러오기·후보·개별/공유 확인 근거를 변경 구간과 연결한다.
- 재확인 항목: 해당 영역에서 확인할 동작을 제시하고 모델의 preserved/corrected/supported 주장과 현재 로컬 차단을 함께 표시한다.
- 미연결 구간: 검토 인용에 연결되지 않은 비어 있지 않은 변경 줄을 표시한다. 같은 변경 블록의 일부만 인용돼도 나머지 줄을 따로 나열한다.

각 행은 ‘변경 연결 있음·영향 확인 필요’, ‘인용 범위 내 변경 미검출·영향 없음 판정 아님’, ‘근거 없어 미평가’로 구분한다. 단순한 문자열 비교를 확정적인 파급 관계나 안전성 판정으로 사용하지 않는다.

## 출처와 한계

현재/이전 기획·Scope·Review의 버전과 SHA-256을 기록한다. 같은 프로젝트·기획의 직전 버전만 비교하며, 리뷰 인용과 실제 수정 기준 원문을 검증한다. 같은 Scope 버전의 내용이 다르면 거부한다. 서로 다른 Scope는 원문 차이는 보여주되 조건별 파급 관계를 자동 연결하지 않는다. 첫 기획이나 기준 스냅샷이 없는 경우에는 비교 불가 사실을 명시한다.

요구/확인 사례는 품질 검토의 역할별 인용을 사용한다. 제약은 검증된 수정 감사의 이전/현재 인용을 사용한다. 저장 규칙은 **동일한 규칙 문자열**만 묶으며, 이름이 달라진 규칙이 같은 의미라고 추정하지 않는다. 인용의 의미가 틀렸다면 연결 후보도 불완전할 수 있다. 제외 기능별 관계·제품 코드/작업 의존성·문서에 명시되지 않은 간접 효과는 이번에 자동 추정하지 않는다.

정확 비교는 최대1,000,000셀의 LCS를 사용한다. 큰 문서는 일치하는 앞/뒤를 제외한 변경 창 전체를 보존하는 방식으로 전환하고, 그 안에 변경되지 않은 줄도 포함될 수 있음을 표시한다. 비교 자료를 잘라내서 조용히 누락하지 않는다.

## 공통 흐름 연결

`Supervisor.reviewPlan()/report()`와 지속 세션 export에서 직전 스냅샷을 불러와 영향표를 만든다. `exportUserReviewBundle()`은 `change-impact.md`와 `change-impact.json`을 기존 검토 묶음에 추가하고 두 파일도 manifest 해시에 포함한다. 검토표에서 별도 영향표로 이동할 수 있다. 기존 호출자는 영향표 입력을 주지 않으면 기존 내보내기 형태를 유지한다.

비교 출처 검증이 실패해도 기존 기획·검토 내보내기는 유지하고 별도 경고를 표시한다. 잘못된 영향표나 다른 기획의 영향표를 export에 붙이면 쓰기 전에 거부한다. 파일 내보내기 외에 Policy·기획·승인·사용량·예산을 바꾸는 동작은 없다. 영향표는 Writer/Reviewer의 모델 입력에 자동 추가되지 않아 이 기능 자체의 API 토큰 비용은 없다.

## 실제 주차 v1→v2 오프라인 결과

[변경 영향표](acceptance/change-impact-20261110/change-impact.md), [구조화 결과](acceptance/change-impact-20261110/change-impact.json), [검증 기록](acceptance/change-impact-20261110/verification.json)을 보존했다. 입력은 기존 원본 SHA-256 `a7d7aea9d3fac4b70f7b9a1265465b3bbe31ca09e9c21082512dacc1921c6385`이며 내부31개 파일은 변경하지 않았다.

- 문자 변경 구간29개, 영향 확인 후보26개를 만들었다. 같은 영역의 여러 인용/규칙이 별도 행이므로 ‘기능26개 변경’이라는 뜻이 아니다.
- 전체/부분 미연결 구간13개를 따로 표시했다. 문서 전부의 의미적 영향 평가가 끝났다고 표시하지 않았다.
- updatedAt 저장 규칙, 불량 데이터 확인 사례, 다중 탭 관련 제약의 변경 원문을 찾아볼 수 있다.
- createdAt의 확인 근거 누락은 현재 차단 지적으로 남는다. 다중 탭의 미지원 fallback도 원문 변경과 모델 교정 주장을 대조해 확인해야 한다. 기존 의미적 결함이 이 표 때문에 해결된 것은 아니다.
- 기존 기획 v2·Scope v1·반복2/2회·SDK7/7회·최종 승인 없음이 유지된다. 추가 모델 호출0회다.

## 검증

기획 차이 재구성(반복/빈 줄 포함), 대형 문서 fallback, 정상/확인 사례 분리, 공유 근거와 부분 미연결 줄, 기준/Review 위조 거부, 다른 Scope의 자동 연결 금지, export 해시/교체 금지 및 실제 주차 응답 재생을 검사했다. TypeScript typecheck 및 전체216개 오프라인 테스트 통과. 실제 제품 코드나 새 기획안 생성은 수행하지 않았다.

다음 후속 후보는 사용자 문서에서 제안한 선택적 Supervisor 중재 모의 평가다. 변경 영향표를 그 모델의 판단 근거로 사용할지는 별도 설계·검증하며, 이번에 중재 LLM을 추가하지 않는다.
