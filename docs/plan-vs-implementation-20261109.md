# 당초 계획과 현재 구현 현황

기준일: 2026-11-09 (한국 시간). ADTF 자체의 구현 현황과 시험 대상으로 기획한 ‘할 일 관리’ 제품의 현황을 함께 정리한다.

최신 추가: [사용자 기획 검토표와 신뢰성 보완](planning-review-table-report-20261109.md)을 구현했다. 요구별 원문 근거·확인 필요 상태·읽기 전용 내보내기·응답 잘림 보호·범위 내 수정 분기를 제공한다. [새 실제 Gemini 시험](planning-review-live-results-20261109.md)은7회 요청으로 두 기획의 승인 대기·Scope 유지 교정을 확인했고 타입 검사/158개 테스트도 통과했다. 공통 값 검증과 근거 의미/역할 보완점은 남아 완전한 품질 인증은 아니다. 변경 영향표·웹 UI·팀원 실행은 보류한다.

## 1. 지금 어디까지 왔는가

**사람의 승인을 받으며 요구를 정리하고 기획·검토·작업 지시를 만드는 지휘자 CLI는 구현했고, 재고와 할 일 두 주제로 실제 Gemini 단독 인수를 마쳤다.** 작업 결과를 수동으로 등록·검수하는 기반도 있다. 실제 코드를 작성하는 팀원 Agent와 완성된 할 일 웹앱은 아직 없다.

소스를 받으면 터미널에서 지휘자를 실행한다. [실행 가이드](local-run-guide.md)의 모델 없는 데모부터 확인할 수 있다. 전체 개발팀이 자율적으로 제품을 완성하는 단계와 현재 지휘자 단독 인수의 완료를 구분해야 한다.

## 2. ADTF 계획 대비 구현

당초 책임과 경계는 [아키텍처](architecture.md), [PM 명세](pm-agent-spec.md), [슈퍼바이저 안내서](supervisor-guide.md), 단계 이력은 [로드맵](roadmap.md)에 있다. ‘구현’은 코드 존재, ‘검증’은 실제 확인 범위를 뜻한다. 임의의 완료 백분율은 쓰지 않는다.

| 계획한 역할/기능 | 현재 구현·검증 | 남은 경계 |
| --- | --- | --- |
| 공통 프로젝트·작업·모델·승인 계약 | strict TypeScript, Node CLI, [Core 타입](../src/core/types.ts)과 설정 검사 | 계약이 있다고 모든 어댑터가 구현된 것은 아님 |
| 사용자 요청 정리·중요한 선택 질문 | Supervisor의 원문·질문·답변·확정 결정 보존, Fake/Gemini 제안. 두 주제 실제 확인 | 대화형 상시 서비스가 아니라 단계별 CLI 명령 |
| Scope 제안과 사용자 승인 | 버전별 Scope, 승인/거절, 승인 출처 연결 | 모델이 사람 승인을 대신하지 않음 |
| Writer 초안·Reviewer 검토·수정 | Planning Controller, Fake/Vertex AI Gemini, 구조화 이슈·근거·버전·반복 한도 | 동일 모델 의미 판단의 사각지대, 모든 주제의 품질 보장 없음 |
| 기획 품질을 일정하게 관리 | 시스템 지침, 요구별 근거와 7점검, 조건부 반례 검토, 저장 상태 감사·코드 차단, 실제 소규모 비교 | 인용/허용 근거의 의미까지 코드가 증명하지 않음. [최신 평가](reviewer-reliability-20261109.md) |
| 최종 기획안 승인 | 정확한 Plan/Scope 버전과 사용자 승인 레코드. 재고 v3·할 일 v4 승인 완료 | pass는 승인 요청일 뿐이며 자동 최종 승인 없음 |
| 추가 답변·Scope 변경 후 기획 재개 | 명시적 continuation, 승인/거절 분기, 과거 스냅샷·총 반복 예산 유지 | Scope 변경 재개는 작업 제안 전 경계. 모델 호출 도중 중단의 자동 재호출 없음 |
| 승인 기획의 작업 분해·지시서 | 산출물·완료 조건·검증 방법·요구 추적·의존성 DAG·출처 해시, 미초기화 제안 수정. 두 주제 실제 인수 | 작업 제안에 별도 Planning Reviewer가 호출되는 것은 아님. 자연어 내용은 추가 대조 필요 |
| 작업 배정·결과 제출·검수·재작업 | [수동 Development Controller](../src/development/controller.ts), 상태/의존성/한도/이력, 격리 통합 시험 | 담당자 지정은 기록이며 실제 팀원 호출이 아님. 실제 제품 작업은 시작하지 않음 |
| 객관적 검증 근거 | [LocalVerificationEngine](../src/verification/engine.ts)의 실제 파일 해시·허용 검사 명령·시도 연결·환경 차단·재작업 제한, 임시 산출물 시험 | 검사 통과 후 완료 조건은 수동 검수. 실제 팀원 산출물 전체 E2E는 미실행 |
| 프로젝트 메모리와 승인 저장 | Planning/Supervisor/Development의 로컬 JSON 저장소, 버전/잠금/이력·승인 파일 | 범용 Core MemoryStore는 계약이며 DB·외부 메모리 서비스는 없음 |
| Persona Engine | PersonaDefinition 타입, 역할 personaId, Writer/Reviewer별 시스템 지침 | 범용 템플릿·파라미터 엔진/플러그인 미구현 |
| Runtime·모델 분리 | 공통 Runtime/모델 계약, Fake·Vertex AI 모델 설정 | AgentRuntimeAdapter는 인터페이스. 실제 Worker Runtime·다른 공급자 호환 실행 미구현 |
| 진행 보고 | 승인/대기/차단·작업 지시·검증 상태·다음 행동을 report로 제공 | 웹 대시보드·항상 실행되는 자동 지휘 서비스 없음 |

## 3. 실제 인수 프로젝트의 현재 상태

| 항목 | 재고·유통기한 | 내 할 일 목록 |
| --- | --- | --- |
| projectId | supervisor-gemini-acceptance | supervisor-todo-acceptance-20261108 |
| 승인 Scope | v4 | v6 |
| 사용자 승인 Plan | v3 | v4 |
| Planning 상태·반복 | user_approved, 3/5 | user_approved, 4/5 |
| Supervisor | revision16, tasks_proposed | revision20, tasks_proposed |
| 최종 작업 제안 | 5개, 수정 이력 2개 | 6개, 수정 이력 1개 |
| 실제 개발 작업 초기화/팀원 실행 | 없음 | 없음 |
| 최종 근거 | [재고 보고서](supervisor-final-acceptance-20261108.md) | [할 일 보고서](supervisor-todo-final-acceptance-20261109.md) |

`completed=false`와 `nextAction=initialize-tasks`는 관리 대상 제품의 개발이 아직 시작되지 않았다는 보고다. 이번에 요청한 지휘자 단독 인수가 미완료라는 뜻은 아니다. 현재 허용 범위를 넘어 자동으로 작업을 초기화하지 않는다.

실제 런타임 데이터 `.adtf`는 Git 소스와 별개다. 보존된 [할 일 최신 체크포인트](acceptance/todo-final-20261109/runtime-checkpoint.json)는 현재 승인 후 상태이며 이전 승인 대기 체크포인트와 섞지 않는다. 새 소스를 다운로드했다고 Cloud의 실행 데이터가 자동 복원되지는 않는다.

## 4. 우리가 기획한 ‘할 일 웹앱’은 어디까지인가

사용자가 확정한 질문 답변·Scope v6와 최종 승인한 [기획 v4 원문](acceptance/todo-20261108/plan-v4.md), [쉬운 요약](acceptance/todo-20261108/plan-v4-user-summary.md)이 기준이다. 이 기획은 위 표의 ADTF 프레임워크와 별도의 미래 제품이다.

| 기획한 사용자 동작 | 기획·작업 지시 | 실제 제품 구현/브라우저 시험 |
| --- | --- | --- |
| 브라우저에서 버튼·입력창 사용 | 승인 기획·지시에 포함 | 미진행 |
| 제목·마감 날짜/시간 필수, 메모 선택으로 추가 | 포함 | 미진행 |
| 할 일과 완료 목록을 나누고 각각 최초 등록 순서 유지 | 포함 | 미진행 |
| 완료 처리와 완료 취소 | 포함 | 미진행 |
| 수정 및 확인 후 삭제 | 포함 | 미진행 |
| 같은 제목도 별도 기록으로 구분 | 포함 | 미진행 |
| 같은 컴퓨터·브라우저 저장, 다시 열어도 유지 | 저장/오류/손상·복원 경계까지 기획·지시에 포함 | 미진행 |

최종 [작업 지시 6개 쉬운 설명](acceptance/todo-final-20261109/work-orders-easy-summary.md)과 [전체 지시서](acceptance/todo-final-20261109/work-orders-v2.md)를 작성·검토했다. 한 수정 응답의 알 수 없는 의존성은 Controller가 거부했고 기존 상태를 보존한 뒤 새 제안을 정상 저장했다. 이는 지시서 품질 시험이며 웹앱이 동작한다는 증거는 아니다. 지시서에 나오는 미래 제품 파일명·개발 서버 명령은 현재 ADTF에 그 앱이 있다는 뜻이 아니다.

## 5. 이번에 추가로 마친 일과 이후 경계

저장 복구 검토를 보완하고, 기존 회귀 2종·새 사례 6종을 실제 Gemini로 반복 비교했다. 전체 132개 자동 테스트와 깨끗한 소스 설치·오프라인 실행도 통과했다. [품질 보고서](reviewer-reliability-20261109.md)에는 중간 실패·수정·원응답·Reviewer 재검토 사유와 비용·한계를 남겼다. 기존 재고/할 일 Scope·Plan·승인 기록은 그대로다.

현재 승인된 지휘자 보완·단독 시험·문서화는 완료했다. 향후 품질 개선은 별도 새 사례로 의미 오판을 계속 측정할 수 있다. 팀원 Agent 설계·연결, 실제 할 일 앱 구현, Runtime/DB/대시보드 확장은 사용자 재지시 전까지 보류한다.
