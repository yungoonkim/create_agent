# 기획 수정 전후·공통 검증 근거 보완

2026-11-09 (한국 시간). 이전 실제 시험에서 운동 수정본의 공통 값 검증이 덜 명시적으로 바뀌고, 일부 인용이 판단의 조건/역할을 충분히 설명하지 못했다. 이번에는 프롬프트 보완과 함께 원문 비교·구조화된 해결 기록·승인 대기 전 차단을 추가했다. 기존 시험 결과를 재작성하지 않았다.

## 바뀐 동작

| 이전 한계 | 보완 |
| --- | --- |
| 이전 Review만 전달하고 이전 기획 원문은 전달하지 않음 | Controller가 직전 기획을 읽어 Reviewer에 양쪽 원문 줄과 정확한 버전을 전달한다. 수정 버전에서 이전 원문이 없거나 다른 프로젝트/버전이면 모델 호출 전에 중단한다. |
| “퇴행 없음”이라는 한 문장으로 수정 전후를 판단 | 같은 Scope에서는 모든 요구·기술 제약 출처를 정확히 한 번 비교한다. 유지/교정/새 보완/누락/확인 필요와 이전·현재 근거를 기록한다. |
| 이전 지적이 수정됐다는 변경 요약을 믿기 쉬움 | 실제 지적 ID와 품질/저장/보존 검사에서 생성된 미해결 피드백까지 해결표에 연결한다. 빠뜨리거나 새 ID를 만들면 검토를 거부하며, 미해결/확인 필요는 `pass`여도 수정 또는 기존 반복 한도 종료로 처리한다. |
| 입력창 제한만 있고 불러온 값도 같은 규칙을 받는지 불명확 | Writer에 공통 필드/값 검증표와 구체적인 잘못된 저장값 사례를 요구한다. JSON 반례 검토에는 불러오기·저장 후보·확인 사례의 근거를 각각 기록한다. |
| “다시 열면 보임”을 유효 데이터 검증 근거로 인용 | 유효 저장값의 trigger가 공통 로드 검증 근거와 연결되는지 확인한다. 제목뿐인 근거, 빈 역할 근거, 불명확한 검증 결과는 승인 대기 전 차단한다. |
| 첫 기획에서도 이전 수정 해결을 satisfied로 표시 | 최초 작성이라는 코드 문맥에서 `revision_resolution=not_applicable`로 구성한다. 모델이 이 항목에 중대한 누락/질문을 잘못 넣었다면 버리지 않고 Review 실패로 보존한다. |

`revisionAudit`는 원문 비교의 출처와 모델 판단을 함께 저장한다. 기준 원문의 SHA-256·버전·Scope를 묶고, 실제 저장된 직전 기획/검토와 저장할 때 및 읽을 때 다시 대조한다. 바뀐 Scope는 `scope_changed`로 분리해 옛 요구의 보존 합격으로 표시하지 않는다. 현재 승인 Scope에 대한 검토는 계속 수행한다. 사용자 요청/결정과 제외 범위도 기존 품질 검토에서 확인한다.

## 사용자가 보는 결과

기존 `review-plan` 내보내기에 다음 표가 추가된다. 추가 모델 호출은 없다.

- **수정 전후 및 이전 지적 확인:** 출처 ID, 유지/교정/새 보완/누락/확인 필요, 이전·현재 문장, 지적별 해결/미해결 근거.
- **저장값·변경 후보의 공통 검증:** 규칙별 불러올 때의 근거, 저장하기 전 후보의 근거, 구체적인 확인 사례와 남은 문제.
- 첫 기획에는 이전 수정 해결이 해당 없음임을 표시한다. 기존 불변 Review에 새 비교 기록이 없으면 원문을 소급 생성하거나 기존 승인을 취소하지 않는다.

## 검사할 수 있는 범위와 한계

코드는 출처·버전·해시·모든 ID의 커버리지·인용의 실제 존재·비어 있는 역할·제목뿐인 근거·선언된 미해결 결과를 확인한다. **문장 두 개가 의미상 같은 규칙인지, 인용이 충분한지, 모델이 필요한 규칙을 모두 찾아냈는지는 자동으로 증명하지 않는다.** 공통 검증표의 항목도 모델이 고르므로 중요한 값 규칙을 빠뜨릴 수 있다. 단순 줄 교집합은 유효 저장값 조건의 의미를 인증하지 않는다. 실제 원문 감사가 계속 필요하다.

첫 검토에서 해당 없음으로 구성하는 것은 모델 답변이 맞았다는 주장이 아니라 실제 이력의 적용 가능성에 대한 코드 판단이다. 중대한 지적을 이 처리로 지우지 않는다. 실제 시험 실행기는 원응답과 파생된 Review를 구분해 보존한다.

SDK 호출 횟수·반복 한도·출력 한도는 늘리지 않았다. Reviewer는 기존 MEDIUM과 16000 출력 한도를 사용하고 Writer의 thinking 설정은 공급자 기본값을 유지한다. 이전 기획과 비교표 때문에 토큰 사용량이 늘거나 응답이 잘릴 수 있으며, 실제 비용/품질 개선은 아직 측정하지 않았다. Codex 대화 모델의 사용량과 Gemini API 과금은 별개다.

## 검증과 다음 실제 시험

새 빌려준 물건 기록의 고정 응답 회귀 검사는 이전 원문 유실/외부 출처, 지적 누락, 기준 원문 교체, 저장 후 변조, 공통 역할 근거 부족, 첫 검토의 잘못된 질문 처리, 비JSON/구버전 호환성을 확인한다. Controller 통합 검사에서는 실제 v2 원문의 로드 조건을 약하게 만들고 모델의 headline pass와 별개로 수정 대기를 유지한 뒤 v3에서 승인 pending으로 끝낸다. 이 검사는 **고정 응답이므로 LLM이 스스로 퇴행을 탐지했다는 증거가 아니다.**

[새 택배 수령 시험 계획](review-evidence-live-protocol-20261109.md)과 [나중에 PC에서 쓸 안내](../examples/review-evidence-live/README.md)를 준비했다. 실제 Gemini 요청은 **0회**이며 오늘 로컬 실행은 필요 없다. 고정 초안의 수령 값 검증 우회 → 실제 Reviewer/Writer 교정·원문 비교를 최대5회 요청으로 시험할 예정이다. 기존 식물/운동·6쌍 비교를 다시 실행하지 않는다.

검증 로그·기존 자료 보존 해시·TEST/STUB 예시는 [보완 기록](acceptance/review-evidence-20261109/README.md)에 남긴다. 실제 최종 승인·제품 구현·팀원 실행은 수행하지 않는다.
