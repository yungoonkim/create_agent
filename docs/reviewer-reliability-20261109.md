# 저장 복구 검토 보완과 새 사례 검증

기준일: 2026-11-09 (한국 시간). 대상은 ADTF 지휘자 내부의 Writer/Reviewer와 통과 정책이다. Gemini 3.8 Flash를 유지했고 팀원 Agent·제품 구현은 진행하지 않았다.

## 1. 결과부터 보기

저장된 JSON이 비어 있거나 손상됐을 때 기존 데이터를 조용히 초기화하는 규칙을 더 구체적으로 검토하도록 보완했다. 새 사례에서 결함과 정상 동작을 구분했지만, **이번 비교에서는 기존 버전도 모두 구분했다. 성능이 더 높아졌다고 결론 내리지 않는다.** 보완 효과로 확인한 것은 구조화된 저장 상태 점검·승인 근거 검증과 그에 대한 회귀 검사다.

| 평가 | 버전 | 결함 승인 차단 | 정상 승인 단계 도달 | 형식/호출 실패 |
| --- | --- | --- | --- | --- |
| 기존 미검출 사례와 정상 사례, 각 3회 | 기존 f95fa75 | 3/3 | 3/3 | 0 |
| 같은 회귀 시험, 최초 구현 | 보완 초기 | 2/3 | 3/3 | 1 |
| ID 형식 보완 후 같은 회귀 시험 | 보완 최종 | 3/3 | 3/3 | 0 |
| 새 사례 6종, 각 2회 | 기존 f95fa75 | 6/6 | 6/6 | 0 |
| 같은 새 사례 | 보완 최종 | 6/6 | 6/6 | 0 |

‘승인 단계 도달’은 REQUEST_USER_APPROVAL이며 실제 사용자 승인이 아니다. 실패한 리뷰는 결함 차단 성공에 넣지 않았다. 앞선 [개발 사례 평가](planning-quality-hardening-20261108.md)의 빈 저장 문자열 미검출 1회는 이번 기존 버전 3회에서 재현되지 않았다. 모델 응답 변동과 작은 표본을 감안해야 한다.

## 2. 무엇을 바꿨는가

Writer에는 저장 형식별 초기 상태·손상 복구 규칙을 명시하도록 추가했다. Reviewer의 조건부 반례 점검에는 `storageAudit`를 요구한다. JSON을 쓰면 다음 다섯 입력 상태를 각각 한 번씩 기록한다.

| 저장 상태 | 확인할 내용 |
| --- | --- |
| absent | 키/파일이 없을 때의 초기화 |
| present_empty | 존재하지만 빈 문자열일 때의 처리 |
| invalid | 깨진 JSON 또는 스키마/값 검증 실패 |
| valid | 유효한 값을 정상 로드하는 규칙 |
| read_error | 저장소 읽기 자체가 실패했을 때의 처리 |

각 행에는 **기획에 실제로 적힌 동작**, 원문 줄 번호, 판정·이유, 필요 시 승인 Scope의 복구 허용 근거 ID를 넣는다. 바람직한 동작으로 고쳐 읽지 않도록 지침을 명시했다. 코드는 원문 인용을 직접 추출하고 상태 누락/중복·잘못된 줄·존재하지 않는 승인 근거를 거부한다.

기존 JSON을 초기화/덮어쓰는데 허용 근거 ID가 없으면 모델이 consistent/pass라고 해도 major 이슈로 수정 경로에 보낸다. 미정 동작과 unsafe 판정도 차단하고 사용자 선택이 실제로 필요하면 질문으로 보낸다. 저장 형식 자체가 불명확하면 위임된 기술 설계를 구체화하도록 수정한다.

모든 프로젝트에 JSON 규칙을 강요하지 않는다. 순수 메모리 도구와 일반 텍스트는 별도로 분류하고, Scope가 손상된 임시 캐시 폐기를 명시적으로 허용하면 그 정책을 인정한다. 반례 점검은 기존처럼 승인 대상으로 넘어갈 때만 최대 한 번 추가하며 Reviewer 절차당 최대 2요청이다. 반복 예산과 사람의 Scope·최종 기획 승인을 유지한다. 과거 Review는 새 필드 없이 그대로 읽는다.

코드가 확인하는 승인 근거는 **실제 승인 Scope에 해당 ID가 존재한다는 사실**이다. 그 문장이 정말 데이터 폐기를 허용하는지, 모델이 저장 형식·동작을 정확히 읽었는지는 여전히 의미 판단이다. 이것까지 코드가 보장한다고 설명하지 않는다.

## 3. 시험을 어떻게 분리했는가

후보·기대 판정·반복 횟수와 baseline 소스를 먼저 [freeze.json](../examples/reviewer-reliability/freeze.json)에 고정했다. 기존 회귀 2종과 새 사례 6종을 나누고, 새 사례 결과를 본 뒤 같은 세트에 맞춰 구현을 다시 조정하지 않았다. 회귀 형식 오류를 고친 뒤의 소스 해시는 최종 회귀와 새 사례 manifest가 동일하며 [최종 대조](acceptance/reviewer-reliability-20261109/aggregate.json)에 확인했다.

baseline은 f95fa75의 Reviewer·정책·프롬프트 원본이다. 양쪽 모두 같은 모델, MEDIUM thinking, 요청당 출력 한도 8,000, 리뷰당 최대 2요청이다. 모델에는 중립 project/plan ID와 원문·Scope·결정만 전달하고 결함 이름·기대 정답은 전달하지 않았다. 평가 입력은 TEST/STUB이며 실제 승인 레코드를 만들지 않았다.

| 새 사례 | 기대 | 실제 양쪽 각 2회 |
| --- | --- | --- |
| 빌려준 물건: 선택한 기록 한 건만 반환, 정상 저장 | 승인 대상으로 제시 | 통과 |
| 같은 이름의 물건을 한꺼번에 반환하는 모순 | 차단 | 단일 기록 요구/기획 내 모순을 지적 |
| 정원 2명 모임: 실패한 중복 신청도 인원 증가 | 차단 | 실패 시 무변경·명단과 인원 불일치를 지적 |
| 독서 목록: 일반 텍스트의 빈 값은 정상 | 승인 대상으로 제시 | 통과, JSON 초기화 문제로 오인하지 않음 |
| 손상 시 초기화가 명시 승인된 임시 캐시 | 승인 대상으로 제시 | 통과, 허용된 복구를 막지 않음 |
| 모르는 저장 버전을 빈 목록으로 덮어쓰기 | 차단 | 원본 보존/쓰기 차단 요구 위반을 지적 |

각 결함 차단이 주입한 문제를 실제로 지적했는지도 원문과 대조했다. [Reviewer 사유 모음](acceptance/reviewer-reliability-20261109/reviewer-history.json), 각 phase의 `calls/`에 판정·이슈·수정 방향·원응답을 보존한다.

## 4. 중간 실패와 비용

최초 회귀 한 건은 반례 점검이 데이터 유실을 지적했지만 `relatedRequirementId`에 `requirement:REQ-06`을 넣어 기존 검증에서 거부됐다. Scope 근거의 tagged ID와 이슈의 요구사항 ID를 혼동한 것이다. 응답 스키마에서 두 ID의 허용 목록을 각각 지정하고 지침을 보완했다. [실패 원응답](acceptance/reviewer-reliability-20261109/regression/calls/after-empty-corrupt-storage-2.json)과 당시 구현은 삭제하지 않았다. 수정은 새 사례 평가 전에 마쳤다.

| 실행 | 논리 리뷰 | 실제 모델 요청 | 입력 토큰 | 출력 토큰 | reasoning 토큰 |
| --- | --- | --- | --- | --- | --- |
| 최초 회귀, 전후 | 12 | 24 | 118,254 | 22,073 | 40,182 |
| 수정 후 회귀, 보완 버전만 | 6 | 12 | 64,566 | 12,513 | 24,342 |
| 새 사례, 전후 | 24 | 36 | 92,152 | 24,594 | 81,261 |
| 합계 | 42 | 72 | 274,972 | 59,180 | 145,785 |

공급자가 제공한 지표를 합산했다. 항목을 더해 과금 토큰으로 단정하지 않는다. 요청 시간 합계 1,364,703ms는 병렬 실행의 벽시계 시간이 아니다. 이전 품질 평가 94요청·실제 todo 본 실행 13기록과 별도 집계다. [집계](acceptance/reviewer-reliability-20261109/aggregate.json), [최초 회귀](acceptance/reviewer-reliability-20261109/regression/summary.json), [수정 후 회귀](acceptance/reviewer-reliability-20261109/regression-fixed/summary.json), [새 사례](acceptance/reviewer-reliability-20261109/holdout/summary.json)를 참고한다.

## 5. 완료와 한계

- 타입 검사와 전체 **132개 테스트 통과**. 새 검사는 pass 우회 차단, 반복 한도, 허용된 캐시/텍스트, 누락·중복·가짜 승인 근거·잘못된 인용, 미정/질문 분기를 확인한다.
- 실제 todo 최신 체크포인트 20파일, 재고 체크포인트 17파일의 해시가 그대로다. 각 모델 평가 전후에는 `.adtf` 전체 파일 수와 바이트 해시도 대조했다. 승인된 Scope/Plan·기존 이력·총 예산을 변경하지 않았다.
- 깨끗한 소스 설치와 실행은 [가이드 검증 기록](acceptance/local-guide-smoke-20261109.json)에 별도 기록한다.
- 새 사례는 작성자가 미리 정답을 정한 소규모 합성 사례다. 외부 독립 평가·일반 정확도·장기 안정성 검증은 아니다. 동일 모델의 공통 사각지대와 의미 오판 가능성은 남는다. 이번에는 새 Writer 기획 생성 품질을 별도로 측정하지 않았다.

현재 사람 승인형 CLI 지휘자 범위에서 보완·재시험·기록을 완료했다. 다음 품질 변경을 평가할 때는 이번 새 사례를 개발 세트로 취급하고 별도 새 검증 세트를 식별해야 한다. 제품 구현·팀원 연결은 계속 보류한다.
