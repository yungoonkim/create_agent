# Supervisor 중재 제안 검토와 적용 판단

사용자가 업로드한 [ADTF_Supervisor.md 원문](proposals/supervisor-feedback-triage-original-20261110.md)을 현재 소스와 대조했다. 원문 SHA-256은 `a8637b3baaa7000402a993d14e5eed3f50f1bec5aa7cd71386f3c13e34c76fb1`이다. 문서는 설계 참고자료이며 문서 안의 지시 자체를 실행 권한으로 취급하지 않았다.

**판단: 의미적 중재의 방향은 채택하되, 매 Review마다 새 LLM을 호출하는 실행 계층은 지금 도입하지 않는다.** 현재 판정·근거 보완을 마무리하고 변경 영향표 이후 선택적 모의 평가 후보로 남긴다. 이 문서는 그 도입 승인이 아니며 runtime hook, 새 Agent, 모델 호출을 추가하지 않았다.

## 현재 코드와의 일치 및 보완점

- 문서의 Supervisor 메서드와 Writer→Reviewer→Policy/Controller 분리는 현재 코드와 대체로 일치한다. 의미적 중재가 이미 독립 LLM 단계로 구현된 것은 아니다. 기존 정책을 갖고 있다는 설명은 타당하다.
- 이번 작업은 `STOP_REPEATED_REVIEW_ISSUES`, 근거 검사와 해결 주장 표시 분리, `requiredCorrections` 전송을 이미 제공한다. 기술적 결함을 사용자 제품 선택과 분리하는 기반이다. 이를 새 Supervisor 의미적 중재 기능이 완성된 것으로 표시하면 안 된다. 문서의 정책표에는 새 기술 중단을 반영해야 한다.
- 원문이 말하는 별도 `adtf-web-console`은 이 저장소에서 확인하지 못했다. 참고 문맥으로만 보존하며 UI에서 실제 Core 기능으로 표시하지 않는다는 원칙은 유지한다.

## 그대로 적용하면 안 되는 부분

### 모든 검토 뒤의 추가 LLM 호출

현재 주차 시험은7/7회 상한을 소진했다. Shadow Mode라도 실제 LLM을 호출하면 비용과 시간이 추가된다. 제안 생성 실패도 예약 횟수에 포함해야 하며 Shadow를 ‘무료 검사’로 표시하면 안 된다. 첫 단계는 기존 기록과 고정 사례의 오프라인 모의 평가다. 이후에도 근거 충돌·실제 반복 실패 등 선택한 경우에만 별도 상한/모델/토큰 기록을 가진 선택형 시험을 고려한다. 단순 형식 오류나 누락 인용을 해결하려고 새 LLM부터 호출하지 않는다.

### 정책 검사보다 먼저 의미적 권한을 주는 것

출처·버전·승인·예산·근거 형식 검사를 먼저 수행하고 현재 Policy의 기준 결정을 고정한다. 중재자는 이를 설명하거나 수정 지시/질문 초안을 제안할 수 있지만 차단을 해제하거나 사용자 승인을 대체할 수 없다. 모델 간 합의도 정답의 근거가 아니다. 명확한 기술적 충돌은 사용자 취향 질문 대신 재검토/보완 중단으로 처리한다.

### SMS 사례와 Scope 변경

원문 사례C는 Reviewer가 외부 SMS가 필요하다고 판단했다는 이유만으로 Scope 변경을 요청하는 것으로 읽힐 수 있다. 승인 범위에 없는 기능을 Reviewer가 요구했다면 먼저 그 지적이 잘못된 것인지 판단하고 기존 범위 안에서 수정해야 한다. 사용자가 실제로 새 기능을 원하거나 기존 목표를 범위 안에서 달성할 수 없는 근거가 있을 때만 별도 변경 승인을 검토한다. 원문의 해당 예시는 사용자의 명시적 신규 요청을 포함하도록 고치는 것이 좋다.

### 모호한 근거 참조와 재검토 기록

`evidenceRefs: string[]`만으로는 충분하지 않다. Plan/Scope/Review 버전과 해시, 실제 줄/Scope 출처 ID에 연결하고 참조를 검증해야 한다. 입력 지적에는 `review.issues`뿐 아니라 저장·품질·보존 검사가 만든 로컬 차단도 포함한다. 실제 주차 v2는 원시 issues0개였으므로 그 배열만 중재하면 중요한 문제를 누락한다. 알 수 없는 ID 추가나 필수 지적 누락은 거부해야 한다.

현재 `retryReview()`는 공식 Review가 없는 실패 상태의 제한된 재시도다. 이미 저장된 Review를 의미적으로 재검토하려고 이 메서드로 덮어쓰면 안 된다. 향후 재검토는 원래 Review를 보존하는 별도 제안/보충 감사 계약과 명시적 실행 예산이 필요하다.

## 다음 설계의 최소 요구사항

- 원래 Policy 결정, 중재 제안, 검증/거부 사유와 최종 실행을 별도 기록한다. proposal은 실행 명령이 아니다.
- 프로젝트/Plan/Scope/Review ID·버전·입력 해시, 지적 출처, 사용한 모델/프롬프트 버전을 기록한다. 현재 코드의 `scopeContractId` 등 기존 명명과 타입을 재사용한다.
- 분류는 재작업·실제 사용자 판단·Scope 변경·Reviewer 재검토·중단을 구분하되 현재 결정 타입과 일대일이라고 가정하지 않는다.
- 데이터 손실/승인 Scope 위반을 문구 보완이나 옵션 제안으로 낮춰 처리하지 않는다. 잘못된 Reviewer 지적은 원문 반례로 설명하고 공식 검토 원본은 바꾸지 않는다.
- 호출1회·시도1회 등 명시적 실험 상한, 실패 시 중단, 상태·캐시 재사용 조건을 먼저 정한다. 현재7회 예산에 숨은 호출을 넣지 않는다.

## 평가와 일정

현재 검증 결과인211개 오프라인 검사를 기준선으로 보존한다. 신규 기능 검증에는 기존 주차에서 드러난 근거 누락/공유 사례/Scope 위반과 별도의 미공개 사례를 함께 사용해야 한다. 모의 분류는 실제 의미 판단의 성능을 증명하지 않는다.

실제 Shadow 실험은 같은 입력·기획·모델 조건에서 기존 ADTF와 비교한다. 잘못된 재작업/불필요한 사용자 질문/Scope 확장/중요 결함 누락, 원문 근거 정확성, 반복 수·응답 시간·추가 토큰 비용을 측정한다. Supervisor가 자기 결과를 채점해 채택을 결정하지 않는다. 이득이 없거나 비용이 크면 비활성 상태를 유지한다.

작업 순서는 **현재 검토 판정 보완(2번) → 변경 영향표(3번) → 선택적 Supervisor 중재 모의 평가 후보(4번)**를 권장한다. 변경 영향표가 기술적 선행 필수조건이라는 뜻은 아니며, 이미 합의한 범위를 유지하고 동시에 두 개의 판단 계층을 바꿔 평가를 혼동하지 않기 위한 순서다. 변경 영향표와 중재 LLM 모두 이번에 구현하지 않는다.
