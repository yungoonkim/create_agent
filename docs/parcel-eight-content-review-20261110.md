# 택배 v2 기획안의 사용자 관점 검토

[실행 원자료와 SHA-256](acceptance/parcel-eight-20261110/manifest.json), [기획안 원문](acceptance/parcel-eight-20261110/plan.md), [모델 검토표](acceptance/parcel-eight-20261110/review.md)를 보존한다. 사용자 실행은 Gemini 반례 검토를 `STOP`으로 끝내고 분리한 시험 복사본에 정식 Review를 기록했다. 정책 결정은 `REQUEST_USER_APPROVAL`, 상태는 `awaiting_approval`이다. `pendingApprovalCreated:true`는 사용자 승인 요청 기록이고 `finalApprovalCreated:false`다. Scope 승인은 DEMO FIXTURE이므로 실제 사용자가 Scope나 기획안을 최종 승인했다는 뜻이 아니다.

## 사용자가 실제로 이해할 수 있는 동작

- 내용 이름·예정 날짜·선택 메모로 택배를 기록한다. 같은 이름도 별도 항목이다. 빈 이름이나 존재하지 않는 날짜는 저장하지 않는다. [기획안 18–27행](acceptance/parcel-eight-20261110/plan.md).
- 한 항목만 받음/미수령으로 전환하거나 수정·삭제한다. 삭제는 확인 후 진행하고 취소하면 기존 목록을 유지한다. [기획안 29–40행](acceptance/parcel-eight-20261110/plan.md).
- 새로고침 후 기록을 복원한다. 저장값 손상·읽기 오류는 기존 값을 덮어쓰지 않고 편집을 차단하며, 저장 실패 시 화면 변경을 확정하지 않는다. [기획안 42–50행과 72–89행](acceptance/parcel-eight-20261110/plan.md).
- 동시에 편집하는 탭은 하나로 제한한다. 다른 탭이나 Web Locks 미지원 브라우저에서는 편집을 막는다. 사용성 제약이므로 사용자가 실제 제품으로 만들 때 이 동작을 수용할지 확인해야 한다. [기획안 92–95행](acceptance/parcel-eight-20261110/plan.md).

Scope의 PARCEL-1/2/3 요구와 위 내용 사이에 명백한 누락·모순은 확인하지 못했다. 모델 검토표도 세 요구를 `reflected`로 표시하며 질문·지적이 0개다. 이것은 문서 근거와 정책 검사를 통과한 결과이지 제품 동작의 시험 결과나 의미상 완전성 보증은 아니다.

## 승인 전 확인할 점

1. **시험 경계:** 이번 Scope는 DEMO FIXTURE다. `awaiting_approval`은 분리한 시험 복사본의 상태이며 실제 사용자 최종 승인은 없다. 사용자 요구가 달라진 실제 프로젝트에 이 상태를 복사하지 않는다.
2. **탭 사용성:** 다른 탭에서 편집을 막는 정책이 사용자 기대에 맞는지 확인한다. Scope 자체에도 포함된 제약이므로 변경하려면 Scope/계획을 함께 조정해야 한다.
3. **극단적인 순번:** `nextSeq`와 `seq`를 안전 정수로 제한하지만 `nextSeq`가 최대 안전 정수에 도달한 상태에서 신규 등록 실패를 어떻게 안내할지는 명시하지 않는다. 일상 사용에서는 발생하기 어렵지만 구현 전 실패/무변경 동작을 한 문장 더 적으면 좋다. 필수 기능 누락으로 단정하지는 않는다.

따라서 **시험 기획안의 문서 검토는 승인 판단을 요청할 수준**이라고 본다. 실제 사용자가 제품 기획으로 승인하려면 위 시험 경계와 탭 정책을 직접 확인해야 한다. 이후 제품 구현·브라우저 동작 시험은 별도 단계이며 이번 결과에 포함되지 않는다. 추가 Gemini 호출은 없었다.
