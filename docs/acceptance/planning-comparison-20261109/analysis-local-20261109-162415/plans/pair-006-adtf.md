# 주간 식단표 브라우저 도구 기획안

## 1. 제품 목표 및 개요
본 도구는 사용자가 한 화면에서 월요일부터 일요일까지의 아침·점심·저녁 총 21개 고정 식단 칸을 확인하고, 메뉴와 메모를 등록·수정·삭제하며 브라우저 로컬 환경에 안전하게 보존할 수 있도록 지원하는 검증 가능한 웹 유틸리티다.

---

## 2. 사용자 여정 (User Journeys)

### 여정 1: 주간 식단표 확인 및 신규 메뉴 등록
1. 사용자가 브라우저(`http://localhost:4173`)로 도구에 접속한다.
2. 화면에 월요일부터 일요일까지, 각 요일별 아침·점심·저녁으로 구성된 21개의 고정 칸과 현재 채워진 칸 수(`0/21`)가 표시된다.
3. 사용자가 '화요일 점심' 빈 칸을 클릭하고, 메뉴 입력창에 "된장찌개", 메모 입력창에 "두부 많이"를 입력한 뒤 [등록] 버튼을 누른다.
4. '화요일 점심' 칸에 메뉴와 메모가 반영되고, 채워진 칸 수가 `1/21`로 갱신된다.

### 여정 2: 기존 메뉴 변경 및 삭제
1. 사용자가 이미 "된장찌개"가 등록된 '화요일 점심' 칸을 선택하고 메뉴를 "김치볶음밥"으로 입력한 뒤 저장을 시도한다.
2. 시스템이 "기존 메뉴를 새 메뉴로 변경하시겠습니까?"라는 확인 대화창을 표시한다.
3. 사용자가 [확인]을 누르면 메뉴가 "김치볶음밥"으로 교체되며, 채워진 칸 수는 `1/21`로 유지된다. 만약 [취소]를 누르면 "된장찌개"와 기존 메모가 그대로 유지된다.
4. 사용자가 '화요일 점심'의 [삭제] 버튼을 누르면 "메뉴와 메모를 삭제하시겠습니까?" 대화창이 나타나고, [확인] 시 빈 칸으로 초기화되며 채워진 칸 수는 `0/21`로 감소한다.

### 여정 3: 재접속 및 저장 무결성 보호
1. 브라우저 창을 닫은 뒤 동일한 프로필로 다시 접속하면 등록했던 식단 정보와 채워진 칸 수가 그대로 복원된다.
2. 만약 저장소 데이터가 외부 요인으로 깨지거나 스키마 규칙을 위반한 경우, 기존 손상 데이터를 덮어쓰거나 임의 초기화하지 않고 화면에 읽기 오류 안내를 표시하며 모든 변경 기능을 즉시 비활성화한다.

## 3. 요구사항별 상세 사양

### R-1: 고정 21칸 식단표 표시
- **정상 동작**: 월요일~일요일(7일)과 아침·점심·저녁(3끼니)의 조합으로 총 21개의 고정 그리드 칸을 렌더링한다. 요일 및 끼니의 순서는 고정된다 (`[Q-1]`).
- **검증 규칙**: 임의의 날짜 달력 연동, 과거/미래 주차 이동, 요일/끼니 추가·삭제 기능은 제공하지 않는다.
- **실패 및 무변경 동작**: 렌더링 시점에 21개 칸 구조가 충족되지 않으면 인터페이스 렌더링을 중단하고 오류를 표시한다.
- **인수 검증 예시**:
  - 화면 로드 시 월·화·수·목·금·토·일 컬럼과 아침·점심·저녁 로우가 정확히 21개의 개별 셀로 화면에 표시되는지 검증.

### R-2: 단일 칸 메뉴명 필수 등록 및 선택 메모 입력
- **정상 동작**: 사용자가 선택한 칸에 앞뒤 공백을 제거(trim)한 필수 메뉴명과 선택적 메모를 입력받아 등록한다. 동일한 메뉴명이 이미 다른 칸에 존재하더라도 등록을 허용한다 (`[Q-2]`).
- **검증 규칙**:
  - 메뉴명: 앞뒤 공백 제거 후 1글자 이상이어야 한다. 공백만으로 구성된 입력은 유효하지 않다.
  - 메모: 선택 입력 항목으로, 빈 값이어도 등록 가능하다.
  - 단일 칸당 최대 1개의 메뉴만 허용된다 (`[Q-2]`).
- **실패 및 무변경 동작**: 메뉴명이 비어 있거나 공백뿐인 경우, 칸 데이터를 갱신하지 않고 입력창 하단에 "메뉴명을 입력해주세요" 경고를 노출하며 기존 상태를 유지한다.
- **인수 검증 예시**:
  - '월요일 아침' 칸에 메뉴명으로 "  비빔밥  ", 메모로 "고추장 적게"를 입력하고 저장 시, 실제 표시되는 메뉴명은 "비빔밥"이어야 한다.
  - '월요일 점심' 칸에도 동일하게 "비빔밥"을 중복 등록할 수 있어야 한다.

### R-3: 기존 등록 칸 덮어쓰기 확인 및 취소
- **정상 동작**: 이미 메뉴가 존재하는 칸에 새 메뉴 또는 메모를 입력하고 저장 요청 시, 브라우저 확인 대화창을 표시한다. 사용자가 확인(Confirm)할 때만 데이터가 교체된다.
- **검증 규칙**: 확인 대화창에서 명시적 동의가 발생하기 전까지는 기존 데이터를 변경할 수 없다.
- **실패 및 무변경 동작**: 사용자가 확인 대화창에서 [취소]를 선택하면, 진행 중인 저장이 중단되고 기존 메뉴명과 메모가 화면 및 저장소에 그대로 유지된다.
- **인수 검증 예시**:
  - '수요일 점심'에 "라면"이 등록된 상태에서 "우동"으로 수정 시도 후 확인 창에서 [취소] 클릭 시, 해당 칸은 여전히 "라면"으로 유지된다.

### R-4: 단일 칸 수정/삭제 확인 및 격리성
- **정상 동작**:
  - 선택한 칸의 메뉴 또는 메모를 수정하거나 삭제(초기화)할 때 확인 대화창을 호출한다.
  - 수정 또는 삭제는 선택된 특정 칸 1개에만 적용되며, 다른 20개 칸의 데이터에는 일체 영향을 주지 않는다 (`[Q-2]`).
- **검증 규칙**: 삭제 시 확인을 거쳐야 하며, 확인 완료 시 메뉴명과 메모가 모두 제거되어 정상 빈 칸 상태로 전환된다 (`[Q-1]`).
- **실패 및 무변경 동작**: 삭제 확인 대화창에서 [취소]를 누르면 삭제 동작이 철회되고 기존 메뉴·메모가 유지된다.
- **인수 검증 예시**:
  - '금요일 저녁' 칸의 [삭제] 클릭 후 확인 창에서 [확인] 선택 시, 해당 칸만 빈 칸으로 전환되고 '목요일 저녁' 등 타 칸의 데이터는 변함없이 유지된다.

### R-5: 채워진 칸 수(0~21) 계산 및 반영
- **정상 동작**: 메뉴가 등록되어 있는 칸의 개수를 `채워진 칸: N / 21` 형태로 실시간 표시한다.
- **수치 증감 규칙**:
  - 빈 칸에 신규 메뉴 등록 성공 시: `+1` 증가.
  - 이미 메뉴가 있는 칸의 메뉴 수정/교체 성공 시: 증가하지 않음 (`±0`).
  - 등록 또는 수정 시도 중 유효성 실패 또는 확인 취소 시: 증가하지 않음 (`±0`).
  - 등록된 칸의 삭제 확인 성공 시: `-1` 감소.
  - 메뉴가 0개 등록된 상태도 정상 상태(`0/21`)로 취급한다 (`[Q-1]`).
- **실패 및 무변경 동작**: 저장 실패 또는 쓰기 차단 상황에서는 카운터가 변하지 않는다.
- **인수 검증 예시**:
  - 채워진 칸 수가 3인 상태에서, 이미 채워진 칸 1곳의 메뉴를 수정하여 성공했을 때 카운터는 3으로 유지된다.
  - 채워진 칸 수가 3인 상태에서, 채워진 칸 1곳을 삭제 완료했을 때 카운터는 2로 변경된다.

### R-6: 로컬 영속성, 데이터 무결성 및 동시성 제어
- **정상 동작**:
  - 유효한 데이터는 브라우저 새로고침이나 재접속 후에도 동일하게 유지된다.
  - 로컬 스토리지 키가 `null`(키 부재)인 경우에만 정상 최초 실행으로 간주하고, 빈 21칸 구조로 초기 렌더링한다.
- **무결성 및 손상 데이터 보존 규칙**:
  - 저장된 값이 빈 문자열, 공백 문자열, 파싱 불가능한 JSON, 지원하지 않는 `schemaVersion`, 고유 키 누락/중복, 21칸 스키마 위반인 경우:
    - **절대 자동 초기화하거나 빈 데이터로 덮어쓰지 않는다.**
    - 기존 로컬 스토리지 원본 값을 그대로 보존한다.
    - 화면에 "저장 데이터 오류: 변경이 차단되었습니다" 안내 메시지를 노출하고 모든 추가/수정/삭제 조작을 비활성화한다.
- **동시성 및 배타 잠금 규칙**:
  - Web Locks API를 사용하여 활성 탭이 배타적 잠금(lock)을 유지한다.
  - 잠금을 획득한 탭만 최신 데이터를 읽고 쓰기를 수행할 수 있다.
  - 잠금을 획득하지 못했거나 Web Locks API를 지원하지 않는 브라우저 환경에서는 모든 변경(쓰기) 작업을 차단한다.
  - 비소유 탭은 선점 탭이 종료된 후 새로고침해야만 최신 데이터를 읽어 작업을 시작할 수 있다.
- **쓰기 확정 파이프라인**:
  - [입력 및 후보 데이터 검증] -> [JSON 직렬화] -> [`localStorage.setItem` 성공] -> [메모리 상태 및 UI 갱신] 순서로 확정한다.
  - `setItem` 실패 시(용량 초과, 브라우저 예외 등) 메모리와 화면은 이전 상태를 유지하며 입력창 내용을 보존한다.
  - `setItem`은 성공했으나 이후 UI 반영 단계에서 런타임 오류가 발생한 경우, 롤백되었다고 허위 안내하지 않고 "저장은 완료되었으나 화면 갱신에 실패했습니다. 새로고침을 진행해 주세요"를 안내한다.
- **인수 검증 예시**:
  - `localStorage`의 대상 키에 `"{ invalid json "`를 수동 주입 후 새로고침 시, 스토리지는 지워지지 않고 원본 문자열을 유지하며 화면은 변경 차단 안내 상태가 되어야 한다.
  - 두 번째 탭을 열었을 때 배타 잠금 미획득으로 인해 등록/수정/삭제 버튼이 비활성화되는지 검증.

## 4. 범위 외 항목 (Excluded Scope)
- **X-1**: 로그인, 회원가입, 외부 백엔드 서버 통신, 타인과의 공유, 결제, 푸시 알림, AI 기반 식단 자동 추천 기능은 제공하지 않는다.
- **X-2**: 칼로리 계산, 영양 성분 분석, 장보기 목록 연동은 지원하지 않는다 (`[Q-3]`).
- **X-3**: 실제 코드 구현, 팀원 단위 태스크 실행, 실제 최종 사용자 배포 승인은 본 기획 범위에 포함되지 않는다.

## 5. 기술 설계 사양

### 5.1 데이터 모델 및 스키마
단일 로컬 스토리지 키(`weekly_meal_planner_data`)에 단일 JSON 문자열로 저장한다.

```json
{
  "schemaVersion": 1,
  "updatedAt": "2026-11-09T10:00:00.000Z",
  "slots": {
    "MON_BREAKFAST": { "menu": "토스트", "memo": "딸기잼" },
    "MON_LUNCH": { "menu": "김치찌개", "memo": "" },
    "MON_DINNER": null,
    "TUE_BREAKFAST": null,
    "TUE_LUNCH": null,
    "TUE_DINNER": null,
    "WED_BREAKFAST": null,
    "WED_LUNCH": null,
    "WED_DINNER": null,
    "THU_BREAKFAST": null,
    "THU_LUNCH": null,
    "THU_DINNER": null,
    "FRI_BREAKFAST": null,
    "FRI_LUNCH": null,
    "FRI_DINNER": null,
    "SAT_BREAKFAST": null,
    "SAT_LUNCH": null,
    "SAT_DINNER": null,
    "SUN_BREAKFAST": null,
    "SUN_LUNCH": null,
    "SUN_DINNER": null
  }
}
```

- **슬롯 키 식별자 (총 21개 고정)**:
  - 요일 접두사: `MON`, `TUE`, `WED`, `THU`, `FRI`, `SAT`, `SUN`
  - 끼니 접미사: `BREAKFAST`, `LUNCH`, `DINNER`
- **슬롯 값 규칙**:
  - 미등록 상태: `null`
  - 등록 상태: 객체 `{ "menu": string (비공백, 앞뒤 공백 제거됨), "memo": string }`
  - 슬롯 수는 정확히 21개여야 하며, 정의되지 않은 키가 포함되거나 필수 슬롯 키가 누락된 경우 스키마 위반으로 판정한다.

### 5.2 검증 및 오류 처리 매트릭스

| 상황 | 원본 데이터 상태 | 시스템 동작 | 사용자 안내 |
| :--- | :--- | :--- | :--- |
| 키 미존재 (`getItem === null`) | 없음 | 정상 최초 실행: 21개 빈 슬롯 상태 메모리 구성 | 빈 식단표 노출 (`0/21`) |
| 구문 손상 (`JSON.parse` 실패) | 보존 (수정/삭제 안 함) | 읽기 차단, 모든 쓰기 차단 | "저장소 데이터 형식이 손상되었습니다. 원본 보존을 위해 쓰기가 차단됩니다." |
| 빈 문자열/공백 데이터 | 보존 | 읽기 차단, 모든 쓰기 차단 | "비정상 저장소 데이터 감지. 변경 차단." |
| 버전 불일치 (`schemaVersion !== 1`) | 보존 | 마이그레이션 시도 금지, 쓰기 차단 | "지원하지 않는 데이터 버전입니다." |
| 키 누락/추가 키/타입 불일치 | 보존 | 읽기 차단, 모든 쓰기 차단 | "식단표 스키마 검증 실패. 원본 데이터 보존 중." |
| 배타 잠금 미획득 (타 탭 점유) | 유지 | 읽기 전용 모드 전환, 쓰기 비활성화 | "다른 탭에서 식단표를 편집 중입니다. 해당 탭 종료 후 새로고침하세요." |
| `setItem` 용량/할당량 오류 | 유지 | 메모리 롤백, 입력 폼 유지 | "저장 공간 부족으로 변경사항을 저장하지 못했습니다." |

### 5.3 트랜잭션 및 원자성 경계
1. 브라우저 로컬 스토리지는 프로세스 충돌이나 전원 차단 수준의 원자성을 보장하지 않으므로, 애플리케이션 레벨의 방어적 파이프라인을 준수한다.
2. 상태 변경 요청 시:
   - 단계 1: 후보 상태 객체 생성 및 스키마 검증.
   - 단계 2: 후보 상태 객체를 직렬화하여 문자열 생성.
   - 단계 3: 배타 잠금 확인 하에 `localStorage.setItem` 실행.
   - 단계 4: `setItem` 정상 반환 확인 후 인메모리 상태 갱신 및 화면 리렌더링.
   - 단계 5: 3단계 실패 시 인메모리 상태를 절대 변경하지 않으며 실패 안내 표시.
