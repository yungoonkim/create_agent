사용자가 Scope v6 승인 후 상세 기획과 아래 점검을 진행하도록 요청했다. 최초 v1은 Reviewer pass였지만 진행자 점검에서 누락을 발견했다. 승인 Scope는 바꾸지 않고 기획을 구체화한다. 다음 실제 사용자 답변을 반영하라:
1. 제목·마감일은 필수, 메모만 비워도 된다.
2. 마감일은 날짜와 시간까지 기록한다. 예: 11월 10일 오후 3시까지.
3. 삭제 버튼은 ‘정말 삭제할까요?’ 확인 후 삭제하며, 취소하면 화면과 저장 내용 모두 유지한다.

사용자 답변과 구별되는 다음 항목은 진행자의 품질 보완 요청이다. 설계 결정을 제안으로 명확히 쓰고 최종 사용자 승인 전에는 승인된 사실로 주장하지 않는다.
- 일상적인 이용 흐름과 구체적 입력/기대 결과를 문서 앞에 둔다. 변경 요약과 ID/기술 용어가 첫 화면을 지배하지 않게 하며 기술 절은 뒤로 분리한다. 사용자에게는 ‘장보기’ 예시로 설명한다.
- 제목 공백과 필수 날짜·시간 누락, 실제 달력에 없는 날짜, 올바르지 않은 시간 입력을 어떻게 거부하고 기존 내용을 보존하는지 명시한다. 날짜/시간 저장·표시의 기준과 지원 범위를 일관되게 정한다. 불필요한 시간대 변환·알림·기한순 정렬 기능은 추가하지 않는다. 지난 마감일 입력 처리도 모호하지 않게 설계 제안으로 명시한다.
- 동일 제목 항목 두 개 중 선택한 고유 ID만 수정/완료/취소/삭제되는 사례를 수락 조건에 넣는다.
- 완료/완료 취소와 정보 수정 후에도 원래 등록순이 유지되어야 한다. 같은 시각 등록도 안정적으로 순서가 정해지는 규칙을 기술 절에 제안한다.
- 저장 용량 초과나 접근 거부는 정상적인 실패 경로로 처리하고 성공 문구·화면만의 완료 상태를 남기지 않는다. 저장이 성공한 뒤에만 해당 화면 변경을 확정하며 실패하면 이전 화면과 저장 내용 유지, 오류 안내, 입력 보존/재시도 방법을 명시한다.
- 저장 JSON의 필드·타입·값·중복 ID·정렬 정보 등 목록 전체 불변식 검증과 손상 데이터 발견 시 기존 데이터를 임의 초기화/덮어쓰지 않는 처리를 구체화한다. 빈 저장소의 첫 실행은 손상과 구분한다.
- 브라우저 저장은 같은 주소·브라우저·프로필 일반 창에서 닫았다 다시 여는 유지 범위를 쉬운 말로 설명한다. 브라우저 저장 데이터를 직접 지움, 비공개 창, 다른 브라우저/기기에서의 한계도 설명한다. 물리 장애/전원 단절 무손실이나 무제한 저장/암호화를 보장하지 않는다.
- 다른 탭의 동시 편집 처리 범위·같은 주소로 열기 조건도 설계에서 명시한다. 기능을 늘리지 말고 일관된 단일 창 사용 조건 또는 충돌 감지 정책을 제안한다.
- HTML처럼 보이는 제목·메모도 코드 실행이 아닌 글자로 보여준다. 저장 변경 전체를 한 단위로 처리하는 경계와 실패 보장을 구체화한다.
- 실제 코드 구현·팀원 실행은 계속 보류하며 개발을 위한 구체적인 기획/작업 지시 작성은 포함한다. 기존 Scope·v1·Review를 보존하고 전체 5회 반복 예산과 새 기획 최종 승인을 유지한다.

Reviewer는 이 수정 요청의 각 항목이 실제로 해결됐는지 확인하고 미해결 사항을 pass로 넘기지 말라. 구현 대신 ‘나중에 정한다’로 핵심 데이터/실패/순서 규칙을 미루지 말라.
