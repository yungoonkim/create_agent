# 프로젝트 계획서: 개인용 웹 할 일 관리 도구 기획 및 작업 지시서 수립 (v4 - 초안)

> **안내**: 본 문서는 최종 사용자 승인 전 검토를 위한 기획 초안(Draft)입니다. 본 시험 세션에서는 기획 대상 제품의 실제 프로그램 코드 구현, 제품 단위·통합 테스트 실행, 팀원 에이전트 실행을 진행하지 않으며, 향후 구현을 위한 상세 기획 및 작업 지시서 수립의 품질 검증만을 목적으로 합니다. (단, 본 지침은 계획 수립 환경 자체의 기존 프레임워크 타입 검사나 회귀 검증을 제한하는 것이 아닙니다.)

---

## 1. 사용자 일상 이용 흐름 및 구체적 예시

사용자가 웹 브라우저 화면에서 실제로 경험하는 일상 동작 시나리오입니다.

1. **할 일 등록 (예: '장보기')**
   * 화면 상단 입력창에 제목(`장보기`), 추가 메모(`사과 3개, 우유 1팩`), 마감일시(`2026-11-10 15:00`)를 입력하고 '추가' 버튼을 누릅니다.
   * **제목**과 **마감일시**는 필수 입력 항목이며, **추가 메모**는 입력하지 않고 비워 두어도 정상 등록됩니다.
   * 이미 목록에 동일한 제목인 '장보기'가 있더라도, 각각 고유한 일련번호를 가진 별개의 할 일로 정상 추가됩니다.
   * 과거 날짜나 과거 시간을 마감일시로 입력해도 오류 없이 입력한 일시 그대로 기록되고 화면에 표시됩니다(기한 경과 경고나 시스템 알림 없음).
2. **목록 분리 및 등록 순서 확인**
   * 화면의 '할 일(진행 중)' 구역에 새로 추가한 '장보기'가 등록된 순서대로 표시됩니다.
   * 이미 완료 처리한 일들은 '완료한 일' 구역에 따로 분리되어 표시됩니다.
   * 컴퓨터 시계를 임의로 과거나 미래로 변경하더라도, 목록 정렬은 시계 시각이 아닌 '등록 성공 시 발급된 영속 고유 순번'에 따라 처음 등록된 선후 관계를 엄격히 유지합니다.
3. **완료 및 완료 취소 전환**
   * 장보기를 마친 후 해당 항목의 '완료' 버튼을 누르면 '완료한 일' 구역으로 이동합니다.
   * 실수로 완료를 눌렀거나 다시 진행해야 한다면 '완료 취소' 버튼을 눌러 언제든 원래의 '할 일' 구역으로 되돌릴 수 있습니다.
   * 완료나 완료 취소를 수행해도 해당 항목의 원래 등록 순번은 절대 바뀌지 않습니다.
4. **할 일 정보 수정**
   * 수정이 필요할 때 '수정' 버튼을 눌러 제목, 마감일시, 메모를 변경하고 저장할 수 있습니다.
   * 내용을 수정해도 원래 등록 순번은 그대로 유지되어 목록 내 위치가 바뀌지 않습니다.
   * 동일한 제목(`장보기`)이 여러 개 있더라도, 사용자가 선택하여 수정한 단 1건의 항목만 정확히 변경됩니다.
5. **삭제 및 취소 확인**
   * 불필요해진 항목의 '삭제' 버튼을 누르면 "정말 삭제할까요?"라는 확인 창이 나타납니다.
   * '취소'를 누르면 아무것도 변경되지 않고 기존 목록과 화면이 그대로 유지됩니다.
   * '확인'을 누르면 선택한 고유 항목 1건만 화면과 컴퓨터 저장소에서 완전히 삭제됩니다.
6. **창을 닫았다가 다시 열었을 때 복원 (로컬 보관)**
   * 인터넷 창을 완전히 닫거나 컴퓨터를 재부팅한 뒤 동일한 브라우저의 일반 창(동일한 주소)으로 다시 접속해도 이전에 기록해 둔 '할 일'과 '완료한 일' 목록이 그대로 복원됩니다.

## 2. 변경 요약 (Change Summary: v3 → v4)

승인된 요구 범위(`scope-v6`)와 사용자 직접 답변을 온전히 보존하면서, 기획자 제안의 사용자 귀속 오류를 바로잡고 저장 검증 규칙 및 순번 증가 조건을 명확화했습니다.

| 번호 | 변경 요청 내용 | 반영 내역 및 검증 기준 (Verifiable Checks) |
| :--- | :--- | :--- |
| **정합 1** | '과거 마감일 허용' 귀속 오류 수정 및 결정 구분 | v3에서 사용자 확정으로 잘못 표시되었던 '과거 마감일 오류 없는 등록 허용'을 '최종 승인 대기 설계 제안'으로 이동. 사용자 직접 답변(Q1~Q7, 제목·마감일 필수/메모 선택, 날짜+시간, 삭제 확인)과 위임/설계 제안을 엄격히 분리 (검증: 6절 대조 확인) |
| **정합 2** | 저장 검증 규칙 표 명시 및 빈 목록 기준 정의 | 봉투 구조 및 각 필드 타입·제약 규칙을 명확한 표로 정리. 빈 목록(`items: []`)의 `maxSequence = 0`으로 정의하여 `nextSequence >= 1` 성립 명시. 스키마/타입/값 위반 시 보정·덮어쓰기 없는 쓰기 차단 명시 (검증: 5.2 표 및 규칙 확인) |
| **정합 3** | `nextSequence` 증가 조건 및 안전 정수 한도 한정 | 신규 등록 성공 시에만 `nextSequence` 배정 및 1 증가. 수정/완료/취소/삭제 시 카운터 및 기존 순번 불변. 등록 전 배정값과 증가 후 값의 `Number.isSafeInteger` 검사 추가. 재시작 및 삭제 후 재등록 순서 보장 수락 기준 명시 (검증: AC-02, 5.1 확인) |
| **정합 4** | 시험 실행 경계 표현 명확화 | 서문의 비실행 대상을 '기획 대상 제품의 실제 구현, 제품 테스트, 팀원 에이전트 실행'으로 명시하여 기획 프레임워크 자체의 타입 검사·회귀 검증과 혼동되지 않도록 정정 (검증: 서문 안내문 확인) |
| **정합 5** | 기존 핵심 정책 및 일상 예시 보존 | 일상 이용 흐름 1절 배치 유지, 과거 마감일 단순 기록·표시 제안 유지(경과 표시/알림 없음), 단일 커밋 경계, 원본 데이터 보존, 순번 정렬, 삭제 확인 대화상자 등 v3의 유효 보완 내용 전면 보존 (검증: 1절~5절 일관성 확인) |

## 3. 세부 업무 분할 (WBS)

### 단계 1: 화면 구조 및 사용자 인터랙션 설계 (UI/UX)
* **작업 1.1**: 입력 폼 규격 명세
  * 한 줄 텍스트 제목 입력창, 여러 줄 텍스트 메모 입력창, 날짜 및 시간 선택기, 등록 버튼 배치
* **작업 1.2**: 목록 분리 레이아웃 명세
  * '할 일(진행 중)' 구역과 '완료한 일' 구역의 분리 배치
  * 항목별 제목, 마감일시, 메모 표시 영역 및 영속 순번 오름차순 정렬 정의
* **작업 1.3**: 제어 인터랙션 명세
  * 완료 및 완료 취소 전환 버튼
  * 인라인 또는 모달 방식의 정보 수정 인터페이스
  * 삭제 클릭 시 브라우저 표준 확인창("정말 삭제할까요?") 호출 및 분기 정의

### 단계 2: 입력값 검증 및 일관성 정책 수립 (Validation Policy)
* **작업 2.1**: 필수값 및 마감일시 유효성 검사 규칙 수립
  * 제목: 앞뒤 공백 제거 후 1자 이상 필수 (공백 문자만 있는 입력 거부)
  * 추가 메모: 선택 입력 (공백 허용)
  * 마감일시: 필수 입력. 시간대 오프셋 없는 정규 문자열(`YYYY-MM-DDTHH:mm`) 형식 강제
  * 날짜/시간 검증: 지원 연도 `0001`~`9999`, 윤년 포함 실존 달력 날짜, 시(`00`~`23`), 분(`00`~`59`)
  * 검증 실패 시: 기존 저장소 및 화면 무변경 유지, 사용자 입력값 완전 보존
* **작업 2.2**: 마감일시 등록 제안 처리 원칙 명세
  * 과거 일시 입력 오류 없이 허용(제안). 현재 시각 비교, 기한 경과 표시, 시스템 알림 배제
* **작업 2.3**: 안전한 텍스트 렌더링 규격 정의
  * HTML 태그 문자가 입력되어도 실행되지 않고 순수 텍스트(Text Content)로 화면에 출력

### 단계 3: 데이터 모델 및 영속성 트랜잭션 설계 (Data Model & Storage)
* **작업 3.1**: 데이터 봉투(Envelope) 및 정렬 모델 명세
  * 최상위 봉투 구조: `{ schemaVersion: 1, nextSequence: number, items: TodoItem[] }`
  * 신규 등록 성공 시에만 `nextSequence` 배정 및 1 증가. 수정/완료/취소/삭제 시 카운터 및 기존 순번 불변
  * 배정값 및 증가 후 값 모두 `Number.isSafeInteger` 검증
  * 목록 정렬: `sequenceNumber` 오름차순(ASC) 단일 기준
* **작업 3.2**: 원자적 단일 커밋 경계 설계
  * 검증 → 직렬화 → `localStorage.setItem(KEY, jsonString)` 실행
  * `setItem` 호출 전/호출 실패 시: 기존 저장소 및 화면 유지, 입력값 보존
  * `setItem` 성공 후 렌더링 실패 시: 저장 완료 및 새로고침 복원 안내
* **작업 3.3**: 초기 로딩 및 손상 데이터 격리 정책 수립
  * `localStorage.getItem(KEY) === null`인 경우에만 정상 빈 목록(`items: []`, `nextSequence: 1`) 초기화
  * 스키마/타입/값 규칙 위반 데이터는 자동 보정이나 덮어쓰기 없이 쓰기 차단 및 경고 표시
* **작업 3.4**: 단일 탭 순차 편집 및 운영 환경 제약 명세
  * 단일 탭 순차 조작 지원 명시, 동일 Origin 고정 주소 기준 안내 및 다중 탭 동시성 한계 명시

### 단계 4: 작업 지시서 작성 및 검토 (Handover)
* **작업 4.1**: 컴포넌트별 상태 전이 규격서 작성
* **작업 4.2**: 브라우저 로컬 저장소 스키마 및 직렬화 지침서 완성

## 4. 관찰 및 검증 가능한 수락 기준 (Acceptance Criteria)

| ID | 요구사항 추적 | 검증 절차 및 관찰 가능한 기대 결과 |
| :--- | :--- | :--- |
| **AC-01** | 입력 검증 및 중복 등록 (REQ-01) | 1. 제목을 공백만 입력하거나 마감일시를 비워두고 '추가' 클릭 시 등록이 거부되고 작성 중이던 입력 내용이 그대로 보존된다.<br>2. 존재하지 않는 날짜(예: `2026-02-31T10:00`) 입력 시 등록이 거부되고 기존 데이터는 변경되지 않는다.<br>3. 과거 마감일시(예: `2020-01-01T09:00`)를 입력해도 오류나 경고 없이 정상 등록되며, 입력한 일시가 그대로 표시된다.<br>4. 제목 `장보기`, 메모 `사과`, 마감일시 `2026-11-10T15:00` 등록 후 동일한 내용으로 한 번 더 등록 시, 각각 서로 다른 고유 ID와 고유 순번을 가진 독립된 2건이 '할 일' 목록에 나타난다. |
| **AC-02** | 목록 분리 및 영속 순번 정렬 (REQ-02) | 1. 미완료 항목과 완료 항목이 화면상 분리된 구역에 각각 표시된다.<br>2. 항목 A 등록(순번 1) 후 항목 B 등록(순번 2) 시, PC 시계를 과거로 되돌린 상태에서 항목 C를 등록(순번 3)하더라도 목록 정렬은 오직 순번 오름차순(A → B → C)을 정확히 유지한다.<br>3. 항목 B를 삭제한 뒤 새로운 항목 D를 등록하면 항목 D는 순번 4를 부여받아 순번 재사용 없이 A(1) → C(3) → D(4) 순서를 유지한다.<br>4. 브라우저를 닫고 다시 열거나, 항목을 수정/완료/취소하더라도 기존 항목의 순번은 변경되지 않고 등록 선후 관계가 유지된다. |
| **AC-03** | 완료 및 완료 취소 전환 (REQ-03) | 1. '할 일' 목록의 특정 항목에서 '완료' 버튼을 누르면 해당 항목만 '완료한 일' 구역으로 이동한다.<br>2. '완료한 일' 구역에서 '완료 취소' 버튼을 누르면 다시 '할 일' 구역으로 복귀하며 순번 및 등록 순서는 유지된다. |
| **AC-04** | 정보 수정 격리 (REQ-04) | 1. 동일 제목 `장보기` 2건 중 특정 1건의 수정을 눌러 제목을 `서점 방문`으로 변경하고 저장 시, 해당 고유 ID를 가진 항목만 변경되고 다른 `장보기` 항목은 변경되지 않는다.<br>2. 수정 중 제목을 공백으로 지우거나 마감일시를 지우고 저장을 누르면 저장이 거부되고 이전 저장 내용이 그대로 유지된다.<br>3. 수정 완료 시에도 `sequenceNumber`와 `nextSequence`는 절대 변경되지 않는다. |
| **AC-05** | 삭제 확인 대화상자 (REQ-05) | 1. 항목의 '삭제' 버튼 클릭 시 브라우저 확인창("정말 삭제할까요?")이 호출된다.<br>2. '취소'를 클릭하면 데이터와 화면에 아무런 변경이 발생하지 않는다.<br>3. '확인'을 클릭하면 해당 고유 ID를 가진 항목 1건만 화면과 저장소에서 완전히 제거되며, `nextSequence` 값은 줄어들지 않고 유지된다. |
| **AC-06** | 단일 커밋 및 저장 실패·손상 격리 (REQ-06) | 1. 정상 등록/수정/완료 후 브라우저를 닫고 동일 고정 주소로 다시 접속했을 때 데이터와 분리 목록이 온전히 복원된다.<br>2. `localStorage.setItem` 호출 실패(용량 초과, 보안 차단 등) 시 성공 표시가 나타나지 않고, 화면은 이전 상태를 유지하며 사용자의 입력 내용은 폼에 그대로 보존된다.<br>3. 저장소의 데이터가 빈 문자열(`""`), 스키마 불일치, 필드 타입 위반, ID/순번 중복 등 손상 상태인 경우 빈 목록으로 자동 덮어쓰지 않고 쓰기를 차단하는 경고 화면을 표시한다.<br>4. `nextSequence` 또는 다음 증가값이 `Number.MAX_SAFE_INTEGER`를 초과하는 경우 신규 등록을 차단하고 기존 저장소와 화면 상태를 그대로 유지한다. |
| **AC-07** | 웹 UI 조작 및 안전한 문자열 출력 (REQ-07) | 1. 제목에 `<script>alert(1)</script>` 또는 `<b>장보기</b>`를 입력하고 등록했을 때 태그가 실행되거나 스타일이 적용되지 않고 입력한 문자열 그대로 화면에 출력된다.<br>2. 마우스 클릭 및 표준 폼 입력만으로 모든 기능이 직관적으로 조작된다. |

## 5. 기술 사양 및 설계 제안 (Technical Specifications & Proposals)

> **기술 용어 안내**:
> * **로컬 저장소(LocalStorage)**: 사용자의 웹 브라우저가 컴퓨터 내부에 제공하는 문자열 데이터 보관소입니다.
> * **봉투 구조(Envelope)**: 데이터 목록뿐만 아니라 버전 정보, 다음 일련번호 등 관리 정보를 하나의 큰 상자처럼 묶어서 보관하는 형식입니다.
> * **커밋 경계(Commit Boundary)**: 작업이 '공식적으로 저장 완료'되었다고 확정하는 정확한 분기점입니다.
> * **안전한 정수(Safe Integer)**: 컴퓨터가 계산 오차 없이 정확하게 다룰 수 있는 정수 범위(`Number.isSafeInteger`, 최대 약 9,007조)입니다.

### 5.1 데이터 모델 및 순번 불변성 사양 제안
* **저장소 봉투 규격 (Storage Envelope)**:
  브라우저 저장소의 단일 고정 키(`todo_app_data_v1`)에 아래 구조를 단일 JSON 문자열로 직렬화하여 저장합니다.
  ```json
  {
    \"schemaVersion\": 1,
    \"nextSequence\": 3,
    \"items\": [
      {
        \"id\": \"todo-20261108-000001-a1b2\",\n        \"title\": \"장보기\",
        \"memo\": \"사과 3개\",
        \"dueDateTime\": \"2026-11-10T15:00\",
        \"isCompleted\": false,\n        \"sequenceNumber\": 1
      },
      {
        \"id\": \"todo-20261108-000002-c3d4\",
        \"title\": \"장보기\",
        \"memo\": \"우유 1팩\",
        \"dueDateTime\": \"2026-11-10T15:00\",
        \"isCompleted\": true,
        \"sequenceNumber\": 2
      }
    ]
  }
  ```
* **순번 배정 및 증가 규칙**:
  * `nextSequence`는 **오직 새로운 할 일 항목의 등록 성공 시에만** 현재 값을 해당 항목의 `sequenceNumber`로 배정하고 정확히 1 증가합니다.
  * 기존 항목의 **수정, 완료 전환, 완료 취소, 삭제** 시에는 `nextSequence`와 기존 항목들의 `sequenceNumber`를 변경하거나 재계산하지 않습니다.
  * 신규 등록 직전 배정할 `nextSequence` 값과 증가 후의 `nextSequence + 1` 값이 모두 `Number.isSafeInteger`를 만족하는지 검사하며, 한도 초과 시 신규 등록을 거부하고 저장소·화면·카운터를 그대로 유지합니다.
  * 목록 정렬은 오직 `sequenceNumber` 오름차순(ASC)만을 유일한 기준으로 적용합니다.

### 5.2 저장소 데이터 검증 규칙 (Validation Rules)

로컬 저장소 데이터를 불러올 때 아래 검증 규칙을 엄격히 적용합니다.

| 필드 / 항목 | 타입 및 제약 규칙 | 위반 시 처리 |
| :--- | :--- | :--- |
| **최상위 객체** | `null`이 아닌 일반 JSON 객체 (`typeof obj === 'object'`) | 쓰기 차단 (손상 격리) |
| **`schemaVersion`** | 정수 `1` (`Number.isInteger(v) && v === 1`) | 쓰기 차단 (손상 격리) |
| **`nextSequence`** | `Number.isSafeInteger(v) && v >= 1` | 쓰기 차단 (손상 격리) |
| **`items`** | 배열 (`Array.isArray(items) === true`) | 쓰기 차단 (손상 격리) |
| **`items[].id`** | 앞뒤 공백 없는 비어 있지 않은 문자열 (`string`, `v.length > 0`) | 쓰기 차단 (손상 격리) |
| **`items[].title`** | 앞뒤 공백 제거 후 1자 이상인 문자열 (`v.trim().length > 0`) | 쓰기 차단 (손상 격리) |
| **`items[].memo`** | 문자열 (`typeof v === 'string'`, 빈 문자열 허용) | 쓰기 차단 (손상 격리) |
| **`items[].dueDateTime`** | 유효한 정규 문자열 (`YYYY-MM-DDTHH:mm`, 실존 날짜 및 시간) | 쓰기 차단 (손상 격리) |
| **`items[].isCompleted`** | 실제 참/거짓 불리언 값 (`typeof v === 'boolean'`) | 쓰기 차단 (손상 격리) |
| **`items[].sequenceNumber`** | `Number.isSafeInteger(v) && v >= 1` | 쓰기 차단 (손상 격리) |
| **불변식 1: ID 고유성** | `items` 내 모든 항목의 `id`는 상호 중복되지 않아야 함 | 쓰기 차단 (손상 격리) |
| **불변식 2: 순번 고유성** | `items` 내 모든 항목의 `sequenceNumber`는 상호 중복되지 않아야 함 | 쓰기 차단 (손상 격리) |
| **불변식 3: 순번 한계** | `nextSequence > maxSequence` 유지 (단, `items`가 빈 배열일 때 `maxSequence = 0`으로 정의하여 `nextSequence >= 1` 성립) | 쓰기 차단 (손상 격리) |

* **손상 격리 정책**: 알 수 없는 스키마 버전, 알 수 없는 필드, 타입 위반, 값 규칙 위반이 감지되면 데이터를 임의로 보정하거나 빈 배열로 덮어쓰지(초기화) 않습니다. 화면에 데이터 손상 경고를 표시하고 신규 등록/수정/완료/취소/삭제 등의 쓰기 동작을 전면 차단하여 원본 데이터를 보존합니다.

### 5.3 마감일시 형식 및 검증 사양 제안
* **단일 정규 포맷**: `YYYY-MM-DDTHH:mm` (시간대 오프셋 없는 순수 달력 날짜 및 시·분).
* **유효성 규칙**:
  * 지원 연도 범위: `0001` ~ `9999` (4자리 연도).
  * 달력 유효성: 윤년을 포함하여 해당 월에 실제로 존재하는 날짜만 허용 (2월 30일 등 거부).
  * 시간 유효성: 시 `00`~`23`, 분 `00`~`59`.
* **처리 제약**: 타임존(UTC) 변환을 수행하지 않으며, 현재 시각과의 대소 비교, 기한 경과 안내, 알림 등은 시스템에 포함하지 않습니다.

### 5.4 로컬 저장소 원자적 커밋 경계
* **커밋 경계 정의**: `localStorage.setItem(KEY, serializedString)` 호출의 정상 반환을 유일한 '커밋 완료'로 정의합니다.
* **저장 실패 시**: `setItem` 호출 전 또는 호출 중 예외(용량 초과 `QuotaExceededError`, 접근 차단 등) 발생 시 화면은 이전 상태를 유지하고 사용자 입력은 폼에 보존됩니다.
* **저장 후 렌더링 실패 시**: `setItem` 성공 후 화면 갱신에 실패한 경우 저장을 무효화하지 않고 새로고침 복원을 안내합니다.
* **초기 로딩 조건**: `localStorage.getItem(KEY) === null` (키 미존재)인 경우에만 정상 빈 목록(`{ schemaVersion: 1, nextSequence: 1, items: [] }`)으로 시작합니다.

### 5.5 브라우저 저장소 보관 범위 및 단일 탭 운용 한계
* **보장 환경**: 동일 컴퓨터, 동일 브라우저, 동일 사용자 프로필, 일반 창 환경에서 **동일한 고정 주소(동일 Origin)** 접속 시 복원 보장.
* **보장 한계**:
  * 브라우저에서 '쿠키 및 기타 사이트 데이터 삭제' 시 데이터가 영구 삭제될 수 있음.
  * 시크릿 모드 창 종료 시 데이터 소멸.
  * 서로 다른 브라우저 간(크롬 ↔ 엣지), 기기 간 동기화 미지원.
  * `file://` 로컬 파일 열기 방식은 브라우저 정책상 영속성이 불안정하므로 보장 대상 제외.
* **단일 탭 지원**: 본 도구는 단일 탭 순차 조작만을 공식 지원하며, 다중 탭 동시 편집에 따른 덮어쓰기 방지나 트랜잭션 락은 제공하지 않습니다. (`storage` 이벤트 감지 시 화면에 편집 차단 및 새로고침 안내를 표시)

## 6. 미확정 결정 사항 및 승인 대기 항목 (Unknowns & Pending Decisions)

사용자의 명시적 확정 답변을 거친 항목과 기획자가 최종 승인을 위해 제안하는 항목을 아래와 같이 명확히 분리합니다.

* **사용자 확정 선택 사항 (Settled Decisions)**:
  1. 이용 화면 형태: 웹 브라우저에서 버튼을 눌러 사용하는 방식 (Q-1).
  2. 기록 정보 범위: 제목·추가 메모·마감일 기록 (Q-2).
  3. 수정 및 삭제: 수정과 삭제 모두 가능 (Q-3).
  4. 완료 취소: 완료한 항목을 다시 미완료(진행 중)로 되돌리기 가능 (Q-4).
  5. 목록 표시 방식: '할 일'과 '완료한 일'을 나누고 각각 등록 순서로 표시 (Q-5).
  6. 중복 등록 허용: 동일한 제목도 각각 별개의 할 일로 추가 가능 (Q-6).
  7. 데이터 보관 원칙: 사용자 컴퓨터에만 저장(세부 구현 방식은 기획에 위임) (Q-7).
  8. 입력 필수 여부 상세: 제목과 마감일시는 필수 입력, 추가 메모는 선택 입력.
  9. 마감일시 상세 단위: 날짜와 시간을 모두 포함하여 기록 및 표시.
  10. 삭제 인터랙션 상세: 삭제 버튼 클릭 시 "정말 삭제할까요?" 확인창을 띄우고 취소 시 변경 없이 유지.
* **최종 승인 대기 설계 제안 사항 (Proposals Pending Approval)**:
  1. **과거 마감일시 등록 허용 제안**: 과거 날짜·시간도 오류 없이 등록을 허용하되, 기한 경과 표시나 알림 없이 입력 문자열 그대로 기록·표시하는 설계안 채택 여부.
  2. **저장소 Envelope 및 단일 키 명칭 제안**: `{ schemaVersion: 1, nextSequence, items }` 봉투 구조와 고정 키 `todo_app_data_v1` 채택 여부.
  3. **마감일시 정규 표기 제안**: 시간대 정보 없는 `YYYY-MM-DDTHH:mm` 단일 표준 표기 사용 여부.
  4. **운영 환경 및 다중 탭 동작 제안**: 동일 Origin 로컬 고정 주소 기준 운용 및 `storage` 이벤트 감지 시 새로고침 안내 후 쓰기 차단 기본 제안 채택 여부.
