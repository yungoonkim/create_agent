v3의 나머지 내용을 유지하면서 아래 좁은 정합성 문제를 수정하라. 승인 Scope v6와 실제 사용자 답변은 바꾸지 않는다. 이전 기획·Review 원문을 보존하고 새 버전은 최종 사용자 승인을 기다린다. Reviewer는 아래 항목별 실제 반영 여부를 대조하라.

1. 가장 중요: v3 6절의 ‘사용자 확정 선택 사항’ 4번(과거 마감일 허용)은 사용자가 직접 답한 적이 없는 진행자의 설계 제안이다. 이를 사용자 확정 사항으로 잘못 표시했다. 반드시 ‘최종 승인 대기 설계 제안’으로 옮겨라. 실제 사용자가 답한 것은 원래 Q-1~Q-7과 추가 상세 답변 3개(제목·마감일 필수/메모 선택, 날짜+시간, 삭제 확인)뿐이다. 기획자의 제안을 사용자의 결정으로 잘못 귀속하지 않는다. 날짜 표기/로컬 저장/단일 탭 조건 등도 위임·설계 제안과 사용자 직접 선택을 정확히 구분하라.
2. 기술 절의 저장 검증 규칙을 짧은 표로 명확히 하라: schemaVersion은 정수1, nextSequence와 각 sequenceNumber는 1 이상의 안전한 정수, items는 배열, id는 비어 있지 않은 문자열로 고유, title은 앞뒤 공백 제거 후 비어 있지 않은 문자열, memo는 문자열(빈 문자열 허용), dueDateTime은 앞서 정한 유효한 정규 날짜+시간, isCompleted는 실제 boolean만 허용. 모든 항목의 ID/sequenceNumber 고유성 검증과 nextSequence>maxSequence를 유지한다. 유효한 빈 items의 maxSequence는0으로 정의해 빈 목록의 nextSequence>=1도 명확히 한다. 알려지지 않은 스키마 버전/필드 타입/값 위반은 보정·덮어쓰기 없이 쓰기 차단한다.
3. nextSequence는 성공한 새 등록에서만 배정·1증가한다. 수정/완료/취소/삭제 시 카운터와 기존 순번을 변경하거나 재계산하지 않는다. 등록 전에 배정할 값과 증가 후 값이 모두 안전한 정수인지 검사하고 한도 초과 시 저장·화면·카운터를 그대로 유지한다. 재시작·삭제 후 재등록에서도 등록순이 유지됨을 수락 기준에 간결히 덧붙여라.
4. 서문의 ‘테스트 실행을 하지 않는다’는 이번 세션에서 계획 대상 제품을 구현/제품 테스트/팀원 실행하지 않는다는 뜻으로 명확히 표현하라. ADTF 프레임워크 자체의 기존 타입 검사·회귀 시험까지 금지한 것으로 표현하지 말라. 제품 구현이나 제품 검증을 이미 했다고 주장하지 않는다.
5. 일상 예시를 맨 앞에 유지하고 기술 내용은 뒤 절에 둔다. 과거 마감일은 ‘오류 없이 등록 가능한 설계 제안’으로만 유지하며 기한 경과 표시·알림 기능을 다시 추가하지 않는다. 저장 실패 전후 경계/원본 보존/순번 정렬/삭제 확인/사용자 입력 규칙 등 v3의 올바른 보완은 그대로 유지하라.

추가 기능을 도입하거나 이전 내용을 모두 다시 설계하지 말고 위 정합성 수정에 집중하라.
