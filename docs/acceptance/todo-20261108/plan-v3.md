# 프로젝트 계획서: 개인용 웹 할 일 관리 도구 기획 및 작업 지시서 수립 (v3 - 초안)

> **안내**: 본 문서는 최종 사용자 승인 전 검토를 위한 후보 기획 초안(Draft)입니다. 본 시험 세션에서는 실제 프로그램 코드 구현, 테스트 실행, 팀원 에이전트 실행을 진행하지 않으며, 향후 구현을 위한 상세 기획 및 작업 지시서 수립 품질 검증만을 목적으로 합니다.

---

## 1. 사용자 일상 이용 흐름 및 구체적 예시

사용자가 웹 브라우저 화면에서 실제로 경험하는 동작 시나리오입니다.

1. **할 일 등록 (예: '장보기')**
   * 화면 상단 입력창에 제목(`장보기`), 추가 메모(`사과 3개, 우유 1팩`), 마감일시(`2026-11-10 15:00`)를 입력하고 '추가' 버튼을 누릅니다.
   * **제목**과 **마감일시**는 필수 입력 항목이며, **추가 메모**는 입력하지 않고 비워 두어도 정상 등록됩니다.
   * 이미 목록에 동일한 제목인 '장보기'가 있더라도, 각각 고유한 일련번호(ID)를 가진 별개의 할 일로 정상 추가됩니다.
   * 과거 날짜나 과거 시간을 마감일시로 입력해도 등록이 거부되지 않으며, 별도의 시스템 알림이나 경고 표시 없이 입력한 일시 그대로 기록되고 표시됩니다.
2. **목록 분리 및 등록 순서 확인**
   * 화면의 '할 일(진행 중)' 구역에 새로 추가한 '장보기'가 등록된 순서대로 표시됩니다.
   * 이미 완료 처리한 일들은 '완료한 일' 구역에 따로 분리되어 표시됩니다.
   * 컴퓨터 시계를 임의로 과거나 미래로 변경하더라도, 목록의 정렬 순서는 시계 시각이 아닌 '등록 성공 시 부여된 고유 순번'에 따라 처음 등록된 선후 관계를 엄격히 유지합니다.
3. **완료 및 완료 취소 전환**
   * 장보기를 마친 후 해당 항목의 '완료' 버튼을 누르면 '완료한 일' 구역으로 이동합니다.
   * 실수로 완료를 눌렀거나 다시 진행해야 한다면 '완료 취소' 버튼을 눌러 언제든 원래의 '할 일' 구역으로 되돌릴 수 있습니다.
   * 완료나 완료 취소를 수행해도 해당 항목의 원래 등록 순번은 절대 바뀌지 않습니다.
4. **할 일 정보 수정**
   * 수정이 필요할 때 '수정' 버튼을 눌러 제목, 마감일시, 메모를 변경하고 저장할 수 있습니다.
   * 내용을 수정해도 등록 순번은 그대로 유지되어 목록 내 위치가 바뀌지 않습니다.
   * 동일한 제목(`장보기`)이 여러 개 있더라도, 사용자가 선택하여 수정한 단 1건의 항목만 정확히 변경됩니다.
5. **삭제 및 취소 확인**
   * 불필요해진 항목의 '삭제' 버튼을 누르면 \"정말 삭제할까요?\"라는 확인 창이 나타납니다.
   * '취소'를 누르면 아무것도 변경되지 않고 기존 목록과 화면이 그대로 유지됩니다.
   * '확인'을 누르면 선택한 고유 항목 1건만 화면과 컴퓨터 저장소에서 완전히 삭제됩니다.
6. **창을 닫았다가 다시 열었을 때 복원 (로컬 보관)**
   * 인터넷 창을 완전히 닫거나 컴퓨터를 재부팅한 뒤 동일한 브라우저의 일반 창(동일한 주소)으로 다시 접속해도 이전에 기록해 둔 '할 일'과 '완료한 일' 목록이 그대로 복원됩니다.

## 2. 변경 요약 (Change Summary: v2 → v3)

승인된 요구 범위(`scope-v6`)와 사용자의 확정 답변을 엄격히 유지하면서, 진행자 품질 점검 피드백 10개 항목을 충실히 반영하여 기획을 보완했습니다.

| 번호 | 변경 요청 내용 | 반영 내역 및 검증 기준 (Verifiable Checks) |
| :--- | :--- | :--- |
| **요청 1** | 범위 단순화 및 불필요한 기능 제안 제거 | 현재 시각 비교 및 '[기한 경과]' 텍스트 표시 제안을 완전히 제거. 과거 마감일도 제약 없이 등록되고 문자열 그대로 표시됨을 명시 (검증: 기한 경과/알림/기한순 정렬/검색/동기화 요구 없음 확인) |
| **요청 2** | 확정 선택과 설계 제안의 엄격한 분리 | 제목·마감일시 필수/메모 선택, 날짜+시간, 삭제 확인은 '사용자 확정 선택'으로 분류하고, 스키마/저장 형식/충돌 방지 등은 '설계 제안'으로 구분. 사용자 흐름을 1절에 전진 배치 (검증: 1절 및 6절 구성 확인) |
| **요청 3** | 마감일시 정규 형식 및 유효성 엄격화 | 타임존 없는 달력 날짜+시·분 형태(`YYYY-MM-DDTHH:mm`) 단일 정규 형식 강제. 연도 `0001`~`9999`, 윤년 포함 실존 날짜, 시 `00`~`23`, 분 `00`~`59` 검증 명시. UTC 변환/현재 시각 판단 배제 (검증: AC-01, 기술 사양 5.2 확인) |
| **요청 4** | 영속 단조 증가 순번에 의한 정렬 단일화 | `createdAt` 시각 정렬 결함(PC 시계 역행 문제)을 제거하고, 등록 성공 시 발급되는 단조 증가 정수 `sequenceNumber`를 유일 정렬 기준으로 확정. 수정/완료/삭제 시 순번 불변 및 안전 정수 한도 검증 추가 (검증: AC-02, 기술 사양 5.1 확인) |
| **요청 5** | 저장 Envelope 구조화 및 엄격한 검증 | 최상위 객체 `{ schemaVersion, nextSequence, items }` 봉투 규격 정의. 로드 시 배열 여부, 필수 키, 타입, 빈 문자열/공백 검증, 순번 고유성 및 `nextSequence > max(sequenceNumber)` 검증 수립 (검증: 기술 사양 5.2 확인) |
| **요청 6** | 초기 실행 조건 및 손상 데이터 엄격 격리 | `localStorage.getItem(key) === null`일 때만 빈 목록 허용. `""`, 잘못된 JSON, null JSON, 스키마 불일치, 읽기 예외는 '손상 데이터'로 분류하여 자동 초기화/덮어쓰기를 전면 차단하고 쓰기 동작 잠금 (검증: AC-06, 기술 사양 5.3 확인) |
| **요청 7** | 단일 JSON 직렬화 및 커밋 경계 명확화 | 전체 데이터를 고정 단일 키에 한 번의 `setItem`으로 저장하는 원자적 경계 정의. `setItem` 성공 전 실패는 입력 보존 및 화면 무변경, `setItem` 후 화면 렌더링 실패는 새로고침 복원 안내로 분리 정의 (검증: AC-06, 기술 사양 5.3 확인) |
| **요청 8** | 저장소 삭제 한계 정확화 및 고정 오리진 명시 | 단순 이미지 캐시 삭제와 구분하여 '쿠키 및 기타 사이트 데이터 삭제'로 정확히 명시. 동일 origin(프로토콜/호스트/포트) 고정 주소 사용 권장 및 `file://` 경로 미보장 안내 (검증: 기술 사양 5.4 확인) |
| **요청 9** | 단일 탭 순차 편집 한정 및 락 미보장 명시 | 지원 운용 범위를 '단일 탭 순차 편집'으로 명시. `storage` 이벤트 감지는 외부 변경 안내 후 쓰기 차단 및 새로고침 유도 수준이며, 동시 편집 트랜잭션 락/다중 탭 안전성은 보장하지 않음을 선언 (검증: 기술 사양 5.5 확인) |
| **요청 10** | 기존 무변경/보존 및 텍스트 렌더링 기준 보존 | 동일 제목 중 지정 ID 단 1건 제어, 삭제 취소 무변경, 유효성 실패 시 기존 데이터 무변경 및 입력값 보존, 저장 실패 시 성공 간주 금지, HTML 태그 문자열 출력 기준 유지 (검증: AC-01~AC-07 확인) |

## 3. 세부 업무 분할 (WBS)

### 단계 1: 화면 구조 및 사용자 인터랙션 설계 (UI/UX)
* **작업 1.1**: 입력 폼 규격 명세
  * 한 줄 텍스트 제목 입력창, 여러 줄 텍스트 메모 입력창, 날짜 및 시간 선택기(피커), 등록 버튼 배치
* **작업 1.2**: 목록 분리 레이아웃 명세
  * '할 일(진행 중)' 구역과 '완료한 일' 구역의 시각적 분리 배치
  * 항목별 제목, 마감일시, 메모 표시 영역 및 고유 순번 순서 정렬 표시 정의
* **작업 1.3**: 제어 인터랙션 명세
  * 완료 및 완료 취소 전환 버튼
  * 인라인 또는 모달 방식의 정보 수정 인터페이스
  * 삭제 클릭 시 브라우저 표준 확인창(\"정말 삭제할까요?\") 호출 및 확인/취소 분기 정의

### 단계 2: 입력값 검증 및 일관성 정책 수립 (Validation Policy)
* **작업 2.1**: 필수값 및 마감일시 유효성 검사 규칙 수립
  * 제목: 앞뒤 공백 제거 후 1자 이상 필수 (공백 문자만 있는 입력 거부)
  * 추가 메모: 선택 입력 (공백 허용)
  * 마감일시: 필수 입력. 시간대 없는 정규 문자열(`YYYY-MM-DDTHH:mm`) 형식 강제
  * 날짜/시간 검증: 지원 연도 `0001`~`9999`, 윤년이 반영된 달력상 실존 날짜, 시(`00`~`23`), 분(`00`~`59`). 값이 누락되거나 불가능한 날짜(예: 2월 30일)는 거부
  * 검증 실패 시: 데이터 및 화면 무변경 유지, 오류 안내 노출, 기존 작성 중이던 입력값 완전 보존
* **작업 2.2**: 마감일시 처리 단순화 원칙 적용
  * 과거 일시 입력 완전 허용. 현재 시각과의 비교, 기한 경과 표시, 시스템 알림, 마감일순 정렬 배제
* **작업 2.3**: 안전한 텍스트 렌더링 규격 정의
  * `<script>`, `<div>` 등 HTML 태그 문자가 입력되어도 코드로 해석되지 않고 순수 텍스트(Text Content)로 화면에 출력

### 단계 3: 데이터 모델 및 영속성 트랜잭션 설계 (Data Model & Storage)
* **작업 3.1**: 데이터 봉투(Envelope) 및 정렬 모델 정의
  * 최상위 봉투 구조: `{ schemaVersion: 1, nextSequence: number, items: TodoItem[] }`
  * 정렬 기준: 오직 영속 `sequenceNumber` 오름차순(ASC) 단일 기준 적용 (시계 역행, 수정, 완료 취소에도 순번 불변)
* **작업 3.2**: 원자적 단일 커밋 경계 설계
  * 후보 객체 생성 → 검증 → JSON 직렬화 → `localStorage.setItem(KEY, jsonString)` 호출
  * `setItem` 반환 성공을 유일한 '커밋(Commit)' 경계로 규정
  * `setItem` 호출 전/호출 실패 시: 기존 저장소 및 화면 상태 100% 유지, 사용자 입력 보존
  * `setItem` 성공 후 화면 렌더링 실패 시: 저장은 완료되었으나 화면 갱신에 실패했음을 안내하고 새로고침 복원 유도
* **작업 3.3**: 초기 로딩 및 손상 데이터 차단 정책 설계
  * `localStorage.getItem(KEY) === null`인 경우에만 정상 빈 목록 초기화
  * 빈 문자열(`""`), 파싱 불가, 스키마 불일치, 접근 권한 예외 시: 자동 초기화나 덮어쓰기를 전면 차단하고 '읽기 전용 경고' 상태로 전환하여 신규 등록/수정/삭제/상태전환 차단
* **작업 3.4**: 단일 탭 순차 편집 및 운영 환경 제약 명세
  * 단일 탭 환경의 순차 조작 지원 명시. 동일 origin 고정 주소 기준 안내 및 다중 탭 동시성 락 미보장 한계 명시

### 단계 4: 작업 지시서 작성 및 검토 (Handover)
* **작업 4.1**: 컴포넌트별 상태 전이 규격서 작성
* **작업 4.2**: 브라우저 로컬 저장소 스키마 및 직렬화 지침서 완성

## 4. 관찰 및 검증 가능한 수락 기준 (Acceptance Criteria)

| ID | 요구사항 추적 | 검증 절차 및 관찰 가능한 기대 결과 |
| :--- | :--- | :--- |
| **AC-01** | 입력 검증 및 중복 등록 (REQ-01) | 1. 제목을 공백만 입력하거나 마감일시를 비워두고 '추가' 클릭 시 등록이 거부되고 작성 중이던 입력 내용이 그대로 보존된다.<br>2. 존재하지 않는 날짜(예: `2026-02-31T10:00`) 입력 시 등록이 거부되고 기존 데이터는 변경되지 않는다.<br>3. 과거 마감일시(예: `2020-01-01T09:00`)를 입력해도 오류나 경고 없이 정상 등록되며, 입력한 일시가 그대로 표시된다.<br>4. 제목 `장보기`, 메모 `사과`, 마감일시 `2026-11-10T15:00` 등록 후 동일한 내용으로 한 번 더 등록 시, 각각 서로 다른 고유 ID와 고유 순번을 가진 독립된 2건이 '할 일' 목록에 나타난다. |

## 5. 기술 사양 및 설계 제안 (Technical Specifications & Proposals)

> **기술 용어 안내**:
> * **로컬 저장소(LocalStorage)**: 사용자의 웹 브라우저가 컴퓨터 내부에 제공하는 문자열 데이터 보관소입니다.
> * **봉투 구조(Envelope)**: 데이터 목록뿐만 아니라 버전 정보, 다음 일련번호 등 관리 정보를 하나의 큰 상자처럼 묶어서 보관하는 형식입니다.
> * **커밋 경계(Commit Boundary)**: 작업이 '공식적으로 저장 완료'되었다고 확정하는 정확한 분기점입니다.
> * **단조 증가(Monotonic Increase)**: 숫자가 중간에 줄어들거나 되돌아가지 않고 항상 이전보다 큰 값으로만 계속 늘어나는 성질입니다.

### 5.1 데이터 모델 및 정렬 불변성 설계 제안
* **저장소 봉투 규격 (Storage Envelope)**:
  브라우저 저장소의 단일 고정 키(`todo_app_data_v1`)에 아래 구조를 단일 JSON 문자열로 직렬화하여 저장합니다.
  ```json
  {
    "schemaVersion": 1,
    "nextSequence": 3,
    "items": [
      {
        "id": "todo-20261108-000001-a1b2",
        "title": "장보기",
        "memo": "사과 3개",
        "dueDateTime": "2026-11-10T15:00",
        "isCompleted": false,
        "sequenceNumber": 1
      },
      {
        "id": "todo-20261108-000002-c3d4",
        "title": "장보기",
        "memo": "우유 1팩",
        "dueDateTime": "2026-11-10T15:00",
        "isCompleted": true,
        "sequenceNumber": 2
      }
    ]
  }
  ```
* **필드 제약 및 불변식 (Invariants)**:
  * `schemaVersion`: 정수 `1` 고정.
  * `nextSequence`: 신규 등록 시 부여할 다음 정수 번호. `1`부터 시작하며, 항상 `nextSequence > max(items.sequenceNumber)`를 만족해야 함. 안전한 정수 범위(`Number.isSafeInteger`) 내에서만 증가하며 한도 초과 시 변경 거부.
  * `id`: 고유 문자열. 항목 간 중복 불가.
  * `sequenceNumber`: 항목 생성 성공 시 `nextSequence` 값을 배정받는 영속 양의 정수. 수정, 완료, 완료 취소, 삭제 등 어떤 작업으로도 기존 항목의 `sequenceNumber`는 변경되지 않음.
* **정렬 단일 기준**:
  * 목록 정렬은 컴퓨터 시계(`createdAt`)를 일체 참조하지 않고, 오직 `sequenceNumber` 오름차순(ASC)만을 유일한 기준으로 적용합니다.
  * PC 시계를 과거로 되돌린 후 새 항목을 등록하더라도 새 항목은 이전 최대 순번보다 큰 순번을 부여받으므로 목록의 가장 뒤에 안정적으로 위치합니다.

### 5.2 마감일시 형식 및 검증 사양 제안
* **단일 정규 포맷**: `YYYY-MM-DDTHH:mm` (시간대 오프셋 없는 순수 달력 날짜 및 시·분).
* **유효성 규칙**:
  * 지원 연도 범위: `0001` ~ `9999` (4자리 연도).
  * 달력 유효성: 윤년을 포함하여 해당 월에 실제로 존재하는 날짜(예: 평년 2월 28일, 윤년 2월 29일, 4월 30일 등)만 허용 (2월 30일, 13월 등 거부).
  * 시간 유효성: 시 `00`~`23`, 분 `00`~`59`.
  * 빈 값, 불완전 입력, 유효하지 않은 일시는 저장 시도 전 단계에서 즉시 거부.
* **시간대 및 비교 제약**:
  * 타임존(UTC) 변환을 수행하지 않으며, 사용자가 입력한 숫자 그대로 저장하고 표시합니다.
  * 화면 표시 포맷을 다르게 하더라도 숫자의 의미(`2026년 11월 10일 15시 00분`)는 왜곡 없이 유지합니다.
  * 현재 시각과의 대소 비교, 기한 경과 안내, 마감일 임박 알림 등은 시스템에 포함하지 않습니다.

### 5.3 로컬 저장소 원자적 커밋 경계 및 손상 데이터 격리
* **단일 원자적 저장 경계**:
  1. 사용자 입력 접수 및 유효성 검증.
  2. 메모리 상에서 신규 봉투 객체(`nextSequence`, `items`) 생성 및 불변식 검증.
  3. `JSON.stringify` 직렬화.
  4. `localStorage.setItem(KEY, serializedString)` 실행.
  * **커밋 성공 판정**: `setItem`이 예외 없이 정상 반환된 시점을 공식 저장 성공(Commit)으로 정의합니다.
  * **저장 실패 시**: `setItem` 호출 전 또는 호출 중 예외(저장 공간 부족 `QuotaExceededError`, 접근 차단 등)가 발생하면, 화면 상태는 변경되지 않고 이전 상태를 유지하며 사용자의 입력 내용은 폼에 안전하게 보존됩니다.
  * **저장 후 렌더링 실패 시**: `setItem`은 성공했으나 화면 갱신 중 오류가 발생한 경우, 저장을 취소한 것으로 간주하지 않고 \"저장은 정상 완료되었으나 화면 표시에 실패했습니다. 페이지를 새로고침하세요.\"라고 안내합니다.
* **초기 로딩 및 데이터 손상 방지 규칙**:
  * **정상 초기 상태**: `localStorage.getItem(KEY) === null` (키 자체가 존재하지 않음)인 경우에만 유효한 빈 목록(`{ schemaVersion: 1, nextSequence: 1, items: [] }`)으로 판단하여 정상 시작합니다.
  * **손상 데이터 상태**:
    * 키는 존재하나 값이 빈 문자열(`""`)인 경우
    * JSON 파싱 오류가 발생하는 경우
    * 파싱 결과가 `null`이거나 객체가 아닌 경우
    * `schemaVersion`이 지원 버전(`1`)이 아니거나 `items`가 배열이 아닌 경우
    * 필수 필드 누락, 필드 타입 불일치, 제목 공백, 유효하지 않은 마감일시 형식
    * `id` 중복, `sequenceNumber` 중복 또는 `nextSequence <= max(items.sequenceNumber)` 위반인 경우
    * 저장소 읽기 시도 중 보안 권한 예외가 발생한 경우
  * **격리 정책**: 손상 데이터 감지 시 임의로 보정하거나 빈 배열로 덮어쓰지(초기화) 않습니다. 화면에 데이터 손상 경고를 표시하고, 추가적인 등록/수정/완료/취소/삭제 쓰기 동작을 완전히 차단하여 기존 원본을 보존합니다. (별도의 백업/복원 도구는 범위에 추가하지 않음)

### 5.4 브라우저 저장소 보관 범위 및 한계 안내
* **복원 보장 환경**:
  * 동일한 컴퓨터, 동일한 웹 브라우저 프로그램, 동일한 브라우저 사용자 프로필, 일반 창(시크릿 모드 제외) 환경에서 **동일한 고정 주소(동일 Origin: 프로토콜 + 도메인 + 포트)**로 접속할 때 데이터가 영속 복원됩니다.
* **보장되지 않는 한계**:
  * 브라우저 설정에서 단순 '캐시된 이미지 및 파일 삭제'가 아닌 **'쿠키 및 기타 사이트 데이터 삭제'** 또는 **'이 사이트의 저장된 데이터 삭제'**를 실행하면 저장 데이터가 완전히 삭제될 수 있습니다.
  * 브라우저 시크릿 창(비공개 브라우징)에서 실행한 경우 창을 닫으면 데이터가 브라우저 정책상 자동 소멸합니다.
  * 서로 다른 브라우저 간(예: 크롬 ↔ 엣지), 서로 다른 기기 간에는 데이터가 공유되거나 동기화되지 않습니다.
  * `file://` 경로를 통해 브라우저로 HTML 파일을 직접 더블 클릭하여 여는 방식은 브라우저 보안 정책에 따라 로컬 저장소 동작 및 영속성이 상이하므로 보장 대상에서 제외합니다. (향후 개발 시 로컬 고정 웹 주소를 제공하는 방식을 작업 지시서에 명시)
  * 갑작스러운 컴퓨터 전원 차단, 물리적 저장 장치 고장으로 인한 브라우저 파일 파손 시 무손실 복구는 보장하지 않습니다.

### 5.5 다중 탭 운용 범위 및 동시성 한계
* **지원 운용 기준**: 본 기획은 **'동일 브라우저 내 단일 탭에서의 순차적 편집'**만을 공식 지원 범위로 한정합니다.
* **다중 탭 동시성 한계**:
  * 외부 탭에서 데이터가 변경되었을 때 브라우저의 `storage` 이벤트를 감지하여 화면에 \"다른 탭에서 내용이 변경되었습니다. 변경 내용을 반영하려면 새로고침하세요.\"라는 안내를 띄우고 추가 편집 동작을 차단하도록 설계할 수 있습니다.
  * 그러나 브라우저 이벤트 전달 지연이나 찰나의 동시 쓰기 상황에서 완벽한 데이터 덮어쓰기 방지, 트랜잭션 락, 실시간 상호 동기화는 기술적으로 보장하지 않으며, 이를 위한 복잡한 잠금 시스템은 본 기획 범위에 포함하지 않습니다.

## 6. 미확정 결정 사항 및 승인 대기 항목 (Unknowns & Pending Decisions)

사용자의 명시적 확정 답변을 거친 항목과 기획자가 최종 승인을 위해 제안하는 항목을 아래와 같이 명확히 분리합니다.

* **사용자 확정 선택 사항 (Settled Decisions)**:
  1. 제목 및 마감일시는 필수 입력, 추가 메모는 선택 입력.
  2. 마감일시는 '날짜와 시간'을 모두 포함하여 기록 및 표시.
  3. 삭제 시 \"정말 삭제할까요?\" 확인창 호출 및 취소 시 무변경 유지.
  4. 과거 마감일시도 오류 없이 등록을 허용하며, 단순 기록 및 표시로 한정.
* **최종 승인 대기 설계 제안 사항 (Proposals Pending Approval)**:
  1. **저장소 Envelope 및 단일 키 명칭 제안**: `{ schemaVersion: 1, nextSequence, items }` 구조와 고정 키 `todo_app_data_v1` 채택 여부.
  2. **마감일시 정규 표기 제안**: 타임존 없는 `YYYY-MM-DDTHH:mm` 단일 표준 표기 사용 여부.
