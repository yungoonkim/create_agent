## [개정 요약 (Revision Summary)]

사용자의 v1/v2 후속 검토 요청(`settledDecisions`)을 반영하여 승인된 범위(`scope-v4`) 내에서 아래 핵심 항목들을 구체화 및 정밀화하였습니다:

1. **저장 JSON 루트 구조 확정 및 전체 목록 중복 lotId 검증 명시**:
   - 저장소 루트 구조를 단일 표준(버전 메타데이터 및 `lots` 배열을 포함하는 단일 루트 객체 규격)으로 명확히 확정.
   - 개별 필드 검증뿐 아니라 역직렬화된 전체 목록에서 `lotId`의 중복 여부를 엄격히 검증하여 중복 발견 시 즉시 로드를 거부하고 원본을 보존하도록 규정.
2. **원자적 저장의 보장 범위 한계 및 플랫폼 이식성 명시**:
   - 동일 파일시스템 내 `rename`은 부분 쓰기(partial write)된 JSON 노출을 방지하기 위한 기법이며, 전원 장애(power cut) 시 디스크 영구 반영까지 완전히 보장하는 것은 아님을 명시.
   - 임시 파일 `fsync`만으로는 부모 디렉터리 메타데이터 변경이 보장되지 않으며, 플랫폼별(POSIX 디렉터리 fsync 가능 여부 vs Windows 디렉터리 동기화 제약) 이식성 한계를 설명.
3. **실패 경계(Failure Boundaries) 구분 및 저장 불확실성 처리**:
   - `rename` 이전 실패(쓰기/fsync/교체 실패)와 `rename` 성공 이후 디렉터리 동기화 실패 단계를 명확히 분리.
   - `rename` 성공 후 디렉터리 동기화 실패 시 새 본파일이 이미 파일시스템에 보일 수 있으므로 "오류면 항상 원본 파일 불변"이라고 무조건 단정하지 않고, '저장 결과 불확실(Uncertain Storage Result)' 오류로 격리 보고하며 임의 되돌리기·초기화·재덮어쓰기를 일절 금지.
4. **임시 파일 정리(Cleanup)의 한계와 고아 파일 처리 규칙**:
   - catch 가능한 런타임 오류 시 임시 파일 삭제는 최선 노력(best-effort)이며 cleanup 자체 실패 시 원래 원인 오류를 보존하고 cleanup 실패를 별도 부가 보고.
   - `SIGKILL`이나 전원 단절 시 Node.js `finally` 블록 실행이 불가능함을 명시하고, 비정상 종료 후 잔류한 임시 파일(`.tmp`)을 다음 실행 시 절대 본파일로 자동 승격하지 않고 무시/격리하도록 규정.
5. **실제 무손실 미증명 선언 및 경계별 관찰 가능한 검사 항목 구체화**:
   - 실제 물리 전원 단절 시험을 수행하지 않은 상태에서 "전원 장애 시 무손실 증명"과 같은 허위 주장을 금지하고, 소프트웨어 레벨의 오류 주입 및 결함 경계별 관찰 가능 검사 사례 수립.

## 1. 범위 요약 및 경계

### 1.1 승인된 필수 기능 (In-Scope)
- **REQ-01 (신규 lot 등록)**: 고유 `lotId`, 상품명, 수량, 표시용 단위, 유통기한(`YYYY-MM-DD`) 등록. 중복 `lotId` 및 빈 문자열 거부, 수량은 0 이상의 안전한 정수 보장.
- **REQ-02 (수량 증감)**: 특정 `lotId`의 수량을 정수(양수/음수/0)로 증감. 결과 수량이 음수이거나 안전 정수 범위를 벗어날 경우 오류 반환 및 기존 데이터 보존. 증감량 0 입력 시 기존 수량 유지.
- **REQ-03 (전체 재고 조회)**: 등록된 전체 lot 목록 표시 (`lotId`, 상품명, 수량, 단위, 유통기한). 수량이 0인 lot도 목록에 유지.
- **REQ-04 (만료/임박 조회)**: 입력받은 기준일(`YYYY-MM-DD`, Asia/Seoul 달력 기준) 및 정수 `N`(0 이상의 안전 정수)을 기준으로 분류.
  - 만료 목록: `유통기한 < 기준일`
  - 임박 목록: `기준일 <= 유통기한 <= 기준일 + N일`
  - 수량이 0인 lot은 조회에서 제외.
  - 정렬: 유통기한 오름차순, 동일 날짜는 `lotId` 오름차순.
  - 기준일 + N 계산 결과가 지원 날짜 범위를 초과할 경우 거부.
- **REQ-05 (로컬 영속화 및 원자적 쓰기)**: 단일 UTF-8 JSON 파일에 저장. 임시 파일 작성 및 동기화 후 원자적 교체(`atomic rename`) 방식으로 저장 실패 시 데이터 오손 방지. 파일 손상/스키마 불일치/읽기/쓰기 오류 시 명확한 한국어 보고와 기존 파일 임의 초기화/덮어쓰기 금지.

### 1.2 명시적 제외 범위 (Out-of-Scope)

## 2. 데이터 저장소 규격 (Storage Schema Specification)

저장소 루트 구조의 다의성을 제거하기 위해 단일 JSON 객체 스키마로 표준을 확정합니다.

### 2.1 JSON 파일 루트 스키마
```json
{
  "version": 1,
  "lots": [
    {
      "lotId": "LOT-20261108-01",
      "productName": "신선우유 1L",
      "quantity": 10,
      "unit": "개",
      "expirationDate": "2026-11-20"
    }
  ]
}
```

### 2.2 엄격한 로드 검증 규칙
1. **루트 구조 검증**: 루트가 null이 아닌 JSON 객체여야 하며, `version` 필드가 정수 1인지, `lots` 필드가 배열인지 확인. 미확인 최상위 필드가 존재하거나 구조가 불일치하면 거부.
2. **요소 레코드 검증**: 각 배열 항목은 객체여야 하며, 필수 5개 필드(`lotId`, `productName`, `quantity`, `unit`, `expirationDate`)가 엄격한 타입 및 도메인 규칙을 만족해야 함. 알 수 없는 필드 포함 시 거부.
3. **전체 목록 중복 lotId 검증**: 파싱된 `lots` 배열 전체를 스캔하여 동일한 `lotId`를 가진 레코드가 2개 이상 존재할 경우 즉시 데이터 오손 오류로 판단하고 로드를 거부.
4. **원본 보존 원칙**: 구문 오류, 스키마 불일치, 중복 `lotId` 발견 시 파일을 임의로 초기화하거나 빈 배열로 저장하지 않고 실행을 중단.

## 3. 원자적 저장 메커니즘과 실패 경계 (Storage Architecture & Failure Boundaries)

### 3.1 파일 저장 생명주기 및 단계별 보장 범위
저장 작업은 동일 파일시스템 디렉터리 내에서 아래 순서로 진행됩니다:

```
[1. 임시 파일 생성] -> [2. 데이터 쓰기 및 fsync] -> [3. 원자적 rename] -> [4. 디렉터리 fsync]
     (Step A)                (Step B)                 (Step C)              (Step D)
```

- **임시 파일 생성 및 쓰기 (Step A ~ B)**:
  - 본파일과 동일 디렉터리에 `[본파일이름].[pid].[timestamp].tmp` 생성 (`EXDEV` 교차 마운트 오류 방지).
  - 임시 파일에 직렬화된 JSON 데이터를 기록하고 파일 디스크립터에 대해 `fsync` 호출.
  - **보장 한계**: 임시 파일 `fsync`는 해당 파일 내용이 디스크에 내려쓰였음을 의미할 뿐, 디렉터리 엔트리나 `rename` 후 메타데이터의 영구 보존까지 보장하지 않음.
- **원자적 파일 교체 (Step C)**:
  - `fs.rename`을 호출하여 임시 파일을 본파일 이름으로 원자적 교체.
  - **보장 범위**: 동일 파일시스템에서 `rename`은 POSIX 원자적 시스템 콜을 사용하여 부분적으로 쓰인(partial write) 불완전한 JSON 파일이 본파일로 노출되는 것을 방지함.
  - **보장 한계**: 모든 OS 및 파일시스템 환경에서 전원 단절(crash/power loss) 후 영구 보존을 완전 보장하는 것은 아님.
- **부모 디렉터리 동기화 (Step D)**:
  - POSIX 호환 환경에서는 부모 디렉터리 fd를 열어 `fsync`를 시도하여 디렉터리 엔트리 변경을 플러시.
  - **이식성 한계**: Windows(Node.js의 `fs.open` 디렉터리 미지원 등)나 특정 파일시스템 환경에서는 디렉터리 fsync가 지원되지 않거나 무시될 수 있음.

### 3.2 실패 경계별 동작 및 오류 처리 원칙

| 구분 | 발생 시점 | 본파일 상태 | 시스템 동작 및 오류 보고 |
| :--- | :--- | :--- | :--- |
| **경계 1: Rename 이전 실패** | Step A~B 쓰기 에러, 디스크 풀, 쓰기 권한 부족, 임시 파일 fsync 실패 | **기존 원본 파일 100% 보존 유지** | 임시 파일 삭제(cleanup)를 최선 노력으로 시도하고, 원본 오류를 보고. |
| **경계 2: Rename 시점 실패** | Step C `rename` 실패 (`EACCES`, `EBUSY`, `EPERM` 등) | **기존 원본 파일 보존** (교체 미발생) | 임시 파일 삭제를 최선 노력으로 시도하고, 교체 실패 오류 보고. |
| **경계 3: Rename 성공 후 디렉터리 동기화 실패** | Step D 부모 디렉터리 fsync 실패 | **새 본파일이 이미 존재할 수 있음** | **'원본 불변'이라고 단정하여 약속하지 않음.** 저장 결과의 불확실성(새 파일이 반영되었으나 영구 동기화 실패 가능성)을 한국어 오류로 명확히 보고. 원본 되돌리기나 강제 덮어쓰기 금지. |

### 3.3 비정상 중단, 임시 파일 잔류 및 최선 노력(Best-effort) Cleanup
1. **Cleanup 자체 실패 처리**:
   - `catch` 블록에서 임시 파일 삭제(`fs.unlink`)를 시도하되, 삭제 과정 자체에서 오류(권한, 파일 잠금 등)가 발생할 수 있음.
   - 이때 본래의 저장 실패 원인(Primary Error)을 덮어쓰지 않고 보존하며, Cleanup 실패 사실을 부가 정보(Suppressed/Secondary Error)로 함께 기록/보고.
2. **비정상 종료(`SIGKILL`, 전원 차단) 한계 명시**:
   - 운영체제 강제 종료 신호(`SIGKILL`)나 물리적 전원 단절 시에는 Node.js 런타임의 `finally` 및 이벤트 핸들러가 실행되지 않으므로 고아 임시 파일(`.tmp`)이 디스크에 잔류할 수 있음.
3. **다음 프로세스 기동 시 격리 규칙**:
   - CLI 도구 재실행 시 디렉터리에 잔류한 `.tmp` 임시 파일을 **절대로 본파일로 자동 승격하거나 병합하지 않음**.
   - 기동 시에는 오직 표준 본파일 경로만 엄격하게 검증하여 로드함 (임시 파일은 무시).

## 4. 단계별 구현 순서 (Implementation Sequence)

```
[단계 1: 입력 표기법 분리 검증 및 정수/날짜 파서]
       │
       ▼
[단계 2: JSON 스키마 검증 및 원자적 영속화 엔진 (경계 분리)]
       │
       ▼
[단계 3: 핵심 도메인 재고 관리 서비스]
       │
       ▼
[단계 4: CLI 서브커맨드 핸들러 및 한국어 인터페이스]
       │
       ▼
[단계 5: 결함 주입 및 시나리오별 관찰 가능성 검증]
```

### 단계 1: 입력 표기법 분리 검증 및 정수/날짜 파서
1. **문자열 표기 정규식 검증**:
   - 수량 및 N: `^(0|[1-9]\d*)$` 정규식으로 지수 표기(`1e3`), 소수점(`.`), 부호(`+`), 공백, 16진수 차단.
   - 증감량: `^(0|-?[1-9]\d*)$` 준수 확인.
2. **도메인 안전 정수 검증**:
   - 파싱 후 `Number.isSafeInteger(val)` 및 `0 <= quantity <= Number.MAX_SAFE_INTEGER` 검증.
3. **Asia/Seoul 달력 날짜 검증**:
   - 시스템 시각 호출 금지. 입력받은 `YYYY-MM-DD`의 연/월/일 유효성(윤년 포함)을 정수 달력 산출식으로 계산.
4. **문자열 필드 검증**:
   - `lotId`, 상품명, 단위의 `trim().length === 0` 거부.

### 단계 2: JSON 스키마 검증 및 원자적 영속화 엔진
1. **엄격한 로더(Strict Loader)**:
   - 파일 부재 시 빈 데이터(`{ version: 1, lots: [] }`) 초기화.
   - 파일 존재 시 UTF-8 읽기 -> JSON 파싱 -> 루트 객체 검증 -> 개별 항목 스키마 검증 -> 전체 `lots` 내 중복 `lotId` 검출.
   - 검증 실패 시 오류 보고 후 즉시 중단(임의 복구/초기화 차단).
2. **단계별 원자적 저장기(Staged Atomic Saver)**:
   - 임시 파일 쓰기 및 `fsync` 구현.
   - `fs.rename` 호출 및 실패 경계 분리.
   - POSIX 디렉터리 `fsync` 구현 및 비지원 환경 예외 격리.
   - 에러 시 최선 노력의 임시 파일 cleanup 및 다중 에러 보존 로직 구현.

### 단계 3: 핵심 도메인 재고 관리 서비스
1. `addLot`: 중복 `lotId` 검사 -> 새 lot 레코드 추가 -> 저장기 호출.
2. `updateQuantity`: `lotId` 조회 -> `수량 + 증감량` 계산 -> 0 이상 및 안전 정수 범위 확인 -> 저장기 호출 (증감량 0은 성공 반환).
3. `listAll`: 전체 lot 반환 (수량 0인 lot 유지).
4. `listExpiring`: 기준일 + N 계산(날짜 오버플로 검증) -> 수량 > 0 필터링 -> 만료(`유통기한 < 기준일`)와 임박(`기준일 <= 유통기한 <= 기준일 + N일`) 분리 -> 유통기한 오름차순, `lotId` 오름차순 정렬.

### 단계 4: CLI 서브커맨드 핸들러 및 한국어 인터페이스
1. 입력 파싱 및 도메인 에러를 명확한 한국어 안내 메시지로 매핑.
2. 조회 결과를 한국어 콘솔 테이블 형태로 포맷팅.

### 단계 5: 결함 주입 및 시나리오별 관찰 가능성 검증
1. 각 실패 경계별 모의 결함 주입(Mocking/Fault Injection) 테스트.
2. 잘못된 데이터 파일 주입 후 불변성 확인.

## 5. 빠뜨리기 쉬운 규칙 및 경계 조건 (Critical Rules)

1. **저장 파일 내 전체 lotId 고유성 보장**:
   - 저장 파일 로드 시 개별 필드가 정상이더라도, 전체 배열 내에 중복된 `lotId`가 존재하면 파일 손상으로 간주하여 즉시 거부.
2. **원자적 저장 실패 시 원본 불변 약속의 한계**:
   - `rename` 이전 실패 시 원본 파일은 완전히 불변임.
   - 그러나 `rename` 성공 직후 디렉터리 동기화 실패 시에는 이미 새 본파일이 디스크에 보일 수 있으므로 "원본이 무조건 불변"이라고 잘못 안내하지 않고, 불확실성 경고와 함께 상태를 보존.
3. **Cleanup 실패 시 원본 에러 보존**:
   - 임시 파일을 지우지 못했더라도 사용자가 직면한 근본 원인(예: 디스크 용량 부족)을 누락하지 않고 1차 원인으로 출력.
4. **수량 0 처리의 비대칭성**:
   - `REQ-03 (전체 재고 조회)`: 수량이 0인 lot 포함.
   - `REQ-04 (만료/임박 조회)`: 수량이 0인 lot 제외.
5. **증감량 0의 취급**:
   - 변경량 `0`은 유효한 정수 연산이며 기존 수량을 유지하고 정상 성공으로 완료.
6. **날짜 계산 오버플로 방지**:
   - `기준일 + N` 계산 시 허용 달력 범위(예: 연도 9999 초과)를 벗어나면 연산을 즉시 거부.

## 7. 확인 가능한 완료 조건 (Acceptance Criteria)

### REQ-01: 신규 lot 등록
- [ ] 유효한 `lotId`, 상품명, 0 이상의 안전 정수 수량, 유효한 단위, `YYYY-MM-DD` 유통기한 입력 시 등록이 성공하고 파일에 반영된다.
- [ ] 수량에 지수 표기(`1e3`), 소수점(`10.0`), 선행 부호(`+5`), 공백이 입력되면 파싱 단계에서 거부된다.
- [ ] 수량 값이 `Number.MAX_SAFE_INTEGER`를 초과하면 거부된다.
- [ ] 중복된 `lotId`, 빈 문자열(`lotId`, 상품명, 단위), 존재하지 않는 달력 날짜(예: `2026-02-29`) 입력 시 등록이 거부된다.

### REQ-02: lotId별 수량 증감
- [ ] 존재하는 `lotId`에 대해 양수/음수 정수 입력 시 정확히 가감된다.
- [ ] 증감량으로 `0`을 입력하면 오류 없이 기존 수량이 그대로 유지되고 성공 처리된다.
- [ ] 차감 결과 수량이 0 미만이 되거나 연산 결과가 안전 정수 범위를 초과하는 경우 변경을 거부하고 기존 수량을 유지한다.
- [ ] 증감량 입력에 비정형 표기(`1.0`, `1e2` 등)나 숫자가 아닌 값이 입력되면 연산을 거부한다.
- [ ] 존재하지 않는 `lotId`에 대한 증감 시도는 오류를 반환하고 데이터를 변경하지 않는다.

### REQ-03: 전체 재고 조회
- [ ] 등록된 전체 lot의 `lotId`, 상품명, 수량, 단위, 유통기한이 한국어로 명확히 표시된다.
- [ ] 수량이 0인 lot도 목록에서 누락되지 않고 온전히 표시된다.

### REQ-04: 유통기한 만료 및 임박 조회
- [ ] 기준일 `2026-05-10`, `N=3` 입력 시:
  - `유통기한 < 2026-05-10`인 lot은 "만료 목록"에 분류된다.
  - `2026-05-10 <= 유통기한 <= 2026-05-13`인 lot은 "임박 목록"에 분류된다.
- [ ] 수량이 0인 lot은 유통기한 조건에 부합하더라도 만료 및 임박 목록에서 반드시 제외된다.
- [ ] 조회 결과는 유통기한 오름차순, 동일한 날짜 내에서는 `lotId` 오름차순으로 정렬된다.
- [ ] N 값에 지수 표기, 음수, 소수점, 안전 정수 범위 초과가 입력되거나, 기준일 + N 계산 결과가 허용 날짜 범위를 벗어날 경우 조회를 거부한다.

### REQ-05: 영속화, 스키마 무결성 및 실패 경계 검증
- [ ] CLI 재실행 시 기존에 등록/수정된 데이터가 온전히 유지된다.
- [ ] 저장 파일은 `{ "version": 1, "lots": [...] }` 구조를 따르며, 루트 구조 불일치나 알 수 없는 필드 존재 시 즉시 로드를 거부하고 기존 파일을 초기화하지 않는다.
- [ ] 파일 로드 시 전체 `lots` 내에 중복된 `lotId`가 존재하면 로드를 거부하고 기존 파일을 보존한다.
- [ ] **[실패 경계 1 검증]** 임시 파일 쓰기/fsync 도중 실패 시, 원본 본파일은 100% 온전하게 유지되고 임시 파일 삭제를 시도하며 원본 오류를 보고한다.
- [ ] **[실패 경계 2 검증]** 임시 파일 cleanup 자체가 실패하는 환경을 시뮬레이션할 경우, cleanup 실패 메시지가 기본 쓰기 오류 메시지를 덮어쓰지 않고 함께 보존·보고된다.
- [ ] **[실패 경계 3 검증]** `rename` 성공 후 부모 디렉터리 동기화 실패 시, "원본 불변"으로 단정하지 않고 저장 결과 불확실성을 오류로 보고하며 원본 파일을 임의로 되돌리거나 초기화하지 않는다.
- [ ] **[비정상 종료 잔류 파일 격리]** 비정상 종료로 인해 잔류한 고아 `.tmp` 파일이 존재하더라도, 다음 CLI 실행 시 이를 본파일로 자동 승격하지 않고 무시하며 오직 본파일만 검증 로드한다.
- [ ] *(전원 차단 시험 실행 선언 배제)* 본 계획은 소프트웨어 결함 주입 검사만 명시하며, 실제 물리적 전원 단절 시험을 수행하지 않은 상태에서 무손실이 증명되었다고 단정하지 않는다.

  - 점주 1인 로컬 실행 환경 기준의 상대 경로(`data/inventory.json`) 또는 환경변수 오버라이드 지원 여부는 작업 지시서 작성 시 명시.
