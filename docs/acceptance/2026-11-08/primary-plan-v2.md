- **프로젝트 ID**: `supervisor-gemini-acceptance`
- **기획안 버전**: v2 (Draft)
- **기반 승인 범위**: `scope-v4` (변경 없음)
- **목표**: 작은 매장의 점주 1인이 로컬 단일 환경에서 로트(lot) 단위로 재고 및 유통기한을 안전하게 기록·조회할 수 있는 Node.js CLI 도구의 상세 구현 계획 수립

## [개정 요약 (Revision Summary)]

사용자의 수정 요청사항(`settledDecisions`)을 반영하여 승인된 범위(`scope-v4`) 내에서 아래 3가지 항목을 구체화 및 보강하였습니다:

1. **숫자 입력 표기와 안전 정수 검증 분리**:
   - CLI 인자 파싱 단계의 표기법 검증(공백, 지수 표기법 `1e3`, 선행/후행 문자, 16진수 등 비표준 형태 거부)과 변환 후 도메인 레벨의 안전 정수(`Number.isSafeInteger`, `0 <= quantity <= Number.MAX_SAFE_INTEGER`) 검증 단계를 분리하여 명시.
2. **저장된 JSON의 필드 및 값 유효성 검증 명시**:
   - 단순히 JSON 구문 오류(`SyntaxError`)뿐만 아니라, 파싱 후 데이터 스키마(배열 구조, 각 lot 레코드의 필수 필드 누락 여부, 알 수 없는 필드, 타입 일치 여부, 정수/날짜 유효성)를 엄격히 검증하고, 스키마 불일치 시에도 원본 보존 및 초기화 금지 규칙 명시.
3. **원자적 저장의 보장 범위와 실패 처리 구체화**:
   - 동일 파일시스템 내 임시 파일 생성 -> 쓰기 및 flush -> 원자적 교체(`fs.rename`) 메커니즘을 상세화하고, rename 실패, 디스크 풀, 쓰기 권한 오류 발생 시 임시 파일 정리(cleanup) 및 원본 파일 불변 보장 방침 구체화.

## 1. 범위 요약 및 경계

### 1.1 승인된 필수 기능 (In-Scope)
- **REQ-01 (신규 lot 등록)**: 고유 `lotId`, 상품명, 수량, 표시용 단위, 유통기한(`YYYY-MM-DD`) 등록. 중복 `lotId` 및 빈 문자열 거부, 수량은 0 이상의 안전한 정수 보장.
- **REQ-02 (수량 증감)**: 특정 `lotId`의 수량을 정수(양수/음수/0)로 증감. 결과 수량이 음수이거나 안전 정수 범위를 벗어날 경우 오류 반환 및 기존 데이터 보존. 증감량 0 입력 시 기존 수량 유지.
- **REQ-03 (전체 재고 조회)**: 등록된 전체 lot 목록 표시 (`lotId`, 상품명, 수량, 단위, 유통기한). 수량이 0인 lot도 목록에 유지.
- **REQ-04 (만료/임박 조회)**: 입력받은 기준일(`YYYY-MM-DD`, Asia/Seoul 달력 기준) 및 정수 `N`(0 이상의 안전 정수)을 기준으로 분류.
  - 만료 목록: `유통기한 < 기준일`
  - 임박 목록: `기준일 <= 유통기한 <= 기준일 + N일`
  - 수량이 0인 lot은 조회에서 제외.
  - 정렬: 유통기한 오름차순, 동일 날짜는 `lotId` 오름차순.
  - 기준일 + N 계산 결과가 지원 날짜 범위를 초과할 경우 거부.
- **REQ-05 (로컬 영속화 및 원자적 쓰기)**: 단일 UTF-8 JSON 파일에 저장. 임시 파일 작성 후 원자적 교체(`atomic rename`) 방식으로 저장 실패 시 데이터 오손 방지. 파일 손상/스키마 불일치/읽기/쓰기 오류 시 명확한 한국어 보고와 기존 파일 임의 초기화/덮어쓰기 금지.

### 1.2 명시적 제외 범위 (Out-of-Scope)
- FEFO(선입선출) 자동 출고 및 자동 차감 (`EXC-01`)
- 별도 폐기 처리 workflow, 폐기 사유 기록, 감사 이력 보존, 별도 상태 필드 (`EXC-02`)
- 실사 보정 workflow, 별도 lot 삭제/수정 기능, 텍스트 검색 기능 (`EXC-03`)
- 바코드/QR 스캐너, 카메라, 외부 POS/엑셀 연동 (`EXC-04`)
- SMS, 카카오 알림톡, 이메일, 모바일 푸시 등 외부 알림 (`EXC-05`)
- 사용자 로그인, 계정/권한 분리, 다중 사용자 및 동시 write 처리 (`EXC-06`)
- 웹/모바일 UI, 클라우드 저장소, 다중 기기 동기화, 배포 파이프라인 (`EXC-07`)
- 결제, 발주/거래처 관리, 매출 통계, 단위 자동 변환 (`EXC-08`)

## 2. 단계별 구현 순서 (Implementation Sequence)

```
[1단계: 파서 및 입력 표기/안전 정수 검증 계층]
       │
       ▼
[2단계: JSON 파일 스키마 검증 및 원자적 영속화 계층]
       │
       ▼
[3단계: 핵심 비즈니스 도메인 서비스]
       │
       ▼
[4단계: CLI 인터페이스 및 한국어 입출력 핸들러]
       │
       ▼
[5단계: 통합 검증 및 시나리오 복원력 점검]
```

### 단계 1: 파서 및 입력 표기/안전 정수 검증 계층
1. **문자열 표기 검증 (String Representation Phase)**:
   - 숫자 인자(수량, 증감량, N)의 원본 문자열에 대해 엄격한 정수 포맷 검증.
   - 정규식 기반 정수 검증: 수량/N은 `^(0|[1-9]\d*)$`, 증감량은 `^(0|-?[1-9]\d*)$` 준수 확인.
   - 소수점(`.`), 지수 표기(`1e3`, `2E+2`), 공백, `NaN`, `Infinity`, 16진수(`0x`) 등 비정형 입력 차단.
2. **도메인 안전 정수 검증 (Domain Safe-Integer Phase)**:
   - 문자열을 숫자로 파싱한 후 `Number.isSafeInteger(val)` 검증.
   - 수량 및 N: `0 <= val <= Number.MAX_SAFE_INTEGER` 확인.
   - 증감량: `Number.MIN_SAFE_INTEGER <= delta <= Number.MAX_SAFE_INTEGER` 확인.
3. **날짜 유효성 검증**:
   - `YYYY-MM-DD` 정규식 포맷 검증 및 윤년/월별 일수 확인(Asia/Seoul 달력 기준).
   - 시스템 시각을 조회하지 않고 문자열 정수 연산만으로 유효 날짜 검증.
4. **필수 문자열 필드 검증**:
   - `lotId`, 상품명, 단위의 공백 제거 후 빈 문자열(`trim().length === 0`) 거부.

### 단계 2: JSON 파일 스키마 검증 및 원자적 영속화 계층 (Storage Engine)
1. **읽기 및 스키마 검증 (Strict Schema Validation)**:
   - 파일 부재 시: 빈 데이터 세트로 정상 초기 구동 (최초 저장 시 파일 생성).
   - 파일 존재 시: UTF-8 텍스트 읽기 -> JSON 구문 분석(`JSON.parse`).
   - 스키마 검증기 실행:
     - 루트가 객체/배열 규격에 부합하는지 확인.
     - 각 항목의 `lotId`(문자열, 공백 아님), `productName`(문자열, 공백 아님), `quantity`(0 이상의 안전 정수), `unit`(문자열, 공백 아님), `expirationDate`(유효한 `YYYY-MM-DD`) 필드 타입 및 값 정밀 검사.
     - 정의되지 않은 미확인 필드 존재 시 또는 누락 필드 존재 시 즉시 로드 실패 처리.
   - 검증 실패 시 원본 파일을 절대로 덮어쓰거나 초기화하지 않고 한국어 오류를 던지며 중단.
2. **원자적 저장 메커니즘 (Atomic Storage)**:
   - 대상 파일과 동일한 디렉터리에 고유 임시 파일(`[targetPath].[pid].[timestamp].tmp`) 생성 (동일 파일시스템 보장).
   - JSON 포맷팅 직렬화 쓰기 후 파일 디스크립터 동기화(flush/fsync 보장).
   - `fs.rename`을 호출하여 원자적 교체 완료.
   - 실패 처리: 쓰기나 교체 중 에러(디스크 공간 부족, 권한 오류 등) 발생 시 임시 파일 즉시 삭제(cleanup), 원본 파일은 그대로 유지.

### 단계 3: 핵심 비즈니스 도메인 서비스 (Inventory Service)
1. `addLot`: `lotId` 중복 검사 -> 도메인 규칙 통과 시 신규 추가 -> 원자적 저장.
2. `updateQuantity`: `lotId` 조회 -> `현재 수량 + 증감량` 계산 -> 결과가 0 이상이고 `Number.MAX_SAFE_INTEGER` 이하인지 검증 -> 변경 반영 후 원자적 저장 (증감량 0은 성공 처리).
3. `listAll`: 전체 lot 반환 (수량 0인 lot 포함).
4. `listExpiring`: 기준일 + N 계산(날짜 범위 오버플로 검증) -> 수량 > 0 필터링 -> 만료(`유통기한 < 기준일`) 및 임박(`기준일 <= 유통기한 <= 기준일 + N일`) 분리 -> 유통기한 오름차순, 동일 시 `lotId` 오름차순 복합 정렬.

### 단계 4: CLI 인터페이스 및 한국어 입출력 핸들러
1. CLI 인자 파서 구현: 각 서브커맨드별 파라미터 매핑.
2. 예외 및 오류 메시지 표준화: 유효성 검증 실패, 스키마 오류, 저장 실패 시 명확한 안내 문구 출력.
3. 조회 결과 목록을 한국어 표준 테이블 형태로 포맷팅하여 콘솔 출력.

### 단계 5: 통합 검증 및 시나리오 복원력 점검
1. REQ-01 ~ REQ-05 전 요구사항에 대한 테스트 케이스 실행.
2. 비정상 입력(지수 표기, 스키마 깨진 JSON, 원자적 저장 중단) 복원력 테스트.

## 3. 빠뜨리기 쉬운 규칙 및 경계 조건 (Critical Rules)

1. **숫자 표기와 안전 정수 검증 분리**:
   - `1e3`, `+100`, `10.0`, `0x10`과 같이 JavaScript `Number()`가 숫자로 파싱하더라도 지수/소수/진법 표기는 문자열 단계에서 정규식으로 엄격히 거부.
   - 정수 표기 통과 후 `Number.isSafeInteger`를 통해 JavaScript의 안전 정수 한계(`9,007,199,254,740,991`)를 초과하지 않는지 확인.
2. **저장된 파일의 스키마 손상 방어**:
   - JSON 구문 오류뿐만 아니라, JSON 구조 내 필드가 누락되었거나(예: `unit` 누락), 수량이 음수/소수로 기록되어 있는 등 데이터 정합성이 깨진 경우 프로그램을 임의로 초기화하지 않고 즉시 로드를 중단하여 원본 보존.
3. **수량 0 처리의 비대칭성**:
   - `전체 재고 조회 (REQ-03)`: 수량이 0인 lot을 **반드시 포함**.
   - `만료/임박 조회 (REQ-04)`: 수량이 0인 lot은 **반드시 제외**.
4. **증감량 0 처리**:
   - 수량 증감 입력이 `0`인 경우 오류가 아니며, 기존 수량을 유지하고 정상 성공으로 처리.
5. **원자적 쓰기의 실패 격리**:
   - 임시 파일은 반드시 대상 파일과 동일한 마운트 경로/디렉터리에 생성하여 교차 디바이스 링크 에러(`EXDEV`)를 방지하고 원자적 `rename` 보장.
   - 저장 실패 시 생성되던 `.tmp` 파일은 즉시 정리(unlink)하여 쓰레기 파일을 남기지 않음.
6. **날짜 계산 및 타임존 독립성**:
   - OS 로컬 시각(`new Date()`)을 참조하지 않으며, 전달받은 `YYYY-MM-DD`를 기준으로 순수 달력 계산 수행.
   - 기준일 + N 계산 시 지원 가능한 날짜 범위(예: 4자리 연도 `9999-12-31` 한계) 초과 여부를 확인하고 초과 시 안전하게 거부.

## 4. 위험 요소 및 대응 방안 (Risks & Mitigations)

| 위험 요소 | 영향 | 대응 방안 |
| :--- | :--- | :--- |
| **파싱 단계에서 부동소수점 변환 왜곡** | 지수 표기나 거대 숫자가 의도치 않게 안전 정수로 둔갑하거나 정밀도 유실 | 문자열 단계에서 엄격한 정수 정규식을 먼저 적용한 후 숫자 변환 및 `Number.isSafeInteger`를 2단계로 검증 |
| **기존 JSON 파일의 데이터 변조/손상** | 프로그램이 손상된 파일을 빈 파일로 덮어써 영구적인 재고 손실 유발 | 파일 로드 시 strict 스키마 검증기를 통과하지 못하면 자동 복구(빈 파일 저장)를 금지하고 읽기 전용 오류 발생 후 종료 |
| **원자적 파일 교체 중 시스템 비정상 중단** | 쓰기 도중 디스크 풀이나 권한 오류로 원본 파일 오손 | 동일 디렉터리 내 `.tmp` 파일 생성 및 쓰기 완료 후 `fs.rename`을 수행하며, 실패 시 `try/finally`로 임시 파일 안전 제거 |
| **OS 런타임 타임존 차이로 인한 날짜 왜곡** | 서버/로컬 타임존에 따라 만료 판정이 하루씩 밀리는 현상 발생 | Node.js 시스템 시각을 배제하고 Asia/Seoul 기준 달력 일수 기반 정수 연산 알고리즘 적용 |

## 5. 확인 가능한 완료 조건 (Acceptance Criteria)

### REQ-01: 신규 lot 등록
- [ ] 유효한 `lotId`, 상품명, 0 이상의 안전 정수 수량, 유효한 단위, `YYYY-MM-DD` 유통기한 입력 시 등록이 성공하고 파일에 영속화된다.
- [ ] 수량 입력에 지수 표기법(`1e5`), 소수점(`10.5`), 부호 표기(`+10`), 공백 등이 포함된 경우 문자열 단계에서 거부된다.
- [ ] 수량 값이 `Number.MAX_SAFE_INTEGER`를 초과하는 경우 안전 정수 검증에서 거부된다.
- [ ] 중복된 `lotId`, 공백/빈 문자열(`lotId`, 상품명, 단위), 존재하지 않는 달력 날짜(예: `2026-02-29`) 입력 시 등록이 거부된다.

### REQ-02: lotId별 수량 증감
- [ ] 존재하는 `lotId`에 대해 양수/음수 정수 입력 시 정확히 가감된다.
- [ ] 증감량으로 `0`을 입력하면 오류 없이 기존 수량이 그대로 유지되고 성공 처리된다.
- [ ] 차감 결과 수량이 0 미만이 되거나 연산 결과가 안전 정수 범위를 초과하는 경우 변경을 거부하고 기존 수량을 유지한다.
- [ ] 증감량 입력에 비정형 표기(`1.0`, `1e2` 등)나 숫자가 아닌 값이 입력되면 연산을 거부한다.
- [ ] 존재하지 않는 `lotId`를 대상으로 증감을 시도하면 에러를 반환하고 데이터를 변경하지 않는다.

### REQ-03: 전체 재고 조회
- [ ] 등록된 전체 lot의 `lotId`, 상품명, 수량, 단위, 유통기한이 한국어로 명확히 표시된다.
- [ ] 수량이 0인 lot도 목록에서 누락되지 않고 전체 목록에 온전히 표시된다.

### REQ-04: 유통기한 만료 및 임박 조회
- [ ] 기준일 `2026-05-10`, `N=3` 입력 시:
  - `유통기한 < 2026-05-10`인 lot은 "만료 목록"에 분류된다.
  - `2026-05-10 <= 유통기한 <= 2026-05-13`인 lot은 "임박 목록"에 분류된다.
- [ ] 수량이 0인 lot은 유통기한 조건에 부합하더라도 만료 및 임박 목록에서 반드시 제외된다.
- [ ] 조회 결과는 유통기한 오름차순, 동일한 날짜 내에서는 `lotId` 오름차순으로 정렬된다.
- [ ] N 값에 지수 표기, 음수, 소수점, 안전 정수 범위 초과가 입력되거나, 기준일 + N 계산 결과가 허용 날짜 범위를 벗어날 경우 조회를 거부한다.

### REQ-05: 영속화 및 무결성
- [ ] CLI 재실행 시 기존에 등록/수정된 데이터가 온전히 유지된다.
- [ ] 저장 파일은 단일 UTF-8 JSON 파일로 관리되며, 저장은 임시 파일 생성 후 `rename` 방식을 따른다.
- [ ] 저장 과정에서 실패(권한 부족, 강제 중단 시뮬레이션 등)가 발생해도 기존 파일이 0바이트가 되거나 손상되지 않고 보존된다.
- [ ] JSON 파일 내 일부 필드가 누락되었거나 타입/값이 잘못된(스키마 불일치) 경우, 빈 파일로 초기화하지 않고 구체적인 검증 오류를 한국어로 출력하며 안전하게 종료한다.

## 6. 미확정/추후 결정 사항 (Explicit Unknown Decisions)

- **CLI 서브커맨드/플래그 명칭 체계**:
  - 커맨드라인 서브커맨드 형태(`lot register`, `lot update` 등) 또는 플래그 형태(`--add`, `--increase` 등)의 세부 CLI 문법은 구현 작업 지시서 작성 시 확정한다.
- **기본 데이터 파일 저장 경로**:
  - 실행 디렉터리 기준 상대 경로(`data/inventory.json`) 또는 환경변수 지정 방식 여부는 점주 1인 로컬 실행 환경 기준에 맞춰 작업 지시서 작성 시 기본값을 명시한다.
