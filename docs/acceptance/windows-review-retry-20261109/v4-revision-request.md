# 기획 v4 수정 요청 — 사용자 수락한 보완

사용자는 기획 v3의 마감일 검증·동시 탭 처리 보완에 동의했고, 진행자가 추천한 ‘동시에 한 탭만 변경 가능, 다른 탭은 변경 차단, 사용 탭 종료 후 다른 탭을 새로고침해 최신 데이터로 사용’ 방식을 수락했다. 이 기록은 수정 지시의 출처이며 아직 작성되지 않은 기획 v4의 최종 승인은 아니다.

승인된 Scope v4와 Q-1~Q-7, 기존 원본 보존·쓰기 차단·커밋 실패 처리·정렬·중복 제목·필수 입력 규칙을 유지한다. 실제 제품 구현·팀원 실행은 하지 않는다.

1. 마감 일시를 등록·수정·저장 데이터 로드·변경 후보 저장 전 같은 규칙으로 검증한다. YYYY-MM-DDTHH:mm 형식과 실제 달력 날짜/시·분의 유효성을 확인하고 자동 날짜 보정으로 잘못된 입력을 허용하지 않는다. 빈 값·아무 글자·2026-02-30T15:00·범위 밖 시/분 등의 거부 사례를 둔다. 잘못된 저장 데이터는 기존 Q-7대로 원본 보존과 변경 차단으로 처리한다.
2. 같은 origin과 브라우저 프로필에서 동시에 한 탭만 변경 권한을 가진다. 저장소를 로드해 변경 가능한 상태로 열기 전에 실제 배타 잠금을 얻고 탭 수명 동안 유지한다. 다른 탭에는 다른 탭 사용 중 안내와 모든 데이터 변경 차단을 적용한다. 사용 탭을 닫으면 다른 탭을 새로고침해 잠금을 얻고 최신 저장값을 다시 검증·로드한 뒤 사용한다.
3. 구체적 보호 방식은 Web Locks API의 배타 잠금처럼 두 탭이 동시에 소유할 수 없는 방법으로 설계한다. 고정 localhost origin 등 사용 조건, 브라우저 지원 여부 확인과 잠금 미지원/획득 실패 시 변경 차단을 명시한다. localStorage의 단순 참/거짓 표시만으로 배타성을 보장한다고 쓰지 않는다. 다른 브라우저·프로필은 저장 영역이 다르다는 경계를 설명한다.
4. 두 탭 동시 열기/추가 시도에서 한 탭만 변경되고 다른 탭의 저장 시도가 없는지, 주 탭 종료 후 새로고침한 탭이 최신 목록을 읽는지, 잠금 미지원 시 쓰지 않는지의 검증 사례를 추가한다. 같은 고정 주소·브라우저 프로필에서 재접속해야 기존 로컬 데이터가 보이는 조건을 명시한다.
5. 기능/검증 본문에 반영하고 변경 요약만으로 해결됐다고 하지 않는다. 사용자 선택으로 수락된 한 탭 정책과 기획자의 잠금 API·기술 설계 제안을 구분해 출처를 기록한다. Reviewer가 위 두 항목과 기존 Q-7 보호 규칙의 회귀를 대조한다.

현재 로컬 상태는 기획 v3/반복3/5/awaiting_approval이다. request-plan-revision으로 이유를 기록한 후 resume-plan으로 다음 기획을 생성하며, 총 반복 한도와 최종 사용자 승인을 유지한다. 초안이 확정되면 승인 기획 기반 작업 제안·지시 품질 확인과 최종 기록을 남기고 제품/팀원 실행 전에 멈춘다.
