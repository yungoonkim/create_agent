## 2. 사용자 여정 및 기능 요구사항

### PARCEL-1: 택배 수령 예정 기록 등록
- **정상 동작**: 사용자는 '내용 이름', '예정 날짜(YYYY-MM-DD)', '메모(선택)'를 입력하여 등록한다. 동일한 내용 이름과 날짜라도 독립적인 새 기록으로 추가되며, 고유 `id`와 순차 증가하는 양의 정수 `seq`가 부여된다. 새 기록의 `received` 상태는 항상 `false`(미수령)로 초기화되고, 목록은 최초 등록 순환(`seq` 오름차순)으로 표시된다. (출처: `settledDecisions` - 단일 사용자 도구, 동일 내용도 별도 기록 허용, 과거/오늘/미래 달력 날짜 모두 허용)
- **입력 검증**:
  - 내용 이름: 앞뒤 공백을 제거한 후 1자 이상의 문자열이어야 함(공백 전용 입력 불가).
  - 예정 날짜: `YYYY-MM-DD` 형식의 실제 존재하는 달력 날짜여야 함(예: `2026-02-28` 허용, `2026-02-30` 불가). 과거·오늘·미래 날짜 모두 유효함.
  - 메모: 문자열(입력하지 않으면 빈 문자열 `""`).
- **실패 및 무변경 동작**: 검증에 실패하면 명확한 오류 안내 메시지를 표시하고, 입력 폼의 입력값, 화면의 기존 기록 목록, 스토리지 저장값을 전혀 변경하지 않는다.
- **인수 확인 사례**:
  1. 내용에 "도서", 날짜에 "2026-11-20"을 입력하여 등록한 뒤, 동일하게 "도서", "2026-11-20"을 다시 등록하면 목록에 미수령 기록 2건이 독립적으로 나열된다.
  2. 내용에 "   "(공백만 입력)을 넣거나 날짜에 "2026-02-30"을 입력하고 등록을 누르면 등록되지 않고 기존 목록과 입력란 내용이 유지된다.

### PARCEL-2: 수령 상태 전환, 수정 및 단건 삭제
- **정상 동작**:
  - **수령 상태 전환**: 목록에서 특정 1건을 선택하여 `received` 값을 `true`(받음) 또는 `false`(미수령)로 즉시 토글 전환한다.
  - **수정**: 특정 1건의 내용 이름, 날짜, 메모를 수정할 수 있다. 수정 시에도 `id`와 `seq`는 절대 변경되지 않는다.
  - **삭제**: 특정 1건 삭제 시 반드시 확인 대화창을 거쳐 단 1건만 영구 제거한다. (출처: `settledDecisions` - 수정/삭제/받음 전환은 선택한 단 1건만 적용)
- **검증 규칙**: 수정 시 적용되는 이름(비공백 필수), 날짜(실제 날짜 필수), 메모 규칙은 PARCEL-1 등록 검증과 완전히 동일하다.
- **실패 및 무변경 동작**:
  - 수정 입력값이 검증을 통과하지 못하면 저장을 거부하고 기존 데이터와 목록을 보존한다.
  - 삭제 확인 대화창에서 '취소'를 선택하면 스토리지 쓰기를 실행하지 않으며 목록을 그대로 유지한다. (출처: `settledDecisions` - 삭제 취소는 쓰지 않음)
- **인수 확인 사례**:
  1. 동일한 이름 "생필품" 2건 중 첫 번째 항목의 수령 버튼을 누르면 해당 1건만 '받음'으로 바뀌고, 두 번째 항목은 '미수령'으로 남는다. 다시 누르면 '미수령'으로 복원된다.
  2. 두 번째 항목의 삭제 버튼을 누르고 확인 창에서 '취소'를 누르면 스토리지 쓰기 없이 2건 모두 화면과 저장소에 유지된다.

### PARCEL-3: 영속성 보존 및 상태 무결성
- **정상 동작**: 브라우저 탭을 닫거나 새로고침한 후 다시 열었을 때(`http://localhost:4173`), 기존에 정상 저장된 항목 목록, 각 항목의 `received` 상태, `seq` 순서가 정확히 복원된다.
- **실패 및 무변경 동작**:
  - `getItem` 자체가 브라우저 보안 정책 등으로 예외(`SecurityError` 등)를 발생시키는 경우, 읽기 실패 안내를 띄우고 빈 값으로 간주하지 않으며, 신규 쓰기 및 데이터 변경을 전면 차단한다.
  - 기존 저장 데이터가 깨진 JSON이거나, 스키마/값 유효성을 위반한 경우 자동 초기화(`clear` 또는 덮어쓰기)나 백업 파일 이동을 하지 않고 원본을 보존하며 변경 기능을 차단한다.
  - 신규 등록·수정·삭제 시 스토리지 쓰기(`setItem`)가 쿼터 초과 등으로 실패하면 현재 입력 폼 내용, 화면 상태, 기존 저장값을 변경 없이 그대로 유지한다.
- **인수 확인 사례**:
  1. 2건을 등록하고 1건을 '받음' 처리한 후 탭을 새로고침하면 2건의 내용과 수령 상태가 그대로 표시된다.
  2. 스토리지 읽기 시 `SecurityError`가 발생하면 "저장소 접근 불가" 안내가 노출되고 등록 버튼이 비활성화되며, 기존 저장소에 쓰기 호출을 하지 않는다.

## 3. 기술 설계 및 데이터 무결성 규격

### 3.1 스토리지 키 및 공통 검증표 (Common Validation)
- **스토리지 키**: 브라우저 `localStorage` 단일 키 `parcel_data` 사용.
- **검증 시점 원칙**: 성공적으로 읽어 들인 저장 데이터(`Load`)와, 쓰기 직전 전체 상태 후보(`Candidate`) 양쪽에 **완전히 동일한 규칙**을 적용한다.

| 대상 필드 | 형식 및 타입 규칙 | 값 유효성 및 컬렉션 불변식 |
| :--- | :--- | :--- |
| `schemaVersion` | 정수(`number`) | 정확히 `1`이어야 함. |
| `nextSeq` | 양의 안전 정수(`number`) | `Number.isSafeInteger(nextSeq) && nextSeq >= 1`, 또한 모든 `items`의 `seq`보다 엄격히 커야 함 (`nextSeq > max(seq)`). |
| `items` | 배열(`Array`) | 0개 이상의 객체 배열. |
| `items[].id` | 문자열(`string`) | 공백이 아닌 고유 식별자(UUID 등), 컬렉션 내 중복 불가. |
| `items[].seq` | 양의 안전 정수(`number`) | `Number.isSafeInteger(seq) && seq >= 1`, 컬렉션 내 중복 불가. |
| `items[].name`| 문자열(`string`) | 앞뒤 공백 제외 1자 이상 (`name.trim().length >= 1`). |
| `items[].date`| 문자열(`string`) | `YYYY-MM-DD` 형태이며 `Date` 파싱 시 연/월/일이 일치하는 실제 달력 날짜. |
| `items[].memo`| 문자열(`string`) | 문자열 타입 필수(`typeof memo === 'string'`). |
| `items[].received`| 불리언(`boolean`) | 반드시 기본형 불리언 `true` 또는 `false` (문자열 `"true"`, 숫자 `1` 등 불허). |

### 3.2 로드 판정 및 저장 데이터 보존 정책
- **정상 최초 실행**: `localStorage.getItem("parcel_data") === null`인 경우에만 최초 실행으로 판정하고 메모리에 빈 목록(`items: []`, `nextSeq: 1`)을 초기화한다. 첫 사용자 조작 발생 전까지는 스토리지에 빈 쓰기를 수행하지 않는다.
- **손상/위반 데이터 처리**: 
  - 읽은 결과가 빈 문자열(`""`), 공백 문자열, 파싱 불가능한 JSON, 스키마 버전 불일치, 또는 공통 검증표의 규칙을 1개라도 위반한 경우(예: 스키마는 유효하나 `date`가 `"2026-02-30"`이거나 `received`가 `"받음"`인 경우).
  - **처리 방식**: 원본 저장 데이터를 절대 덮어쓰거나 삭제하지 않고 보존하며, "저장 데이터 손상" 오류 안내를 표시하고 화면 목록 표시 및 일체의 데이터 변경(추가/수정/삭제)을 전면 차단한다.
- **구체적 위반 사례 검증**:
  - *저장된 값 위반 사례*: `{"schemaVersion":1,"nextSeq":2,"items":[{"id":"p1","seq":1,"name":"책","date":"2026-11-10","memo":"","received":"받음"}]}`가 저장되어 있는 경우 -> `received`가 불리언이 아니므로 로드 거부, 스토리지 원본 보존, 수정/등록 차단.
  - *신규 입력 위반 사례*: 이름에 공백만 입력하거나 날짜를 `2026-11-31`로 입력한 경우 -> 쓰기 후보 생성 전 차단, 스토리지 미호출.

### 3.3 커밋 순서 및 장애 한계
1. **커밋 단계**:
   1. 사용자의 등록/수정/상태전환/삭제 요청 발생.
   2. 변경 후의 전체 상태 객체 후보(Candidate: `{schemaVersion:1, nextSeq, items}`) 생성.
   3. 전체 후보에 대해 3.1 공통 검증표 규칙 검증 수행 (실패 시 중단, 기존 상태 보존).
   4. 후보 객체를 JSON 문자열로 직렬화.
   5. `localStorage.setItem("parcel_data", serialized)` 호출.
   6. 스토리지 저장이 성공한 경우에만 인메모리 상태 및 화면 UI 목록 확정.
2. **UI 렌더링 실패 처리**: 스토리지 쓰기(`setItem`)가 성공한 직후 브라우저 DOM 렌더링 등 UI 단계에서 예외가 발생하면, "저장 취소"로 잘못 안내하지 않고 "저장은 완료되었으나 화면 갱신에 실패했습니다. 페이지를 새로고침하십시오"를 안내한다.
3. **내구성 한계 명시**: 본 도구는 단일 브라우저 로컬 스토리지를 사용하므로 OS 비정상 종료, 기기 전원 차단, 하드웨어 장애까지 영구 보장하지는 않는다.

### 3.4 다중 탭 및 동시성 제어
- 동일 브라우저 프로필 및 고정 오리진(`http://localhost:4173`) 환경에서 Web Locks API(`navigator.locks.request("parcel_data_lock", ...)`)를 사용한다.
- 편집 권한을 가진 탭 수명 동안 배타적 잠금을 유지하며, 잠금을 정상 획득한 시점에 최신 스토리지를 읽어들인다.
- 잠금을 획득하지 못한 다른 탭이나 Web Locks 미지원 환경에서는 편집 및 데이터 변경 기능을 차단하며, 기존 편집 탭이 종료된 후 새로고침하여 사용할 것을 안내한다.

## 4. 범위 외 항목 및 주의 사항 (Exclusions)
- **제외 기능**: 사용자 로그인/인증, 외부 백엔드 서버 연동, 택배 운송장 배송 조회 API 연동, 푸시 알림, 타 사용자와의 목록 공유, 공개 순위 산정 기능은 구현하지 않는다.
- **실행 제한**: 본 계획서는 테스트 스텁(TEST/STUB) 환경의 기획 사양이며, 실제 상용 제품 릴리스, 팀원 작업 할당, 최종 사용자 실승인 행위는 본 단계에서 수행하지 않는다.
