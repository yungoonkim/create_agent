# 주차 위치 기록 도구 기획안 (버전 2)

**문서 상태:** 미승인 초안 (기획 및 검토 단계이며 최종 사용자 승인이나 제품 구현 코드가 아님)  
**대상 프로젝트:** parking-planning-trial

---

## 0. 버전 2 변경 사항 요약 (Revision Summary)

1. **저장소 빈 값(`present_empty`) 명시:** 키는 존재하나 내용이 빈 문자열(`""`) 또는 공백만 있는 경우, 암묵적 빈 배열 리셋 대신 손상 데이터로 판정하여 원본 문자열을 보존하고 쓰기를 차단하도록 처리 규격을 보완함.
2. **동시성 제어 스키마 반영:** 다중 탭 낙관적 락에 사용되는 타임스탬프(`updatedAt`) 필드를 공통 유효성 검증 테이블에 공식 필드로 포함함.
3. **통합 불량 데이터 검증 인수 사례 보완:** 개별 필드(`id`, `memo`, `status`, `createdAt`) 및 고유성 불변식 위반을 포괄 검증하는 통합 로드 차단 사례와 통합 후보 차단 사례를 명시함.
4. **다중 탭 인터리빙 한계 및 직렬화 경계 명시:** 단순 check-then-write나 `storage` 이벤트 감지만으로는 두 탭이 동시에 동일 버전을 읽고 검증을 통과한 뒤 교차 쓰기하는 경합(Interleaving)을 완전 차단할 수 없음을 밝히고, `BroadcastChannel` 기반 분산 락 제안과 미지원 환경 폴백 동작을 기술함.

## 1. 결정 사항 구분

### 1.1 사용자 명시 결정 (출처: approvedScope)
- **단일 현재 기록 규칙:** 현재 주차 중인 기록은 시스템 전체에서 최대 1개만 허용한다. 이미 존재하면 새 기록을 추가하지 않고 사유를 안내한다. (PARK-1, PARK-2, PARK-3)
- **필수 및 선택 항목:** 주차 위치(공백 제외 필수), 주차 시각(필수, 현재 시각 기본값 제공 및 수정 가능), 메모(선택 사항)로 구성한다. (PARK-1)
- **상태 전이 및 복원:** 현재 기록을 '차 찾음'으로 변경하면 이전 기록으로 보관된다. '찾음 취소' 시 현재 기록으로 되돌리되, 이미 다른 현재 기록이 있으면 기존 데이터를 보존하고 충돌을 안내한다. (PARK-2)
- **데이터 보존 및 수정/삭제:** 개별 기록의 위치·시각·메모를 수정하고 확인 후 삭제할 수 있다. 잘못된 수정과 삭제 취소는 저장값을 변경하지 않는다. 브라우저 재방문 시 로컬 컴퓨터에 보존되며, 저장 실패나 데이터 손상 시 임의 초기화나 덮어쓰기를 금지한다. (PARK-3)
- **제외 범위:** 계정 로그인, 서버 동기화, GPS 자동 감지, 지도·주차장 연동, 알림, 타인 공유는 포함하지 않는다. (EX-PARK-1)
- **진행 범위:** 본 문서는 기획안 작성 및 검토까지만 수행하며, 실제 제품 코드 구현, Agent 실행, 자동 승인은 수행하지 않는다. (EX-PARK-2)

### 1.2 위임된 설계 제안 (기획자 제안)
- **저장소 키 및 포맷:** 브라우저 `localStorage`에 키 `parking_records_v1`을 사용하여 메타데이터 객체(`{ "version": 1, "updatedAt": "...", "records": [...] }`)를 JSON 문자열로 직렬화하여 저장한다.
- **고유 식별자(Identity):** 시간 왜곡에 영향받지 않도록 브라우저 `crypto.randomUUID()` 규격의 문자열을 생성하여 `id`로 부여한다.
- **다중 탭 직렬화 경계(Serialization Boundary):** `BroadcastChannel`을 이용한 탭 간 짧은 점유 토큰(뮤텍스 제안) 교환과 저장소 `updatedAt` 타임스탬프 비교를 결합하여 쓰기 트랜잭션을 직렬화한다. 브라우저가 이를 지원하지 않는 환경에서는 최종 쓰기 직전 재검증(Re-read & Check) 후 불일치 시 롤백하는 폴백 방식을 사용한다.

### 1.3 미해결 및 확인 필요 사항
- 현재 승인된 요구사항 범위 내 미해결 모순은 없다. 추후 장기 사용으로 인해 브라우저 로컬 저장 용량(통상 5MB) 한계에 근접할 경우, 이전 기록의 보관 건수 제한 정책(예: 최대 100건 보관 등)에 대한 사용자 정책 결정이 필요할 수 있다.

## 2. 사용자 여정 및 화면 인터랙션 흐름

### 2.1 여정 1: 새로운 주차 기록 등록
1. 사용자가 웹 페이지를 열면 상단에 [주차 위치 등록] 입력 양식이 표시된다.
2. '주차 시각' 입력창에는 현재 컴퓨터 시각(예: 2026-11-10 14:30)이 기본값으로 채워져 있으며, 사용자가 직접 날짜와 시간을 고칠 수 있다.
3. 사용자가 '주차 위치'에 "지하 2층 B-04"를 입력하고, '메모'에 "기둥 옆 전기차 충전소 부근"을 입력한 뒤 [주차 등록] 버튼을 누른다.
4. 시스템은 유효성을 검증하고, 현재 주차 중인 기록이 없는지 확인한 뒤 등록을 완료한다.
5. 화면 상단에 '현재 주차 기록' 카드가 생성되고, 등록 폼은 초기화된다.
6. **차단 흐름:** 이미 '현재 주차 중' 카드가 존재하는 상태에서 다시 등록을 시도하면, 버튼 하단에 "이미 주차 중인 기록이 있습니다. 기존 기록을 '차 찾음' 처리한 후 새로 등록해 주세요."라는 경고를 표시하고 기존 기록과 사용자가 방금 입력한 내용을 지우지 않고 그대로 유지한다.

### 2.2 여정 2: 차 찾기 완료 및 찾음 취소(되돌리기)
1. 주차한 차를 찾은 사용자는 현재 주차 기록 카드의 [차 찾음] 버튼을 누른다.
2. 즉시 해당 기록의 상태가 '찾음(이전 기록)'으로 변경되며, 상단 '현재 주차 기록' 영역은 빈 상태("현재 주차 중인 차량이 없습니다")로 바뀌고, 하단 '이전 주차 기록 목록' 최상단에 해당 기록이 나타난다.
3. **되돌리기 정상 흐름:** 실수로 버튼을 누른 경우, 이전 기록 카드 우측의 [찾음 취소] 버튼을 누른다. 현재 주차 중인 기록이 비어 있으므로 즉시 '현재 주차 기록'으로 복귀한다.
4. **되돌리기 충돌 흐름:** 사용자가 '차 찾음' 후 새롭게 다른 주차 기록을 등록해 이미 현재 주차 기록이 있는 상태에서, 이전 기록 목록의 어떤 항목에 대해 [찾음 취소]를 누르면 시스템은 동작을 중단하고 "현재 다른 주차 기록이 이미 존재하여 되돌릴 수 없습니다."라는 경고를 띄운다. 기존의 현재 주차 기록과 이전 목록 데이터는 전혀 바뀌지 않는다.

### 2.3 여정 3: 기록 수정 및 삭제
1. 기록 카드의 [수정] 버튼을 누르면 위치, 시각, 메모가 입력 가능한 폼 형태로 변경된다.
2. 내용을 고치고 [수정 완료]를 누르면 유효성 검증을 거쳐 저장소가 갱신된다. 만약 위치를 전부 지우고 공백으로 비운 채 저장하려 하면 "위치를 입력해야 합니다." 오류가 나타나며 수정 폼의 입력값과 기존 저장값이 안전하게 유지된다. [수정 취소]를 누르면 저장소 변경 없이 원래 상태로 닫힌다.
3. 기록 카드의 [삭제] 버튼을 누르면 "이 기록을 완전히 삭제하시겠습니까?" 브라우저 확인창이 나타난다. [확인]을 누르면 해당 기록이 저장소 및 목록에서 영구 제거되며, [취소]를 누르면 어떤 데이터도 변경되지 않는다.

### 2.4 여정 4: 브라우저 재방문 및 저장 오류 보호
1. 브라우저를 닫았다가 다시 열면 로컬 저장소에서 기록을 읽어와 화면에 이전과 동일하게 복원한다.
2. 로컬 저장소 데이터가 외부 요인에 의해 훼손되었거나 읽기 권한이 차단된 경우, 또는 키는 있으나 내용이 빈 텍스트인 경우 시스템은 절대로 저장소를 빈 배열로 초기화하거나 새 데이터로 덮어쓰지 않는다.
3. 화면에 "저장된 데이터를 안전하게 읽을 수 없어 읽기 전용 상태로 전환되었습니다."라는 경고를 띄우고, 등록/수정/삭제 버튼을 비활성화하여 원본 훼손을 방지한다.

## 3. 기능별 세부 규격 및 인수 검증 기준

### [PARK-1] 주차 기록 등록
- **정상 동작:** 위치, 시각, 메모(선택)를 입력받아 새 기록을 생성하고 활성 상태(`ACTIVE`)로 저장한다. 시각은 기본값으로 현재 시각을 제공하며 수정할 수 있다.
- **검증 규칙:** 위치는 좌우 공백 제거 후 1글자 이상이어야 한다. 시각은 유효한 날짜 및 시간 형식이어야 한다.
- **실패 및 무변경 동작:** 현재 활성 상태인 기록이 이미 존재하는 경우 등록을 거절하고 입력창의 내용을 지우지 않고 보존한다. 입력값 유효성 검사 실패 시 오류 메시지만 노출하며 저장소는 변경하지 않는다.
- **인수 검증 사례:**
  1. *사례 1 (정상 등록):* 현재 기록이 없는 상태에서 위치 "지상 1층 A구역", 시각 "2026-11-10 09:00" 입력 후 등록 시 현재 주차 기록에 "지상 1층 A구역"이 표시되고 브라우저 저장소에 1건이 저장된다.
  2. *사례 2 (공백 입력 차단):* 위치에 스페이스 공백만 입력하고 [주차 등록] 클릭 시 "위치를 입력해주세요" 오류가 뜨며 입력값과 저장소 상태가 유지된다.
  3. *사례 3 (중복 현재 주차 차단):* 이미 현재 기록이 1건 있는 상태에서 새 위치를 입력하고 [주차 등록] 클릭 시 "이미 주차 중인 기록이 있습니다" 경고가 나타나며, 기존 현재 기록과 신규 입력 양식 내용이 모두 보존된다.

### [PARK-2] 차 찾음 및 찾음 취소
- **정상 동작:** 현재 기록(`ACTIVE`)에서 [차 찾음] 실행 시 상태를 완료(`RESOLVED`)로 변경하여 이전 목록으로 이동시킨다. 이전 기록에서 [찾음 취소] 실행 시 상태를 다시 `ACTIVE`로 변경한다.
- **검증 규칙:** 시스템 전체에서 `ACTIVE` 상태를 가진 기록은 언제나 0개 또는 1개여야 한다.
- **실패 및 무변경 동작:** [찾음 취소]를 시도할 때 이미 `ACTIVE` 상태인 기록이 존재하면 변경을 즉시 중단하고 충돌 경고를 출력한다. 저장소 데이터 및 화면 목록은 전혀 변경되지 않는다.
- **인수 검증 사례:**
  1. *사례 1 (차 찾음 전환):* 현재 주차 기록에서 [차 찾음] 클릭 시 현재 영역이 빈 안내 문구로 바뀌고, '이전 주차 기록' 목록 맨 위에 해당 기록이 즉시 추가된다.
  2. *사례 2 (정상 찾음 취소):* 현재 주차 기록이 비어 있는 상태에서 이전 기록 목록의 최신 항목 [찾음 취소] 클릭 시, 해당 항목이 이전 목록에서 사라지고 상단 '현재 주차 기록' 영역으로 복귀한다.
  3. *사례 3 (취소 충돌 차단):* 이전 기록 A가 있는 상태에서 새 주차 B를 등록(`ACTIVE`)한 뒤, A의 [찾음 취소]를 누르면 "현재 다른 주차 기록이 존재합니다" 오류가 표시되고 A는 이전 기록에, B는 현재 기록에 그대로 유지된다.

### [PARK-3] 기록 수정, 삭제 및 로컬 영속성
- **정상 동작:** 개별 기록의 위치, 시각, 메모를 수정할 수 있다. 삭제 버튼 클릭 시 확인 절차(Confirm)를 거쳐 영구 삭제한다. 브라우저 재실행 시 기존 기록을 온전히 복원한다.
- **검증 규칙:** 수정 시에도 공통 검증 규칙(위치 필수, 시각 형식)을 충족해야 한다. 확인 대화상자에서 취소를 누르면 삭제가 중단된다.
- **실패 및 무변경 동작:** 수정 중 유효하지 않은 값 입력 시 저장을 차단하고 편집 양식을 유지한다. 읽기/저장 I/O 실패 시 임의 덮어쓰기나 초기화를 수행하지 않는다.
- **인수 검증 사례:**
  1. *사례 1 (정상 수정):* 메모가 비어 있던 현재 기록의 [수정]을 눌러 메모에 "출구 정면" 입력 후 [저장] 시 즉시 반영되고 재접속 후에도 유지된다.
  2. *사례 2 (수정 유효성 실패 보호):* 기존 시각 "2026-11-10 10:00"을 달력상 불가능한 값으로 임의 변경하려 할 경우 "유효한 날짜와 시각이 아닙니다" 오류가 뜨며 저장소가 바뀌지 않고 기존 시각이 유지된다.
  3. *사례 3 (삭제 취소):* [삭제] 클릭 시 나타나는 대화상자에서 [취소]를 누르면 데이터가 삭제되지 않고 화면과 저장소에 그대로 남는다.
  4. *사례 4 (저장소 손상 및 빈 값 보호):* 저장소 키의 값이 비정상적인 문자열이거나 빈 텍스트(`""`)인 상태에서 페이지를 열면 화면에 "데이터 무결성 오류: 안전을 위해 읽기 전용으로 잠깁니다" 경고가 노출되며 원본 키를 빈 배열로 덮어쓰지 않고 쓰기 버튼이 비활성화된다.

## 4. 데이터 영속성 및 공통 유효성 검증 설계

### 4.1 공통 유효성 검증 테이블 (COMMON VALIDATION)

다음 규칙은 **(1) 로컬 저장소에서 데이터를 처음 읽어올 때(Loaded Data)**와 **(2) 사용자의 입력/수정 사항을 저장소에 쓰기 직전의 전체 후보 상태(Proposed State)** 양쪽 모두에 **동일하게** 적용된다.

| 필드명 | 데이터 타입 | 필수 여부 | 유효성 검증 규칙 및 제약 | 허용/차단 기준 예시 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | 문자열 (String) | 필수 | 비어있지 않은 고유 식별 문자열 (공백 불가) | 허용: `"c3a0-4b2e"`, 차단: `""`, `"   "`, `null` |
| `location` | 문자열 (String) | 필수 | 앞뒤 공백 제거 후 1글자 이상 | 허용: `"지하 1층"`, 차단: `"   "` (공백 전용), `""` |
| `parkedAt` | 문자열 (String) | 필수 | ISO 8601 형식 (`YYYY-MM-DDTHH:mm`)의 실제 유효한 달력 시각 | 허용: `"2026-11-10T14:30"`, 차단: `"2026-02-30T10:00"` |
| `memo` | 문자열 (String) 또는 null | 선택 | 문자열 규격 (문자열 또는 빈 문자열, null 허용) | 허용: `"기둥 뒤"`, `""`, `null`, 차단: 숫자, 배열 등 비문자열 타입 |
| `status` | 문자열 (String) | 필수 | 열거형 값: `"ACTIVE"`(현재 주차 중) 또는 `"RESOLVED"`(차 찾음 완료) | 허용: `"ACTIVE"`, `"RESOLVED"`, 차단: `"PARKED"`, `"DELETED"`, `""` |
| `createdAt` | 문자열 (String) | 필수 | 생성 시점의 유효한 ISO 8601 날짜 시각 문자열 | 허용: `"2026-11-10T14:30:00.000Z"`, 차단: 유효하지 않은 날짜 포맷 |
| `updatedAt` | 문자열 (String) | 필수 | 최종 수정 시점의 유효한 ISO 8601 날짜 시각 문자열 (동시성 비교용) | 허용: `"2026-11-10T14:30:00.000Z"`, 차단: 결손, 유효하지 않은 시각 |

#### 컬렉션 단위 불변식 (Collection Invariants)
1. **단일 현재 주차 불변식:** 저장 객체의 `records` 배열 내에서 `status === "ACTIVE"`인 항목의 개수는 항상 **0개 또는 1개**여야 한다. (2개 이상 절대 불가)
2. **식별자 고유성 불변식:** `records` 배열 내 모든 항목의 `id`는 상호 중복되지 않아야 한다.

---

### 4.2 구체적 검증 위반 예시 및 처리 방식

#### (1) 스키마는 유효하나 값이 잘못된 기존 영속 데이터 예시 (Loaded Invalid Scenario)
- **저장소 보관 내용 예시 (스키마는 맞으나 값·불변식 위반 복합 페이로드):**
  ```json
  {
    "version": 1,
    "updatedAt": "2026-11-10T10:00:00.000Z",
    "records": [
      {
        "id": "rec-duplicate-01",
        "location": "지하 1층 A-01",
        "parkedAt": "2026-02-31T14:00",
        "memo": 12345,
        "status": "ACTIVE",
        "createdAt": "2026-02-10T14:00:00Z",
        "updatedAt": "2026-02-10T14:00:00Z"
      },
      {
        "id": "rec-duplicate-01",
        "location": "지상 2층 B-03",
        "parkedAt": "2026-11-10T10:00",
        "memo": "입구 쪽",
        "status": "ACTIVE",
        "createdAt": "2026-11-10T10:00:00Z",
        "updatedAt": "2026-11-10T10:00:00Z"
      }
    ]
  }
  ```
- **문제점:** JSON 문법 및 키 구조는 존재하나, `rec-duplicate-01`의 주차 시각(`2월 31일`)이 불가능한 날짜이고, `memo`에 비문자열 숫자가 들어있으며, `id`가 중복되었고, 컬렉션 내 `ACTIVE` 상태가 2건 존재하여 모든 검증 규칙과 불변식을 위반함.
- **처리 동작 (보존 및 쓰기 차단):**
  - 기존 `localStorage` 데이터를 빈 배열로 초기화하거나 임의로 수정하여 덮어쓰지 않고 **있는 그대로 보존**한다.
  - 시스템은 '데이터 무결성 오류' 상태로 진입하고, 화면에 "기존 저장 데이터에 오류가 있어 데이터를 변경할 수 없습니다. 안전을 위해 읽기 전용으로 잠깁니다." 알림을 띄운다.
  - 모든 쓰기 동작(추가/수정/삭제/상태전환) 버튼을 비활성화한다.

#### (2) 잘못된 신규 사용자 입력 및 후보 상태 예시 (Candidate Rejection Scenario)
- **사용자 입력 내용:** 위치란에 `"     "`(스페이스 공백만 입력), 주차 시각에 달력 형식을 벗어난 값 입력, 또는 내부 조작으로 status에 `"INVALID"`가 주입된 후보 상태.
- **처리 동작:**
  - 저장소 쓰기 단계(Candidate Commit)로 진입하지 않고 즉시 차단한다.
  - 화면에 "주차 위치를 공백 없이 입력해 주세요" 및 "올바른 시각을 선택해 주세요" 안내를 노출한다.
  - 사용자가 작성 중인 텍스트나 입력 폼 내용을 지우지 않고 그대로 유지하여 재입력할 수 있도록 한다.
  - 기존 브라우저 저장소 데이터는 1바이트도 수정되지 않는다.

---

### 4.3 저장소 읽기 상태 구분 및 처리 규격

1. **키 부재 (Missing Key):**
   - 저장소에 `parking_records_v1` 키 자체가 존재하지 않는 경우 (`localStorage.getItem() === null`).
   - **처리:** 최초 방문 정상 상태로 판정한다. 내부 메모리 목록을 빈 배열(`[]`)로 시작하며 정상적인 신규 등록을 허용한다.
2. **키 존재 및 빈 값 (Present Empty):**
   - 저장소에 키는 존재하지만 값이 빈 문자열(`""`)이거나 공백 문자로만 채워져 있는 경우.
   - **처리:** 키 부재(정상 초기 상태)로 간주하지 않고 '손상 데이터'로 판정한다. 원본 문자열을 빈 배열로 덮어쓰지 않고 그대로 보존하며 시스템을 읽기 전용 모드로 잠근다.
3. **읽기 I/O 실패 (Read Operation Failure):**
   - 브라우저 보안 정책, 시크릿 모드 저장소 차단, I/O 오류 등으로 인해 `localStorage.getItem()` 호출 시 예외(SecurityError 등)가 발생하는 경우.
   - **처리:** 키가 없는 것으로 조용히 간주하지 않는다. 즉시 사용자에게 "브라우저 저장소에 접근할 수 없습니다. 브라우저 저장소 권한 및 설정을 확인해 주세요." 메시지를 노출하고 쓰기 기능을 잠근다. 원본 저장소에는 일체 쓰기를 시도하지 않는다.
4. **손상되거나 유효하지 않은 데이터 (Corrupted / Invalid Content):**
   - JSON 파싱에 실패(`SyntaxError`)하거나, 파싱은 되었으나 공통 유효성 검증 테이블 및 컬렉션 불변식을 만족하지 못하는 경우.
   - **처리:** 파괴적 복구(빈 데이터로 덮어쓰기)를 엄격히 금지한다. 기존 저장 문자열을 그대로 유지하고 시스템을 읽기 전용 모드로 잠근다.

---

### 4.4 커밋 경계(Commit Boundary) 및 안전한 쓰기 시퀀스

데이터 변경(등록, 상태 전환, 수정, 삭제)은 다음의 엄격한 순서로만 진행된다.

1. **원자적 점유 획득 (planner proposal):** 다중 탭 충돌을 방지하기 위해 `BroadcastChannel`을 통해 짧은 쓰기 잠금 토큰을 획득한다.
2. **최신 저장소 재확인 (Re-read & Concurrency Check):** 저장소의 최신 직렬화 문자열을 읽고 직전 확인 시점의 `updatedAt`과 일치하는지 비교한다. 불일치 시 락을 해제하고 쓰기를 즉시 중단하며 "다른 창에서 데이터가 변경되었습니다. 최신 데이터를 불러옵니다." 경고를 표시하고 최신 상태를 화면에 동기화한다.
3. **후보 상태 생성 (Candidate State Generation):** 복제된 데이터에 변경 사항을 반영하고 현재 시각을 새 `updatedAt`으로 할당한 후보 전체 객체를 구성한다.
4. **공통 유효성 전체 검증 (Validation):** 후보 객체 전체에 대해 `4.1 공통 유효성 검증 테이블`의 필드 규칙과 컬렉션 불변식(ACTIVE 최대 1개, 고유 ID)을 완벽히 검증한다. 검증 탈락 시 잠금을 해제하고 작업을 중단하며 사용자 입력을 보존한다.
5. **직렬화 및 저장소 기록 (Commit):** 후보 객체를 JSON 문자열로 직렬화하여 `localStorage.setItem`을 실행한다.
   - *저장 실패 처리:* 용량 초과(`QuotaExceededError`) 등 브라우저 쓰기 실패 시, 락을 해제하고 기존 메모리 상태를 유지(롤백)하며, 화면에 "저장 공간이 부족하여 저장하지 못했습니다." 경고를 표시하고 사용자의 입력 폼 내용을 화면에 유지한다.
6. **점유 해제 및 메모리 뷰 반영 (Release & View Update):** 쓰기 성공 후 쓰기 잠금을 해제하고, 화면 표시용 메모리 데이터를 교체하여 화면 UI를 갱신한다.

---

### 4.5 다중 탭 동시성 한계 및 환경 제약

- **경합 시나리오 (Interleaving Scenario):**
  - 두 탭(탭 A, 탭 B)이 동시에 같은 시점의 데이터를 읽은 뒤, 탭 A와 탭 B가 각각 신규 '현재 주차 기록'을 생성하고 유효성 검증을 통과하는 상황.
  - 단순 check-then-write나 `storage` 이벤트 감지만으로는 두 탭이 쓰기 직전 검증을 동시에 마쳐버리면 탭 B가 탭 A의 기록을 조용히 덮어쓰거나(Lost Update), 두 탭의 작업이 교차 반영되어 활성 주차 기록이 2개가 되는 불변식 파괴가 발생할 수 있다.
- **직렬화 경계 제안 (Serialization Proposal):**
  - 기획자는 탭 간 메시지 교환(`BroadcastChannel`)을 통한 선점형 잠금 프로토콜을 제안한다. 쓰기 시퀀스에 진입한 첫 번째 탭만이 저장소 쓰기 권한을 가지며, 후행 탭은 `updatedAt` 충돌로 쓰기가 거부되어 입력을 유지한 채 최신 데이터를 불러오도록 유도한다.
- **미지원 환경 한계 (Unsupported Environment Limit):**
  - 브라우저가 `BroadcastChannel`을 지원하지 않거나 비활성화된 환경에서는 완벽한 선점 잠금이 불가능하며, `localStorage.setItem` 직전의 재확인(Re-read) 기법으로만 충돌을 최소화한다. 극단적인 밀리초 단위의 동시 쓰기 경합 시 마지막 쓰기가 이전 쓰기를 덮어쓸 물리적 한계가 존재함을 명시한다.

## 5. 용어집 (Glossary)

- **현재 주차 기록 (`ACTIVE`):** 현재 차량이 주차되어 있는 상태의 기록. 시스템 내에 최대 1개만 존재할 수 있다.
- **이전 주차 기록 (`RESOLVED`):** '차 찾음' 처리가 완료되어 보관 중인 주차 이력 목록. 시간 역순으로 정렬되어 목록에 표시된다.
- **찾음 취소 (Undo):** 완료된 이전 주차 기록을 다시 '현재 주차 기록' 상태로 되돌리는 기능. 현재 주차 중인 기록이 이미 존재할 경우 실행이 차단된다.
- **후보 상태 (Proposed/Candidate State):** 사용자의 입력이나 상태 변경 요청을 반영하여 저장소에 쓰기 전 임시로 구성한 전체 데이터 객체. 공통 유효성 검증을 통과해야만 실제 저장소에 기록된다.
- **읽기 전용 보호 상태 (Read-only Lock):** 저장소 오류, 읽기 실패, 빈 데이터, 손상 데이터가 발견되었을 때 기존 사용자 데이터를 보존하기 위해 추가적인 변경과 덮어쓰기를 전면 차단하는 안전 모드.
- **점유 경계 (Serialization Boundary):** 다중 탭 환경에서 동일한 데이터에 동시 접근하여 덮어쓰는 것을 막기 위해 설정한 쓰기 권한 획득 및 버전 확인 절차.
