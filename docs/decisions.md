# 아키텍처 결정 기록

## D-001 — 초기 설정 형식은 JSON

- 상태: 채택
- 결정: 초기 설정은 JSON으로 저장한다.
- 이유: Node.js와 자연스럽게 맞고 추가 파서가 필요 없다.
- 결과: 주석 등 작성 편의의 필요가 확인될 때 YAML 도입을 검토한다. 역할 설정의 YAML 예시는 설명용일 뿐이다.

## D-002 — Core와 Runtime/Provider 분리

- 상태: 채택
- 결정: Core는 공통 계약을 정의하고 Runtime SDK/Provider 구현은 어댑터에 둔다. Runtime과 Provider/Model 선택을 구분한다.
- 이유: 교체 가능성을 유지하고 검증되지 않은 호환성을 가정하지 않는다.

## D-003 — 파일 기반 프로젝트 메모리부터 시작

- 상태: 채택
- 결정: 첫 저장소 구현은 로컬 파일 기반으로 하고 메모리 계약 뒤에 둔다.
- 이유: 초기 CLI에 외부 인프라를 요구하지 않는다.

## D-004 — Node 내장 테스트 러너 사용

- 상태: 채택
- 결정: TypeScript 빌드 결과를 `node:test`로 검사하고 별도 테스트 프레임워크는 추가하지 않는다.
- 이유: 적은 의존성으로 계약과 순수 정책 함수를 검증한다.

## D-005 — 승인과 실행 권한 분리

- 상태: 채택
- 결정: Planning 검토와 사용자 승인은 별개이며, 승인 Scope 변경에는 별도 승인이 필요하다.
- 이유: PM이 목표나 핵심 요구사항을 조용히 바꾸지 못하게 한다.

## D-006 — Planning 계약을 도메인 모듈로 분리

- 상태: 채택
- 결정: Planning Loop 계약과 정책은 `src/planning/`에 두고 공통 Project, 승인, 모델 타입은 `src/core/`에서 재사용한다.
- 이유: Core에 Planning 전용 타입을 중복해서 넣지 않으면서 경계를 분명히 한다.

## D-007 — Scope와 기획안 이력을 버전 불변으로 관리

- 상태: 채택
- 결정: 승인된 Scope 변경은 새 버전, 기획 수정은 새 PlanDraft 버전으로 기록한다. 각 기획안은 Scope 버전을 참조하고 검토는 특정 기획안 버전에 연결한다.
- 이유: 이력을 보존하고 오래된 검토가 새 기획에 잘못 적용되는 일을 막는다.

## D-008 — 공유 메모리 기록은 Controller가 소유

- 상태: 채택
- 결정: Writer와 Reviewer는 결과를 반환하고, Controller가 검증 후 PlanningMemoryStore를 통해 기록한다.
- 이유: 공유 파일의 동시 수정을 피하고 저장 권한을 한곳에 둔다.

## D-009 — Scope 비교는 구조적이며 의미 판정은 하지 않음

- 상태: 채택
- 결정: 결정론적 정책은 필드 차이와 프로젝트/버전 오류를 찾는다. 의미 검토는 Reviewer가 맡고 불확실한 경우 사용자가 결정한다.
- 이유: 문자열 동일성만으로 요구사항의 의미가 같은지 판단할 수 없다.

## D-010 — 비용 계산과 분리된 토큰 사용량 기록

- 상태: 채택
- 결정: Provider별 누락 가능성을 고려해 토큰 수를 선택 필드로 두고 금액 계산값은 포함하지 않는다.
- 이유: 사용량 응답 형식은 다르고 비용 계산에는 별도의 최신 요금 정보가 필요하다.

## D-011 — 반복 이슈는 ID와 유형, 심각도 진행을 함께 비교

- 상태: 채택
- 결정: 같은 ID·유형·관련 요구사항의 이슈는 심각도 감소 시 개선으로 보고, 동일/상승 심각도일 때만 미해결 반복 후보로 사용자 확인을 요청한다. 다른 ID나 유형은 단순 반복으로 확정하지 않는다.
- 이유: ID만 비교하면 실제 개선을 무시할 수 있고, 설명 문자열만으로 의미적 동일성을 안전하게 판단할 수 없다.

## D-012 — Reviewer 결과는 Controller 경계에서 교차 검증

- 상태: 채택
- 결정: 현재/이전 Review의 프로젝트와 Plan 버전을 검증하고, 현재 Plan의 Scope 버전이 Controller가 확인한 승인 Scope와 일치하는지 검사한다. `pass`에 중대 이슈가 있으면 수정으로 보내며 Scope 위반은 별도 승인 경로로 보낸다.
- 이유: Reviewer 결과를 그대로 신뢰하거나 오래된/다른 프로젝트의 검토를 현재 승인에 사용하는 일을 막는다.

## D-013 — STEP 2A는 Fake 역할과 로컬 파일로 오프라인 실행

- 상태: 채택
- 결정: Planning 포트는 유지하고 Fake Writer/Reviewer와 주입 가능한 Controller로 오프라인 흐름을 실행한다. `providerId`가 `fake`가 아닌 설정은 거부한다.
- 이유: 외부 호출 없이 Scope 승인, 재작업, 버전 저장, 중단 정책을 검증한다.

## D-014 — Plan/Review는 추가 전용, 상태만 원자 교체

- 상태: 채택
- 결정: Scope/Plan/Review 레코드는 기존 파일을 덮어쓰지 않는다. 최신 `state.json`과 승인 결정은 임시 파일을 기록한 뒤 교체한다. 프로젝트 ID와 안전한 식별자 검증으로 경로를 구성한다.
- 이유: 반복 실행과 중단 시 기존 확정 버전을 보존하고 프로젝트 간 경로 혼합을 막는다.

## D-015 — 데모 Scope 승인과 실제 최종 승인을 구분

- 상태: 채택
- 결정: 샘플 Scope는 `DEMO FIXTURE`로 표시된 별도 파일에서만 불러오며, CLI는 이를 실제 사용자 결정이라고 표시하지 않는다. 최종 Plan 승인은 항상 pending으로 남긴다.
- 이유: 오프라인 테스트를 가능하게 하면서 실제 승인 권한을 가장하지 않는다.

## D-016 — Review 구조/참조 정합성은 정식 저장 전에 검증

- 상태: 채택
- 결정: Review에 Scope ID/버전을 명시하고 공통 파서와 참조 검증을 Controller와 파일 저장소에서 재사용한다. 잘못된 필드·프로젝트·Plan/Scope 참조·중복 버전은 정식 Review로 저장하지 않는다. Controller는 별도 오류 로그와 실패 상태를 남긴다.
- 이유: 존재하지 않는 Plan 버전이나 다른 프로젝트에 대한 응답을 정상 검토 이력에 포함하지 않기 위함이다. 품질 이슈나 Scope 변경 제안이 포함된 유효한 Review는 기존 정책 판단을 위해 보존한다.
- 결과: Scope 필드가 없는 과거 Review는 자동 변환하지 않고 읽기 검증에서 거부한다. 오류 기록 타입과 `appendError`는 Planning 계약에 두며 Core의 `MemoryEvent`를 재사용한다. 외부 JSON 역할 설정은 내부 `PlanningRoleConfig.model`로 변환한다.

## D-017 — STEP 2B의 Gemini 인증은 Vertex AI ADC 사용

- 상태: 채택
- 결정: 로컬 PC에서 실행하는 Gemini 모델 호출은 Vertex AI와 Google Gen AI SDK (`@google/genai`)로 구현하고, 자격 증명은 Application Default Credentials (ADC)에서 읽는다. GCP 프로젝트와 위치는 환경 변수, 모델 ID는 역할별 설정으로 받는다. Writer와 Reviewer는 초기 설정에서 `gemini-3.8-flash`를 사용한다.
- 이유: API 키나 개인 자격 증명을 소스코드/저장소에 저장하지 않고, 개발 및 실행 환경의 ADC 공급 방식을 활용한다.
- 결과: Writer와 Reviewer는 독립 모델 설정을 유지한다. 로컬 실사용 호출 전 ADC 및 GCP 프로젝트 접근 권한을 구성하고 확인해야 한다.

## D-018 — STEP 3는 승인 기획에 연결된 수동 개발 명령

- 상태: 채택
- 결정: 최종 승인된 현재 Plan과 Scope를 작업의 출처로 고정하고 해시를 기록한다. 수동 JSON 작업 정의는 생성 후 불변이며 담당자 지정·결과 제출·검수를 별도 명령으로 기록한다. Scope의 데모 승인 fixture는 개발 권한을 만들 수 없다.
- 이유: Reviewer의 통과나 Worker의 결과 보고를 최종 승인·검증 사실로 혼동하지 않기 위함이다. 수동 작업 분해의 의미상 범위 적합성은 사용자가 검토한다.
- 결과: 이 단계는 Runtime을 호출하거나 보고된 파일의 존재를 자동 검증하지 않는다. 수동 검수 통과에는 모든 완료 조건의 체크와 설명이 필요하다. 자동 증거 수집 및 재작업 한도는 STEP 4에서 추가한다.

## D-019 — 개발 상태와 전이 이력을 하나의 버전 스냅샷으로 저장

- 상태: 채택
- 결정: 프로젝트별 schemaVersion 1 파일에 작업과 변경 전후 이력을 함께 저장한다. 기대 revision과 배타 잠금 파일로 동시 쓰기를 거부하고, 임시 파일을 교체한다. 기존 출처·작업 정의·이력의 변경을 거부한다.
- 이유: 상태 저장 성공과 이력 저장 실패가 분리되지 않도록 하고, 오래된 실행 결과의 덮어쓰기를 막는다.
- 결과: 실패 시 현재 상태를 보존한다. 중단으로 남은 잠금은 자동으로 제거하지 않는다. 실제 실행 프로세스 유무를 확인한 후 수동 복구한다. 최종 Plan 승인은 승인 레코드를 먼저 기록하며, 중간 중단 후 같은 명령으로 상태 갱신을 마칠 수 있다.

## D-020 — 지휘자 겸 기획자 하나를 먼저 완성하고 팀원은 순차 연결

- 상태: 채택 (사용자 방향 확인: 2026-11-08)
- 결정: ADTF의 첫 대상은 총괄 PM·슈퍼바이저 하나다. 기획 작성·검토는 지휘자의 책임에 포함한다. 지휘자를 독립적으로 검증한 뒤 개발·테스트 등 팀원 Agent를 하나씩 구현하고 연결한다.
- 이유: 현재 만들고 있는 대상과 최종 팀 운영 구조를 분명히 하고, 기획 기능 또는 수동 상태 관리만으로 지휘자가 완성됐다고 오해하지 않도록 한다.
- 결과: STEP 4의 검증·재작업 정책 이후 요구 정리·Scope 제안·기획·작업 분해·지시서·보고를 지휘자로 통합하는 마일스톤을 둔다. 팀원 연결 전 정책 검증에는 명시적 테스트용 보고를 사용한다. 첫 제품 테스트 주제는 재고·유통기한 CLI를 제안하며 실제 제품 Scope 승인은 별도 기록한다. 안내서와 테스트 계획은 실제 실행 기록과 구분한다.

## D-021 — 객관적 검증 근거와 완료 조건 검수를 분리

- 상태: 채택
- 결정: 선택형 verificationProfile 작업에 파일·선언 입력 해시, 실제 명령 결과를 수집하고 기획·작업·결과·시도와 연결한다. 객관적 검사 통과 후 완료 조건의 수동 검수를 받는다. 검수 직전에 선언 파일의 해시를 다시 확인한다.
- 이유: 파일 존재나 종료코드 0이 모든 기능의 의미상 완성을 증명하지 않으며, 오래된 검증 결과를 새 제출물에 재사용할 수 없도록 한다.
- 결과: 근거는 개발 상태와 전이 이력에 함께 저장한다. 기존 프로필 없는 작업은 기존 수동 의미를 유지하고 과거 승인이나 증거를 자동 변환하지 않는다.

## D-022 — 운영자 명령 목록과 제한된 로컬 검사 프로세스

- 상태: 채택
- 결정: Worker 보고의 명령 문자열 대신 별도 운영자 설정의 commandId를 사용한다. shell:false, 인수 배열, 최소 환경 변수, 명령당 최대 60초 및 제한된 출력으로 실행한다. 선언 파일은 선택 작업공간 안의 상대 경로로 제한한다.
- 이유: 검사할 명령과 보고된 결과의 권한을 분리하고, 무한 실행·출력 또는 잘못된 경로를 명확한 차단으로 처리한다.
- 결과: OS 샌드박스나 전체 저장소 무결성 증명이 아니다. 운영자가 신뢰할 실행 파일과 테스트를 지정한다. 로그의 일반 토큰 표기는 가리지만 임의 비밀정보의 완전한 탐지를 보장하지 않는다.

## D-023 — 시도·재작업 예산과 환경 차단의 구분

- 상태: 채택
- 결정: 프로필 작업은 담당자 지정 시도와 품질 재작업 횟수를 별도로 기록한다. 산출물·검사·수동 검수 실패는 예산 내 재작업, 소진 후 차단이다. 도구 누락·시간·출력량·접근·설정 문제는 환경 차단이며 품질 재작업 예산을 소비하지 않는다.
- 이유: 인프라 복구를 코드 재작업과 혼동하거나 상태 초기화로 실패 한도를 우회하지 않도록 한다.
- 결과: 최대 재작업 수는 작업 정의의 불변 필드다. 한도 차단은 재개 대신 사용자의 취소·새 계획 결정을 기다린다. 이번 단계는 Worker 자동 재호출을 추가하지 않는다.

## D-024 — 지휘자 제안과 승인 권한을 분리한 단계별 진입점

- 상태: 채택
- 결정: SupervisorProposer는 질문·Scope·작업 제안만 반환한다. Controller가 ID·버전·시간·승인·상태를 소유하고, 원문과 답변을 분리 보존한다. 기존 Planning과 Development를 재사용한다.
- 이유: 모델이 만든 승인·완료 주장을 실제 결정으로 취급하지 않고 검증된 상태 규칙을 유지하기 위해서다.
- 결과: 사용자 Scope·Plan 승인과 운영자 작업 수락을 각각 받는다. 작업은 승인 출처 해시, 요구 ID 추적 및 DAG 검사에 연결한다. 실행 명령·검증 프로필·재작업 예산은 모델 제안으로 설치하지 않고 운영자가 별도로 지정한다.

## D-025 — STEP 5A 기본 통합과 STEP 5B 변경 후 재개를 분리

- 상태: 채택
- 결정: 기본 통합 흐름을 먼저 검증하고, 기존 Planning의 추가 질문·Scope 변경·한도·실패 상태는 보고 후 중단한다. 원문·승인·기획 버전을 삭제해 재실행하지 않는다.
- 이유: 변경 승인 이후의 새 Scope/Plan 출처와 기존 작업 처리 정책이 없는 상태에서 자동 재개하면 승인 경계를 훼손할 수 있다.
- 결과: STEP 5A의 TEST/STUB 정책·CLI 검증과 실제 Gemini 전체 주제 인수를 구분한다. STEP 5B에서 버전 전환·재개 및 실제 기획 품질을 검증한 뒤 팀원을 연결한다. 토큰 사용량 집계는 기존 Planning 역할만 지원하며 신규 제안 호출 집계도 후속 보완한다.

## D-026 — 명시적 재개 권한과 총 반복 한도 보존

- 상태: 채택 (STEP 5B)
- 결정: 대기 기획의 전체 상태·원본 Scope·Plan/Review 해시를 continuation으로 보존한다. 답변 또는 변경 결정을 받은 뒤 별도 resume-plan만 새 버전을 생성한다. 총 iterationCount/maxIterations를 유지하며 설정으로 초기화하지 못한다.
- 이유: 추가 질문이나 Scope 변경을 이용해 이전 승인·오류·반복 한도를 삭제하거나 무한 재시도를 만들지 않도록 한다.
- 결과: 재개 시작을 supervisor에 먼저 기록하고 Planning의 continuationId에 연결한다. 완료된 모델 실행의 저장 마무리는 재시도 가능하지만 도중 중단된 모델 호출은 자동 재실행하지 않는다. 진행 보고에 다음 행동과 중단 이유를 표시한다.

## D-027 — 작업 제안 전 Scope 변경 결정과 새 기획 승인

- 상태: 채택 (STEP 5B)
- 결정: 사용자 및 Reviewer 변경 요청을 기획 대기 단계에서 받아 새 Scope 전체와 변경 요청을 함께 명시적으로 승인/거절한다. 승인 시에도 모델은 별도 명령으로 호출한다. 거절한 Reviewer 변경은 기존 Scope에 맞춰 수정하고, 사용자가 제안한 변경의 거절은 기존 승인 절차로 돌아간다.
- 이유: 요청 승인과 범위 스냅샷 승인, 기획안 승인, 실제 실행 권한이 혼동되지 않도록 한다.
- 결과: 이전 Scope/Plan/승인은 유지하고 새 Plan 버전은 다시 검토·최종 승인한다. 이미 제안·초기화한 작업의 정의 변경과 자동 이관은 지원하지 않고 별도 사용자 결정이 필요한 후속 범위로 둔다.

## D-028 — 제안 호출 사용량을 기획 역할 기록과 분리

- 결과: JSON 파싱 실패에도 제공받은 토큰 지표는 기록한다. 원문·답변·응답 본문·공급자 오류 본문은 이 ledger에 넣지 않는다. 기록 실패 시 제안을 확정하지 않으며 공급자가 이미 과금했을 수 있음을 알린다. 달러 비용 계산이나 청구서 대조를 대신하지 않는다.

## D-029 — 현재 지휘자 하나의 완성과 단독 검증에 집중

- 이유: 실제 질문이 재고 핵심 규칙을 놓쳤고, Scope에 음수 증감량을 금지하는 모순이 생겼다.

### D-038 실제 평가 후 보완

- 직접 인용 요청만으로는 정상 후보도 검증 실패하여 줄 번호를 선택하고 코드가 원문을 추출하도록 변경했다. 빈 줄 선택 실패 후에는 유효한 비공백 줄 번호를 동적 응답 enum으로 제한했다.
- 동일 모델의 사각지대가 남아, 첫 검토가 승인 대상으로 보낼 때만 현재 판정에 노출되지 않은 독립 반례 점검을 추가했다. 실제 요청은 논리적 리뷰당 최대2회이고 단계별 사용량을 기록한다. 반복 예산·최종 사용자 승인은 유지한다.
- 최종 개발 사례 차단6/10→9/10, 정상4/4 유지, 형식 오류0이지만 빈 저장 문자열 결함 미검출1회를 명시했다. 호출/토큰 비용 증가와 중간 실패도 [보고서](planning-quality-hardening-20261108.md)에 기록했다.
