# 아키텍처 결정 기록

## D-001 — 초기 설정 형식은 JSON

- 상태: 채택
- 결정: 초기 설정은 JSON으로 저장한다.
- 이유: Node.js와 자연스럽게 맞고 추가 파서가 필요 없다.
- 결과: 주석 등 작성 편의의 필요가 확인될 때 YAML 도입을 검토한다. 역할 설정의 YAML 예시는 설명용일 뿐이다.

## D-002 — Core와 Runtime/Provider 분리

- 상태: 채택
- 결정: Core는 공통 계약을 정의하고 Runtime SDK/Provider 구현은 어댑터에 둔다. Runtime과 Provider/Model 선택을 구분한다.
- 이유: 교체 가능성을 유지하고 검증되지 않은 호환성을 가정하지 않는다.

## D-003 — 파일 기반 프로젝트 메모리부터 시작

- 상태: 채택
- 결정: 첫 저장소 구현은 로컬 파일 기반으로 하고 메모리 계약 뒤에 둔다.
- 이유: 초기 CLI에 외부 인프라를 요구하지 않는다.

## D-004 — Node 내장 테스트 러너 사용

- 상태: 채택
- 결정: TypeScript 빌드 결과를 `node:test`로 검사하고 별도 테스트 프레임워크는 추가하지 않는다.
- 이유: 적은 의존성으로 계약과 순수 정책 함수를 검증한다.

## D-005 — 승인과 실행 권한 분리

- 상태: 채택
- 결정: Planning 검토와 사용자 승인은 별개이며, 승인 Scope 변경에는 별도 승인이 필요하다.
- 이유: PM이 목표나 핵심 요구사항을 조용히 바꾸지 못하게 한다.

## D-006 — Planning 계약을 도메인 모듈로 분리

- 상태: 채택
- 결정: Planning Loop 계약과 정책은 `src/planning/`에 두고 공통 Project, 승인, 모델 타입은 `src/core/`에서 재사용한다.
- 이유: Core에 Planning 전용 타입을 중복해서 넣지 않으면서 경계를 분명히 한다.

## D-007 — Scope와 기획안 이력을 버전 불변으로 관리

- 상태: 채택
- 결정: 승인된 Scope 변경은 새 버전, 기획 수정은 새 PlanDraft 버전으로 기록한다. 각 기획안은 Scope 버전을 참조하고 검토는 특정 기획안 버전에 연결한다.
- 이유: 이력을 보존하고 오래된 검토가 새 기획에 잘못 적용되는 일을 막는다.

## D-008 — 공유 메모리 기록은 Controller가 소유

- 상태: 채택
- 결정: Writer와 Reviewer는 결과를 반환하고, Controller가 검증 후 PlanningMemoryStore를 통해 기록한다.
- 이유: 공유 파일의 동시 수정을 피하고 저장 권한을 한곳에 둔다.

## D-009 — Scope 비교는 구조적이며 의미 판정은 하지 않음

- 상태: 채택
- 결정: 결정론적 정책은 필드 차이와 프로젝트/버전 오류를 찾는다. 의미 검토는 Reviewer가 맡고 불확실한 경우 사용자가 결정한다.
- 이유: 문자열 동일성만으로 요구사항의 의미가 같은지 판단할 수 없다.

## D-010 — 비용 계산과 분리된 토큰 사용량 기록

- 상태: 채택
- 결정: Provider별 누락 가능성을 고려해 토큰 수를 선택 필드로 두고 금액 계산값은 포함하지 않는다.
- 이유: 사용량 응답 형식은 다르고 비용 계산에는 별도의 최신 요금 정보가 필요하다.

## D-011 — 반복 이슈는 ID와 유형, 심각도 진행을 함께 비교

- 상태: 채택
- 결정: 같은 ID·유형·관련 요구사항의 이슈는 심각도 감소 시 개선으로 보고, 동일/상승 심각도일 때만 미해결 반복 후보로 사용자 확인을 요청한다. 다른 ID나 유형은 단순 반복으로 확정하지 않는다.
- 이유: ID만 비교하면 실제 개선을 무시할 수 있고, 설명 문자열만으로 의미적 동일성을 안전하게 판단할 수 없다.

## D-012 — Reviewer 결과는 Controller 경계에서 교차 검증

- 상태: 채택
- 결정: 현재/이전 Review의 프로젝트와 Plan 버전을 검증하고, 현재 Plan의 Scope 버전이 Controller가 확인한 승인 Scope와 일치하는지 검사한다. `pass`에 중대 이슈가 있으면 수정으로 보내며 Scope 위반은 별도 승인 경로로 보낸다.
- 이유: Reviewer 결과를 그대로 신뢰하거나 오래된/다른 프로젝트의 검토를 현재 승인에 사용하는 일을 막는다.

## D-013 — STEP 2A는 Fake 역할과 로컬 파일로 오프라인 실행

- 상태: 채택
- 결정: Planning 포트는 유지하고 Fake Writer/Reviewer와 주입 가능한 Controller로 오프라인 흐름을 실행한다. `providerId`가 `fake`가 아닌 설정은 거부한다.
- 이유: 외부 호출 없이 Scope 승인, 재작업, 버전 저장, 중단 정책을 검증한다.

## D-014 — Plan/Review는 추가 전용, 상태만 원자 교체

- 상태: 채택
- 결정: Scope/Plan/Review 레코드는 기존 파일을 덮어쓰지 않는다. 최신 `state.json`과 승인 결정은 임시 파일을 기록한 뒤 교체한다. 프로젝트 ID와 안전한 식별자 검증으로 경로를 구성한다.
- 이유: 반복 실행과 중단 시 기존 확정 버전을 보존하고 프로젝트 간 경로 혼합을 막는다.

## D-015 — 데모 Scope 승인과 실제 최종 승인을 구분

- 상태: 채택
- 결정: 샘플 Scope는 `DEMO FIXTURE`로 표시된 별도 파일에서만 불러오며, CLI는 이를 실제 사용자 결정이라고 표시하지 않는다. 최종 Plan 승인은 항상 pending으로 남긴다.
- 이유: 오프라인 테스트를 가능하게 하면서 실제 승인 권한을 가장하지 않는다.

## D-016 — Review 구조/참조 정합성은 정식 저장 전에 검증

- 상태: 채택
- 결정: Review에 Scope ID/버전을 명시하고 공통 파서와 참조 검증을 Controller와 파일 저장소에서 재사용한다. 잘못된 필드·프로젝트·Plan/Scope 참조·중복 버전은 정식 Review로 저장하지 않는다. Controller는 별도 오류 로그와 실패 상태를 남긴다.
- 이유: 존재하지 않는 Plan 버전이나 다른 프로젝트에 대한 응답을 정상 검토 이력에 포함하지 않기 위함이다. 품질 이슈나 Scope 변경 제안이 포함된 유효한 Review는 기존 정책 판단을 위해 보존한다.
- 결과: Scope 필드가 없는 과거 Review는 자동 변환하지 않고 읽기 검증에서 거부한다. 오류 기록 타입과 `appendError`는 Planning 계약에 두며 Core의 `MemoryEvent`를 재사용한다. 외부 JSON 역할 설정은 내부 `PlanningRoleConfig.model`로 변환한다.

## D-017 — STEP 2B의 Gemini 인증은 Vertex AI ADC 사용

- 상태: 채택
- 결정: 로컬 PC에서 실행하는 Gemini 모델 호출은 Vertex AI와 Google Gen AI SDK (`@google/genai`)로 구현하고, 자격 증명은 Application Default Credentials (ADC)에서 읽는다. GCP 프로젝트와 위치는 환경 변수, 모델 ID는 역할별 설정으로 받는다. Writer와 Reviewer는 초기 설정에서 `gemini-3.8-flash`를 사용한다.
- 이유: API 키나 개인 자격 증명을 소스코드/저장소에 저장하지 않고, 개발 및 실행 환경의 ADC 공급 방식을 활용한다.
- 결과: Writer와 Reviewer는 독립 모델 설정을 유지한다. 로컬 실사용 호출 전 ADC 및 GCP 프로젝트 접근 권한을 구성하고 확인해야 한다.
