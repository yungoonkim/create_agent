# 기획 세션 지속 실행과 위험 중심 검토

사용자가 매번 ZIP/명령/압축 전달을 반복하는 비용을 줄이도록 요청했다. [공통 CLI](../src/cli/planning-session.ts), [세션 조정](../src/planning/session.ts), [모델 요청 원장](../src/planning/session-ledger.ts)을 추가한다. 기존 PlanningLoopController가 수정·검토를 수행하고 새 세션은 승인 Scope·설정·저장 상태·명시적 요청 상한·검증된 응답 재사용을 관리한다. 서비스 UI나 제품 구현·팀원 실행은 추가하지 않는다.

## 실행·재개 경계

- 최초에는 승인 Scope/요구/설정 스냅샷과 해시를 저장한다. 설정 변경으로 기존 반복 예산을 초기화하지 않는다.
- `run`은 신규 실행 또는 정확한 `revising`/`reviewing` 상태에서만 진행한다. 검토 완료된 수정은 실제 REVISE 판정·현재 버전·이전 검토 ID·실제 Scope 승인을 검증해 이어간다. 검토 실패 재개는 기존 단일 retryReview 정책을 사용한다.
- 사용자 질문·Scope 변경·최종 승인·limit/failed 상태에서는 새 호출을 하지 않는다. 최종 승인은 자동으로 만들지 않는다. 사용자 결정 이후의 일반 연결은 기존 지휘자 continuation을 통해 수행하며, 새 세션 CLI가 그 결정을 자동 대체하지 않는다.
- 새 Writer를 호출하기 전에 최대 Writer1+일반1+반례1에 해당하는3회가 남아 있어야 한다. 중간 결과만 만들고 비용 상한에 걸리는 상황을 줄인다. 반례가 불필요한 경우 실제 호출 수는 더 적다.
- 전체 세션 잠금과 SDK 요청 잠금으로 중복 실행을 막는다. 비정상 종료 후 자동으로 잠금을 지우거나 알 수 없는 요청을 반복하지 않는다.

## 요청 원장과 예산

모델 요청 전체의 정규화 SHA-256을 키로 사용한다. 완료 응답이 정확히 일치할 때만 재사용하고, 캐시 응답에서는 과거 usage를 제거해 사용량을 중복 집계하지 않는다. 실제 응답 원문과 최초 usage는 원장에 남긴다. SDK 호출 전에 예약을 영속화하므로 전송 실패/불명확한 종료도 횟수에 포함한다. 같은 실패 요청은 자동으로 다시 보내지 않는다. 캐시가 잘못된 응답이면 동일한 로컬 검증에서 다시 중단될 뿐 유료 fallback은 없다.

원래 budget.json은 해시로 보호하며 증액은 명시적 `budget --max-calls TOTAL --reason TEXT` 명령과 별도 순서 있는 변경 기록으로만 제공한다. 기존 사용 횟수·원래 상한·반복 제한을 유지한다. 자동 증액은 없다. 이는 SDK 호출 상한이며 통화 단위 청구액 보장은 아니다.

세션 export는 잠금 아래 별도 디렉터리로 복사한 스냅샷에 기획 검토표/상태/해시를 넣는다. 이후 실행이 진행돼도 기존 압축의 원자료는 변하지 않는다. 변경된 코드와 별도로 세션 폴더를 유지하면 다음 주제별 배포물 없이 계속 사용할 수 있다.

## 검토 규칙 v2

기존 검토 스냅샷과 v1 판정은 그대로 유지한다. 새 반례 프롬프트는 데이터 손실·권한 밖 Scope 변경·구체적 모순을 우선한다. 빈 문자열이 실제 JSON 파싱 실패 분기에 포함되면 해당 근거를 인용해 설명할 수 있도록 하고, 중복된 별도 분기를 강요하지 않는다. null/키 부재와 같은 것으로 처리해도 된다는 뜻은 아니다.

`validation.version:2`는 여러 규칙을 하나의 실제 실패/원본 보존 사례로 묶는 `acceptanceGroups`를 지원한다. 각 그룹은 1부터 시작하는 ruleIndexes, 실제 인용, 연결 이유를 가진다. 모든 개별 규칙의 load/candidate 근거와 supported 판정은 여전히 필요하다. 그룹 인용도 현재 원문과 일치해야 하며 헤딩이나 빈 인용은 통과 근거가 아니다. 버전이 없는 과거 검토는 기존의 개별 사례 규칙을 그대로 적용한다.

Writer와 반례 프롬프트에는 A/B가 같은 값을 읽고 검사한 뒤 차례로 덮어쓰는 순서를 점검하도록 추가한다. 이것만으로 모델이 모든 동시성 결함을 잡는다고 주장하지 않는다. 실제 원문 반례와 사용자 검토가 계속 필요하다.

## 이번 주차 기록의 처리

사용자 복구 압축 [원본](acceptance/parking-recovery-20261110/parking-review-recovery.tar.gz)은 내부16개 해시 검사를 통과했다. SHA-256 `84fa13a59fa2623b713fcec3aad39feb36e44d86123dadf5ddf5f692c25f152b`. 반례 정상 완료·REVISE, 새1회/누적4회, 원래 상한6회다. raw issues/questions는 모두 빈 배열이며, 저장 감사에서 제시된 근거 부족을 로컬 정책이6개 지적으로 만들었다. 일반 검토의 updatedAt 제안도 수정 피드백에 포함됐다. 새 응답 총22,070토큰 중 thinking11,394토큰이며 최종 청구액은 확정하지 않는다. 반복적인 유료 전송 진단은 이번 결과로 중단한다.

실제 복구 결과를 오프라인으로 가져와 `revising`, 반복1/2회, 사용4/6회, 남은2회가 보존되는 것을 확인했다. 다음 반복에3회가 필요하므로 request_budget_decision에서 새 호출0회로 중단한다. 기존 검토를 v2 기준으로 다시 작성하거나 승인하지 않았다. 추가 실호출은 예산을6→7회로 늘릴지 사용자가 결정한 뒤에만 가능하다. 이번 구현·검증에서 Gemini 호출과 예산 증액은0회다.

테스트는 실제 API 대신 명시적 TEST/STUB 전송을 사용한다. 자동 수정 후 pending 승인, 버전 보존, 저장 상태 재개 검증, 재실행 시 호출0회, 요청 캐시·실패/미완료 예약·예산 증액 이력·복구 import 및 그룹 근거 검증을 확인한다. 실제 새 기획안의 품질이나 모델의 새 지침 준수는 아직 측정하지 않았다.

## 후속 사용자 승인

사용자는 누적6→7회 증액 질문 뒤 다음 단계를 진행하겠다고 승인했다. [별도 승인 기록](acceptance/parking-recovery-20261110/budget-approved-7.json)에 기존4회·원래6회·현재7회·새 최대3회 및 준비 중 모델 호출0회를 남겼다. 이전 준비/오프라인 검사 기록은 그 시점 그대로 보존한다. 확인용 세션의 nextAction은 run이며 실제 PC 모델 실행 결과는 아직 받지 않았다.
