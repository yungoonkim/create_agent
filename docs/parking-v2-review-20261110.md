# 주차 v2 실행 결과와 남은 검토 문제

[사용자 원본](acceptance/parking-v2-20261110/parking-export-c7572906.tar.gz)의 SHA-256은 `a7d7aea9d3fac4b70f7b9a1265465b3bbe31ca09e9c21082512dacc1921c6385`이다. 내부31개 파일 목록·SHA-256을 확인했다. [기획 v2](acceptance/parking-v2-20261110/plan-v2.md)와 [오프라인 감사 요약](acceptance/parking-v2-20261110/audit-summary.json)을 함께 보존한다. 원본 기획·공식 Review·상태·승인을 수정하지 않았다. 이번 분석 추가 모델 호출0회다.

## 확인된 실행

Writer v2, 일반 검토, 반례 검토가 각각 STOP으로 완료됐다. 새 SDK 요청3회이며 이전4회를 포함해7/7회를 사용했다. 반복2/2회, 기획 v2, Scope v1 유지, 상태는 `awaiting_user_input`이다. 최종 기획 승인 기록은 없다. 세션 자동 수정·검토·상한 유지와 export는 실제 PC에서 동작했다. 이것을 내용 품질의 최종 합격으로 해석하지 않는다.

확인 가능한 새 요청 토큰은 Writer26,366 + 일반 검토36,146 + 반례14,811 =77,323이다. 이전 사용량을 포함한 총액이나 실제 청구액은 아니다. 이전 응답 재사용으로 재호출은 줄였지만 이번 전체 문맥 입력은 여전히 크다. 비용 절감 효과가 검증됐다고 주장하지 않는다.

## 중단 원인

모델의 v2 outcome은 pass, 원시 issues는0개, challengeCompleted는 true다. 그러나 저장 감사의 로컬 근거 검사에서 `issue-storage-validation-6`이 남았다. v1과 v2의6번째 규칙은 모두 createdAt이므로 이번 반복 감지는 같은 항목을 가리킨다(일반적으로 순번 기반 ID의 안정성은 별도 개선 대상이다).

모델은 createdAt을 supported로 판정하고 acceptanceGroups[0]에서 확인했다고 설명했지만, 실제 그룹 ruleIndexes는 `[1,3,4,5,8,9]`, `[2,3,5]`이며6이 없다. 개별 acceptance 인용도 비어 있다. 따라서 로컬 검증이 통과시키지 않은 것은 맞다. 추가로 v2 예시134·143행의 createdAt 값은 정상 날짜여서, 단순히 그룹 인덱스에6을 추가하는 것도 충분한 보완이 아니다. 구체적 잘못된 값과 기대하는 보존 동작이 필요하다. 원시 응답이나 원본을 임의 보정하지 않는다.

이전 지적 해결표는 모델이 모두 resolved라고 주장했지만 현재 로컬 근거 판정과 모순된다. 정책은 같은 지적 반복을 감지해 사용자 입력 대기로 멈췄다. 사용자에게 새로운 제품 취향을 물어야 하는 상황은 아니며, 기술적 검토 불일치의 설명과 처리 흐름을 보완해야 한다. 현재 기획 반복과 SDK 예산은 모두 소진됐으므로 같은 명령으로 추가 유료 실행을 시도하지 않는다.

## 실제 내용의 개선과 남은 결함

- 빈 저장 문자열 보존이60·93행 등에 명시됐다. updatedAt이 공통 규칙에 포함됐고 실패 사례가 관련 규칙별 그룹으로 제공됐다. 로컬 저장 감사 지적은6개에서1개로 줄었다. 이 수치는 해당 체크리스트 결과이며 전체 품질 점수는 아니다.
- 다중 탭 동시 쓰기의 위험을13·198~200행에서 인지하고 잠금 제안을 추가했다. 하지만30·203~204행은 BroadcastChannel 미지원 환경에서 재확인만 하고 실제 덮어쓰기가 발생할 수 있음을 허용한다. 이는 승인된 기존 값 보존/오래된 탭의 덮어쓰기 방지 조건을 충족하지 못한다. 한계를 적었다는 이유로 승인된 요구가 완화되지는 않는다.
- BroadcastChannel은 메시지 전달 API이며 그 자체가 원자적 잠금은 아니다.186·202행은 잠금 프로토콜의 획득/동시 요청/중단 시 동작을 구체화하지 않은 채 직렬화를 보장한다고 설명한다. 이것은 제품 코드 실행 여부와 무관하게 기획에 남은 근거 공백이다. 원시 반례 issues0개는 이 결함을 지적하지 못했다.
- 그룹 사례도 각 규칙과 의미상 연결되는지 확인해야 한다. 그룹0은 비어 있는 ID 검사까지 포함한다고 기재됐지만 예시는 정상 비공백 문자열 ID의 중복 사례다. 구조·인용 검증만으로 의미적 범위를 증명하지 못한다.
- 저장 검토표는 개별 acceptance가 없을 때 그룹 근거를 펼쳐 보여주지 않는다. 그룹으로 검증된 항목도 ‘근거 없음’으로 표시될 수 있어 사용자에게 혼란을 준다. 로컬 차단과 모델의 해결 주장도 분리해 표시할 필요가 있다.

## 진행 순서

1. 현재 단계: 주차 v2 실행·내용·예산 감사와 원자료 보존(이 문서).
2. 다음 단계: 검토 근거와 해결 판정의 불일치, 동시성 요구 위반, 그룹 근거 표시 및 불필요한 입력 중복을 오프라인으로 정리·보완한다. 기존 응답 재생과 고정 반례로 먼저 검증한다. 새 실호출은 현재 상한을 자동 연장하지 않고 별도 결정한다.
3. 이후 단계: 별도의 변경 영향표를 구현한다. 기존 요구별 수정 전후 비교/지적 해결표 위에 영향 범위와 확인할 항목을 연결한다. 사용자는 이번에 영향표 구현을 요청한 것이 아니라 작업 순서를 질문했다. 이 단계는 아직 착수하지 않는다.

별도로, 앞서 전달한 데이터 복구 ZIP에서 빈 `ledger/calls`와 `runs` 디렉터리가 누락되어 생긴 중단은 배포 문제였다. 같은 오류를 오프라인 재현했고 빈 디렉터리 복원 후4/7회 상태 조회가 정상임을 확인했다. 이번 사용자 파일에서 실제 요청3회와 export가 확인돼 실행이 이어졌음을 알 수 있다.
