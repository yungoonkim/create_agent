## API 오류에 대해 확인한 범위

실패 요청은 공통 GeminiPlanningReviewer의 challenge 경로이며 `responseJsonSchema`, JSON MIME, medium thinking, SDK attempts 1을 사용했다. 에러는 어느 인자가 잘못됐는지 특정하지 않는다. 과거 택배 시험의 구조화 응답 전송 오류와 같은 유형이지만 스키마가 이번 오류의 확정 원인이라고 단정하지 않는다.

이전 택배의 no-schema/필수 키/최대8개 보완은 분리한 고정 후보 실험에만 적용됐고 공통 Reviewer에는 통합되지 않았다. 이번 새 주제는 기존 공통 경로를 실행했으므로 과거 후보의 전송 성공을 그대로 기대할 수 없었다. 새 실행 패키지를 준비할 때 이 차이를 충분히 반영하지 못했다.

## 기획 내용과 일반 Reviewer 판단

추가·차 찾음/취소·수정·삭제·입력 보존·로컬 읽기 오류·손상 데이터 보호 등 기본 흐름은 v1에 포함됐다. 하지만 일반 검토의 pass를 완성도 통과로 받아들일 수 없다. 반례 검토는 실행되지 않았으므로 아래 문제를 찾아냈을지 여부도 알 수 없다.

1. **다중 탭 저장 경쟁을 막는 근거가 부족하다.** v1 21행, 169~174행, 181~183행은 storage 이벤트와 updatedAt 비교 후 setItem을 설명한다. A/B 탭이 같은 버전을 읽고 각각 후보를 만든 뒤 A 비교→B 비교→A 저장→B 저장 순으로 진행하면 두 비교 모두 통과하고 B가 A의 기록을 덮어쓸 수 있다. 각 후보의 ACTIVE 개수는 1개여도 기록 소실은 생긴다. 이벤트와 사전 비교만으로 비교~저장 구간의 배타성을 보장하지 않는다. 이는 브라우저 제품을 구현해 확인한 결함이 아니라 문서의 동시성 보장이 성립하지 않는 반례다.
2. **동시성 메타데이터 규격이 빠졌다.** 19행은 단일 JSON 배열, 182행은 updatedAt을 요구하지만 94~101행의 공통 필드 표에는 위치·타입·갱신/충돌 규칙이 없다. 일반 Reviewer가 이를 단순 제안으로 남겼다. 핵심 보존 조건에 쓰는 값이므로 단순 표기 보완으로 취급하기 어렵다.
3. **찾음 전환의 탭 충돌 처리도 명시해야 한다.** 167행은 모든 변경을 나열하지만 183행의 최신 값 비교 대상에는 등록/수정/삭제만 있다. 차 찾음/찾음 취소까지 동일한 안전 경계에 들어가야 한다. 현재 문서는 이를 명확히 연결하지 않는다.

## 다음 작업의 경계

전체 실행을 다시 시작하거나 Writer를 새로 호출하지 않는다. 먼저 공통 반례 전송 경로에 과거 후보의 효과와 한계를 반영할 방법을 준비하고, 저장된 요청/일반 응답으로 오프라인 검증한다. 실제 재호출이 필요해지면 이전 3회와 남은 상한을 유지하는 명시적 이어가기 도구를 따로 준비한다. 실패한 반례만 처리하며 기획/일반 검토 원본을 재사용한다.

전송 문제가 해결돼도 위 내용 결함을 해결했다고 간주하지 않는다. Reviewer가 실제 반례를 지적으로 기록하는지와 Writer 수정 후 원래 요구가 보존되는지를 별도로 평가해야 한다. 최종 사용자 승인·제품 구현은 아직 수행하지 않는다.
