# 택배 수령 기록의 새 근거·수정 보존 실모델 시험 계획

생성 전에 고정한 기능 시험이다. **실제 Gemini 호출0회이며 실행/품질 결과가 아니다.** 사용자가 오늘 모바일로만 작업하므로 Cloud에서 도구·오프라인 검증만 준비하고 실제 실행은 이후 PC 작업 때 수행한다.

## 입력과 제한

- 새 주제는 혼자 사용하는 택배 수령 기록이다. 이름·예정 날짜·메모 등록, 같은 내용의 별도 기록, 한 건의 받음/미수령 전환·수정·확인 삭제·로컬 보존을 기획한다.
- 고정 v1에는 “저장된 received의 타입 검증을 건너뛴다”는 고의 예외를 추가했다. 이 초안은 모델이 생성하지 않았다. 실제 Writer는 수정 단계부터 호출한다. 공통 검증의 선언과 예외가 모순되는 것을 발견하고 같은 Scope 안에서 교정하는지 본다.
- [고정 사례](../examples/review-evidence-live/cases.json)·[해시/설정](../examples/review-evidence-live/freeze.json)은 생산 코드 커밋 `2b8a365`와 파일 해시, 실행기, 잠금파일, 요금표에 연결한다. 완성 참고안은 dry-run 또는 고정 초안의 기반에만 쓰고 live Writer에 정답으로 별도 주입하지 않는다.
- Vertex AI / iceu-songpa11 / global / gemini-3.8-flash / ADC. Reviewer MEDIUM·출력16000, Writer는 기존 공급자 기본 thinking·출력16000이다. 비결정성 및 Writer 기본값의 변동 가능성은 남는다.
- 논리적 검토 최대2라운드, **전체 SDK 요청 최대5회**: 일반·반례 최대4회 + 실제 수정 Writer 최대1회. 첫 일반 검토가 수정으로 분기하면 반례를 생략하므로 더 적을 수 있다. 추가 유료 채점은 없다.
- Scope는 TEST/STUB 승인 fixture이며 실제 사용자 승인·제품 구현·팀원 실행은 하지 않는다. 완료해도 최종 승인 pending으로 둔다.

## 원문 감사 기준

1. 정상 종료/스키마 검증·실제 사용량·부분 응답/실패를 구분하는가. MAX_TOKENS나 전송 실패는 합격이 아니다.
2. 고의 검증 우회를 찾아 원문 규칙·예외와 함께 타당하게 지적하는가. Scope 변경/질문으로 불필요하게 우회하지 않는가.
3. 수정본이 예외를 없애고, 공통 검증을 로드와 전체 후보 양쪽에 명시하는가. JSON 문법은 맞지만 received가 문자열인 저장값의 보존/차단 사례가 구체적인가.
4. 모든 승인 요구/제약에 대한 이전·현재 근거와 이전 지적/생성된 품질 피드백별 해결 근거가 맞는가. 잘못된 규칙을 그대로 유지하는 것을 보존으로 칭찬하거나, 변경 요약만으로 해결을 선언하지 않는가.
5. 최초 검토의 해당 없음과 실제 재검토의 해결 판단을 구분하고, valid trigger가 진짜 값 검증 통과 조건을 뒷받침하는가. 사용자 검토표가 원문·버전·해시와 맞는가.
6. 미해결·한도·오류·규칙 퇴행과 알려지지 않은 토큰/비용을 빠뜨리지 않고 보존하는가. 최종 사용자 승인을 대신하지 않는가.

진행자 Codex가 원문을 감사하며 구현자와 같은 평가자다. 외부 독립 평가나 익명 A/B 비교, 일반적인 품질 향상 검증이라고 주장하지 않는다. 수정 기획 하나의 성공만으로 실패율/재현성/오탐률을 추정하지 않는다. 코드가 인용의 존재를 확인해도 의미가 틀릴 수 있다.

## 실행·보존

고정 시험의 시작 예약은 체크아웃당1회이며 SDK도1시도다. 이미 시작한 ID/예약을 삭제하거나 실패를 성공으로 교체하지 않는다. 인증/프로토콜 실패도 기록에 남긴다. 유료 호출의 자동 복구·재생은 없으며, 실패 후 후속 시험이 필요하면 먼저 원자료를 보존하고 별도 실행 관계를 명시해야 한다.

새 ID의 별도 물리 저장소에서 원요청/응답·모든 버전·Review·비교표·실패·사용량·해시·압축을 보존한다. 요금은 제공 지표와 고정 요금표 소계만 산출하며 미제공 지표는 모름이다. 실제 청구서 금액으로 단정하지 않는다. 옛 승인 프로젝트나 완료한 실험을 재실행하지 않는다.
