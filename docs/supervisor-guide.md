# ADTF 총괄 PM·슈퍼바이저 안내서

정리일: 2026-11-08 (Asia/Seoul)

## 1. 무엇을 먼저 만드는가

ADTF의 첫 목표는 **개발팀 전체를 이끄는 지휘자 겸 기획자 Agent 하나를 완성하는 것**이다. 문서에서는 이를 총괄 PM 또는 슈퍼바이저라고 부른다. 기획은 이 Agent의 주요 책임 중 하나다.

지휘자를 먼저 독립적으로 검증한 다음 개발, 테스트 등 팀원 Agent를 하나씩 만들고 연결한다. 현재 팀원들을 동시에 만들거나 실제 개발팀이 자동 운영되는 것으로 간주하지 않는다.

지휘자의 책임은 다음과 같다.

- 사용자의 목적과 필수 요구, 제외할 기능, 제약, 미확정 사항을 정리한다.
- 중요한 불확실성을 질문하고, 승인할 범위를 제안한다.
- 기획안을 작성·검토·수정하고 사용자에게 최종 승인을 요청한다.
- 승인된 기획을 작업으로 나누고 각 작업의 지시서·산출물·완료 조건·의존성을 정한다.
- 팀원이 연결된 뒤에는 준비된 작업을 위임하고, 결과와 검증 근거를 확인한다.
- 결과에 따라 검수 승인, 재작업, 차단, 범위 변경 승인 요청을 결정한다.
- 전체 진행 상황과 완료·미완료·미검증 사항을 사용자에게 보고한다.

사용자는 목표와 범위 및 기획안의 최종 승인 권한을 갖는다. 지휘자가 승인된 핵심 요구를 조용히 바꾸거나 자신의 검토를 사용자 승인으로 처리해서는 안 된다.

## 2. 역할 이름을 어떻게 이해하면 되는가

| 이름 | 역할 | 현재 상태 |
| --- | --- | --- |
| 총괄 PM·슈퍼바이저 | 요구 정리부터 위임·검수·보고까지 지휘 | 기본 통합·추가 답변·변경 승인 후 재개 구현, 실제 모델 품질 인수는 남음 |
| Planning Writer | 승인 Scope 안에서 기획 초안과 수정본 작성 | Fake 및 Gemini 호출 구현 |
| Planning Reviewer | 기획의 누락·모순·범위·위험 검토 | Fake 및 Gemini 호출 구현 |
| Controller | 승인·버전·상태·반복 제한을 코드 규칙으로 관리 | Planning 실행 및 수동 Development 구현 |
| 개발 Worker | 지시받은 코드를 실제 작성·수정 | 아직 미구현, 지휘자 검증 이후 추가 |
| 테스트·검증 팀원 | 독립적으로 산출물을 검사하고 결과 보고 | 아직 미구현, 추후 하나씩 추가 |

Writer와 Reviewer는 지휘자의 기획 기능을 나눈 역할이다. 현재 둘 다 Gemini 3.8 Flash를 사용할 수 있지만, 이 사실만으로 독립된 개발 팀원이나 완성된 지휘자가 생긴 것은 아니다.

Controller의 상태 전이 코드는 LLM의 판단을 그대로 실행하지 않도록 승인과 저장 경계를 지킨다. STEP 5A에서는 모델의 질문·Scope·작업 제안을 이 규칙과 연결했다.

## 3. 최종적으로 사용자는 어떻게 요청하는가

최종 사용 흐름의 예시는 다음과 같다. 기본 흐름은 현재 단계별 `supervisor` 명령으로 연결하며, 한 번의 요청으로 승인과 실행을 모두 자동 처리하는 명령은 없다.

```text
사용자: "작은 매장의 재고와 유통기한을 관리할 도구를 만들고 싶어."
   ↓
지휘자: 목적·제약 확인, 중요한 미확정 사항 질문
   ↓
지휘자: 필수·제외 기능과 완료 조건을 포함한 Scope 제안
   ↓
사용자: Scope 승인
   ↓
Writer 초안 → Reviewer 검토 → 필요하면 새 버전으로 수정
   ↓
지휘자: 기획안과 남은 의사결정 보고
   ↓
사용자: 특정 버전의 기획안 최종 승인
   ↓
지휘자: 개발 작업 분해, 의존성·지시서·검증 계획 작성
   ↓
[팀원 연결 이후] 준비된 작업 위임 → 팀원 결과 제출
   ↓
지휘자: 실제 산출물·검사 결과 확인 → 승인 / 재작업 / 차단
   ↓
지휘자: 완료 결과, 검증 근거, 남은 한계 보고
```

Scope 변경이 필요하면 별도 승인을 요청한다. 승인 대기, 환경 오류, 검증 실패, 재작업 한도 초과를 완료라고 보고하지 않는다.

## 4. 현재까지 실제로 만든 내용

| 단계 | 구현·확인한 내용 | 아직 자동화되지 않은 부분 |
| --- | --- | --- |
| STEP 1 | TypeScript CLI, 공통 프로젝트·모델·Runtime·승인 계약 | 통합 지휘자 |
| STEP 1.5 | 기획·검토·Scope·버전·상태 계약과 판단 정책 | 요구 대화 및 기획 실행 |
| STEP 2A | Fake Writer/Reviewer, 파일 메모리, Planning Loop | 실제 모델 호출 |
| STEP 2B | Gemini Writer/Reviewer, 사용량·오류 기록, Scope 승인 CLI | 대화로 Scope를 자동 정리하고 제안하는 입구 |
| STEP 3 | 최종 Plan 승인, 수동 작업 등록·담당 지정·결과 제출·검수·이력 | AI 작업 분해 및 실제 Worker 실행 |
| STEP 4 | 선택형 파일·명령 근거, 시도·재작업 한도, 품질 실패·환경 차단 판단 | 지휘자 전체 통합과 실제 Worker 재호출 |
| STEP 5A | 원문·질문 답변·Scope 제안·승인·기획·작업 분해·지시서·진행 보고 통합 | 기획 중 추가 답변·Scope 변경 승인 후 재개, 실제 Gemini 전체 인수 |
| STEP 5B | 추가 답변·변경 승인/거절 후 명시적 재개, 새 버전 승인·작업 출처, 사용량 기록 | 실제 Gemini 전체 주제의 의미상 품질 인수 |

STEP 2B는 사용자의 Windows PC에서 ADC로 실행한 결과를 확인했다. Writer Plan v1 저장, Reviewer 검토, 최종 사용자 승인 대기까지 도달했다. 그 화면만으로 생성 기획안의 내용상 품질까지 평가한 것은 아니다.

STEP 3는 Cloud의 격리된 테스트 데이터로 최종 승인 → 작업 생성 → 담당 지정 → 결과 제출 → 수동 검수 → 후속 작업 준비까지 검증했다. 기존 40개와 신규 13개를 합쳐 테스트 53개가 통과했다. 사용자의 Windows 기획안을 Cloud에서 대신 승인하거나 실제 Worker가 개발했다고 기록한 것이 아니다.

STEP 4에서는 실제 임시 파일과 Node 검사 명령으로 근거·실패·한도·환경·동시 실행 정책을 검증했다. 신규 21개를 포함한 전체 74개가 통과했다. 상세 결과와 검증하지 않은 부분은 [실행 보고서](step4-report.md)에 기록했다.

STEP 5A에서는 단계별 CLI로 질문·답변을 기록하고 모델이 Scope와 작업 목록을 제안할 수 있다. 기존 수동 JSON 기획 진입점도 유지한다. Cloud의 TEST/STUB 통합 시험을 포함한 전체 93개 테스트가 통과했다. [사용법](supervisor-workflow.md)과 [실제 시험 결과](step5a-report.md)를 참고한다.

STEP 5B에서는 기획 중 추가 질문 답변과 Scope 변경 승인/거절을 받은 뒤 이전 기록을 보존하고 새 Plan 버전으로 이어가는 기능을 추가했다. 반복 한도·중단 후 중복 호출 방지와 사용량 기록까지 전체 111개 테스트가 통과했다. 실제 Gemini의 질문·기획 내용 품질을 평가한 결과는 아니며 [검증 보고서](step5b-report.md)에 경계를 기록했다.

## 5. 지휘자를 먼저 완성하기 위해 남은 작업

1. **실제 모델 기획 품질 평가.** 같은 재고·유통기한 주제로 Gemini가 중요한 질문·날짜 경계·요구 추적·작업 지시를 충분히 생성하는지 확인한다. 고정 TEST/STUB 통과와 의미상 품질 평가는 별개다. 실행용 config와 원문은 examples/supervisor-gemini에 준비했다.
2. **지휘자 단독 인수 마무리.** [테스트 시나리오](supervisor-test-plan.md)의 실제 모델 정상 흐름과 변경 후 재개까지 확인하고 보고서를 보완한다. 현재 Cloud에는 ADC와 Vertex AI 접속 설정이 없어 실호출하지 않았다.
3. **그다음 팀원 Agent를 하나씩 연결.** 먼저 사용할 개발 Worker의 범위와 Runtime 호환성을 정하고, 지시서 입력 → 실제 결과 → 지휘자의 검수까지 확인한다. 이후 필요에 따라 테스트 등 다른 팀원을 추가한다.

질문·작업 제안은 모델 호출로 생성할 수 있으나 다음 명령은 사용자가 선택하며 실제 Worker는 실행하지 않는다. 지휘자 전체 인수 테스트 완료로 설명하지 않는다.

## 6. 어떤 주제로 시험하는가

권장 첫 주제는 **작은 매장의 재고·유통기한 관리 CLI**다. 현재는 테스트 제안이며 실제 관리 대상 프로젝트의 승인 Scope가 아니다.

외부 API나 결제 없이 결과를 확인할 수 있고, 입고 묶음별 유통기한·재고 수량·날짜 경계 같은 도메인 규칙으로 기획의 구체성을 평가할 수 있다. 상세 입력, 가정, 기대 결과와 실패 시나리오는 [지휘자 테스트 계획](supervisor-test-plan.md)에 정리했다.

지휘자 단독 단계에서는 이 제품의 기획과 작업 지시·검수 판단을 시험한다. 실제 제품 구현까지 확인하는 테스트는 개발 Worker가 연결된 뒤 같은 주제로 확장한다.

## 7. 실행 기록은 어디에 남는가

현재 구현이 실제로 사용하는 기록은 다음과 같다.

| 기록 | 위치·내용 |
| --- | --- |
| 원본 요구사항 | `.adtf/projects/<projectId>/requirements.md` |
| 지휘자 원문·질문 답변·제안·이력 | `.adtf/projects/<projectId>/supervisor/state.json` |
| 기획 재개 권한·기준·결정·시작/완료 | 같은 supervisor 상태의 continuations |
| 질문·Scope·작업 제안 사용량 | `supervisor/usage.jsonl` (본문·자격 증명 제외) |
| Scope 버전 | `scope/v<version>.json` 및 승인 연결 |
| 기획안 버전 | `planning/plans/<planId>/v<version>.json` |
| 기획 검토 | `planning/reviews/<planId>/v<version>.json` |
| Planning 상태·오류·사용량 | `planning/state.json`, `planning/errors/`, `planning/usage.jsonl` |
| 수동 개발 작업과 전이 이력 | `development/state.json` |
| STEP 4 검증 근거 | 같은 개발 상태의 작업별 `evidence`와 과거 before/after 이력 |
| 사용자 승인 레코드 | `.adtf/approvals/` |

위 상대 경로는 프로젝트 폴더 아래의 해당 기록을 뜻한다. 지휘자 진입 시 원문은 supervisor 상태에 저장되고 기획 시작 시 requirements.md에도 보존된다. 작업 지시서는 저장된 작업 제안과 승인 기획으로부터 report에서 구성한다.

실행마다 사람이 읽을 수 있는 보고서도 작성한다. 보고서에는 실행 ID, 코드 커밋, 환경, 모델, 입력, 질문·답변, 승인한 Scope/Plan 버전, 작업·검토 이력, 검증 결과, 실제로 실행하지 못한 부분, 다음 행동을 담는다. 원본 JSON 기록과 보고서의 참조가 맞아야 한다. 인증 토큰이나 ADC 파일 내용은 포함하지 않는다.

## 8. Cloud와 PC를 어떻게 구분하는가

모바일 Codex의 Cloud 대화에서 개발과 테스트를 계속 지시할 수 있다. PC 페어링은 이 개발 작업의 필수 조건이 아니다.

Cloud 코드 수정 결과는 GitHub 브랜치로 공유한다. Windows의 ADC와 `.adtf` 실행 데이터는 Cloud로 자동 동기화되지 않는다. 실제 Gemini 호출은 호출할 환경에 ADC 등 지원 인증과 네트워크 접근이 준비돼 있어야 한다. 현재 확인한 실제 Gemini 실행 환경은 사용자의 로컬 PC다.
