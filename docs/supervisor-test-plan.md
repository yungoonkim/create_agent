# 지휘자 겸 기획자 Agent 테스트 계획

정리일: 2026-11-08 (Asia/Seoul)
상태: **테스트 제안·기대 동작 정의. 전체 시나리오 실행 전.**

이 문서는 지휘자를 먼저 완성하고, 그 후 팀원 Agent를 하나씩 연결한다는 개발 순서를 따른다. 아래 샘플 답변·기획·승인은 테스트 설계를 설명하기 위한 예시이며 실제 사용자 승인 기록이 아니다.

## 1. 첫 주제와 목적

**주제: 작은 매장의 재고·유통기한 관리 CLI.**

이 주제를 통해 지휘자가 모호한 요청을 구체적인 기획으로 바꾸고, 실제로 검증 가능한 작업 지시를 작성하는지 확인한다. 외부 데이터 제공업체의 장애나 웹 화면 디자인과 별개로 수량·날짜·저장 결과를 비교할 수 있다.

이 제품은 ADTF가 나중에 관리할 테스트 대상이다. 테스트 대상의 업무 코드를 ADTF 프레임워크 소스와 섞지 않는다. 지휘자 단독 테스트는 기획·지시·판단을 평가하고, 실제 제품 개발은 팀원 연결 이후의 통합 테스트에서 수행한다.

## 2. 사용자 최초 요청

```text
작은 매장에서 혼자 사용할 재고·유통기한 관리 도구를 만들고 싶어.
물건이 들어오거나 나가면 수량을 바꾸고,
유통기한이 가까운 물건을 확인할 수 있으면 좋겠어.
우선 내 컴퓨터에서 사용하고 기획안은 한국어로 작성해줘.
```

처음 요청에는 일부 정보를 의도적으로 남겨 둔다. 지휘자가 임의로 로그인, 결제, 클라우드 배포 등을 추가하는지, 업무 규칙을 확인하는지 관찰한다.

## 3. 지휘자가 확인할 중요한 질문

질문의 정확한 문장이나 개수를 강제하지 않는다. 아래처럼 기획을 바꾸는 불확실성을 해결하는지가 기준이다.

| 미확정 항목 | 확인하는 이유 | 재현용 샘플 답변 |
| --- | --- | --- |
| 같은 상품의 유통기한이 다른 경우 | 상품 한 개의 날짜로 덮어쓰면 먼저 들어온 재고를 잃을 수 있음 | 입고 묶음별 lotId로 별도 관리 |
| 수량과 단위 | 소수 수량, 음수, 단위 변환의 범위 결정 | 수량은 정수, 단위는 표시용 문자열, 단위 변환 없음 |
| 유통기한 임박 기준 | 당일·경계일의 포함 여부 결정 | 기준일부터 N일 뒤까지 양 끝 포함, 만료는 별도 표시 |
| 사용 환경·보관 | UI 및 외부 인프라 범위 결정 | 1인용 Node.js CLI, 로컬 JSON 파일 |
| 제외 기능 | 범위 확대 방지 | 로그인·결제·문자/푸시·바코드·외부 API·배포 제외 |

실제 테스트에서는 질문과 답변을 원문으로 기록한다. 테스트 진행자가 위 샘플을 입력했다는 사실도 구분한다. 꼭 필요하지 않은 질문을 끝없이 반복하거나 이미 답한 항목을 다시 묻는지도 관찰한다.

## 4. 승인할 Scope의 예시

다음은 범위 제안이다. 실제 실행에서는 독립 프로젝트 ID와 새 Scope 버전을 만들고, 사용자가 내용을 확인한 뒤 승인한다.

| 요구 ID | 필수 기능 | 검증 가능한 완료 조건 |
| --- | --- | --- |
| INV-001 | 입고 묶음 등록 | 서로 다른 lotId의 같은 이름 상품과 서로 다른 날짜가 각각 보존됨 |
| INV-002 | 묶음별 수량 변경 | 증감 후 수량이 정확하고 0 미만이 되는 요청은 실패하며 기존 기록 유지 |
| INV-003 | 전체 재고 조회 | 각 lotId·상품명·수량·단위·유통기한을 구분해 표시 |
| INV-004 | 만료·임박 재고 조회 | 주어진 기준일과 N일에 맞는 묶음만 분류, 수량 0인 묶음은 알림 대상 제외 |
| INV-005 | 저장 및 입력 검증 | 재실행해도 기록 유지, 중복 lotId·존재하지 않는 날짜·소수 수량·잘못된 N 거부 |

제약 예시:

- TypeScript strict, Node.js CLI, 로컬 JSON 파일로 시작한다.
- 수량은 0 이상의 정수이며 등록 시에도 같은 조건을 적용한다.
- 유통기한은 실제로 존재하는 `YYYY-MM-DD` 날짜다.
- 날짜 테스트는 명시적인 기준일을 받는다. 사용자 날짜 기준은 Asia/Seoul로 명시하되 테스트를 PC 현재 시각에 의존시키지 않는다.
- 출력 순서는 유통기한 오름차순, 같은 날이면 lotId 순으로 고정한다.
- 승인된 제외 기능을 필수 구현으로 추가하지 않는다.

## 5. 기대 기획안

Writer가 만드는 기획안에는 최소한 다음 내용이 서로 맞게 들어 있어야 한다.

1. 목적, 사용자와 주요 사용 흐름
2. 승인된 필수·제외 기능 및 제약
3. 입고 묶음 데이터 모델과 수량·날짜 검증 규칙
4. 등록·수량 변경·조회·유통기한 확인 동작과 오류 처리
5. 요구 ID별 완료 조건과 구체적인 테스트 사례
6. 개발 순서와 의존성, 실제 구현 위험과 미확정 사항

Reviewer는 문장이 그럴듯한지만 평가하지 않는다. 원본 요청·Scope·기획안을 대조하고, 누락 요구 ID와 수정 방향을 포함한 이슈를 남긴다. 수정이 필요하면 Writer가 새 버전을 만들고 이전 버전은 보존한다. 최종 버전의 검토가 끝나도 사용자 승인 전에는 개발을 시작하지 않는다.

## 6. 날짜·수량의 구체적인 판정 예

기준일 `2026-11-08`, N=2인 **재현용 데이터**를 사용한다. 실제 실행 당일의 날짜라는 뜻은 아니다.

| lotId | 상품 | 수량 | 유통기한 | 기대 분류 |
| --- | --- | --- | --- | --- |
| LOT-A | 우유 | 3 | 2026-11-07 | 만료 |
| LOT-B | 우유 | 5 | 2026-11-08 | 임박: 당일 포함 |
| LOT-C | 요거트 | 2 | 2026-11-10 | 임박: N일 뒤 경계 포함 |
| LOT-D | 치즈 | 4 | 2026-11-11 | 임박 대상에서 제외 |
| LOT-E | 주스 | 0 | 2026-11-09 | 수량 0이므로 임박 대상에서 제외 |

기획안과 지시서가 이 표의 기대 결과를 설명할 수 있어야 한다. 향후 구현 검사에는 LOT-B에서 2개 출고 → 수량 3, 추가 4개 출고 시 오류 및 수량 3 유지도 포함한다.

## 7. 지휘자 단독 인수 테스트

STEP 5A는 기본 통합 CLI와 TEST/STUB 흐름을 검증했다(전체 93개 테스트). 아래 전체 주제에 대한 실제 Gemini 의미상 인수 시험과 변경 승인 후 재개는 아직 완료하지 않았다. 정책 시험은 [STEP 4 보고서](step4-report.md), 통합 시험별 대응과 남은 항목은 [STEP 5A 보고서](step5a-report.md)에 기록했다.

| ID | 상황 | 지휘자의 기대 행동 | 남길 근거 |
| --- | --- | --- | --- |
| SUP-01 | 최초의 모호한 요청 | 필요한 질문과 답변을 기록하고 Scope 제안 | 원본 요청, 질문·답변, 미확정 사항 |
| SUP-02 | Scope 승인 전 | 승인 대기, 승인을 대신 만들지 않음 | Scope 버전과 승인 상태 |
| SUP-03 | 정상 기획 | 요구 ID가 연결된 한국어 기획 작성·검토 | Plan/Review 버전과 요구 추적표 |
| SUP-04 | 기획에 날짜 경계 누락 | 이슈와 수정 방향을 남기고 새 Plan 버전 검토 | 수정 전후와 Review 연결 |
| SUP-05 | Reviewer 통과 | 특정 Plan 버전에 대한 최종 사용자 승인 요청 | pending 승인 레코드 |
| SUP-06 | 최종 기획 승인 | 작업·산출물·조건·검증 방법·의존성 제안 | 구조화 작업 목록과 지시서 |
| SUP-07 | 입고 처리 전 조회 구현을 시작하려 함 | 의존성에 맞게 순서를 조정하거나 대기 | 작업 상태·선행 조건 |
| SUP-08 | 테스트용 팀원이 '완료'라고만 보고 | 근거 부족을 표시하고 추가 제출 또는 차단 | 테스트용 보고, 누락 근거와 판단 |
| SUP-09 | 테스트용 보고는 성공, 실제 검사 fixture는 실패 | 실패 근거에 따라 재작업 요청 | 검사 결과와 재작업 사유 |
| SUP-10 | 같은 문제가 재작업 한도를 초과 | 중단·차단 후 사용자에게 원인과 선택지 보고 | 시도·재작업 횟수, 중단 사유 |
| SUP-11 | 사용자가 로그인 기능을 중간에 요청 | 기존 Scope를 보존하고 변경 승인 요청 | 변경 요청, 영향, 승인 대기 |
| SUP-12 | 테스트 환경에 필요한 도구가 없음 | 환경 차단을 보고하고 완료로 처리하지 않음 | 실행 환경 및 오류 |
| SUP-13 | 성공·실패·대기 작업이 섞임 | 각각을 구분한 진행/완료 보고서 작성 | 작업별 상태와 근거 링크 |

팀원 Agent가 없는 단계에서는 **TEST/STUB로 표시한 보고**와 실제 임시 파일·검사 fixture를 사용한다. LLM이 특정 실패 이슈를 매번 만들어주리라 기대하지 않고, 실패 정책은 재현 가능한 입력으로 검증한다. 실제 모델 기획 품질은 별도 실행에서 평가한다.

## 8. 팀원 연결 이후의 통합 테스트

지휘자 단독 테스트가 충족된 뒤, 첫 개발 Worker를 연결해 같은 주제를 실제로 구현한다. 개발 Worker가 지시서를 받아 작업하고, 지휘자는 실제 파일·변경 목록·검사 결과를 근거로 판단해야 한다.

그다음 필요에 따라 테스트 팀원을 추가해 독립 검증과 교차 검수를 확인한다. 단계별로 어떤 팀원을 연결했는지와 실제 Runtime·모델의 지원 여부를 기록한다. 연결되지 않은 팀원이 작업한 것처럼 보고하지 않는다.

## 9. 실행 방식과 판정

- Fake/stub 검증은 매번 같은 입력으로 승인·상태·실패 정책을 재현한다.
- 실제 Gemini 검증은 고정한 요청과 Scope로 작성·검토를 수행한다. LLM 결과는 달라질 수 있으므로 문장 일치 대신 요구 포함·제외 기능 준수·판정 가능한 완료 조건을 평가한다.
- 팀원 연결 전에는 실행 가능한 정책 시나리오만 수행하고, 미구현 시나리오는 미실행으로 남긴다.
- 준비된 환경에서 한 번 통과한 뒤 별도 실행 ID로 재현해 결과와 수정 횟수를 비교한다. 단일 결과만으로 모든 주제에서 성능이 보장된다고 결론내리지 않는다.
- 현재 실제 Gemini 인증은 로컬 ADC에서 확인됐다. Cloud에서 실제 모델을 호출하려면 Cloud 환경에도 지원 인증과 네트워크 접근을 별도로 준비해야 한다.

지휘자 합격 기준은 필수 요구 보존, 검토·승인 버전 정합성, 구체적인 작업 지시, 근거에 따른 검수·재작업·중단, 사실과 일치하는 보고다. 자동으로 실제 개발을 수행했다는 합격 판정은 팀원 연결 이후 통합 테스트에서만 할 수 있다.

## 10. 사람이 읽을 수 있는 실행 보고서 양식

아래 양식을 실행마다 복사해 작성한다. 자동 보고서 생성은 아직 구현되지 않았다. 원본 실행 데이터는 프로젝트 메모리에 보관하고, 공유할 문서에는 인증정보를 넣지 않는다.

```markdown
# 슈퍼바이저 테스트 실행 보고서

- 실행 ID / 실행 일시 / 테스트 시나리오 버전:
- 코드 커밋 / 실행 환경 / 모델 / 역할별 설정:
- 수행 범위: 지휘자 단독 또는 연결된 실제 팀원 목록
- 사용자 입력과 질문·답변:
- 승인 Scope ID·버전 / 승인 결정:
- Plan ID·버전 / Review 결과 / 최종 승인 결정:
- 요구사항 → 기획 항목 → 작업 → 검증 근거 연결:
- 테스트용 보고와 실제 Worker 결과의 구분:
- 시나리오별 결과: 통과 / 실패 / 미실행 / 승인 대기
- 수정·재작업 횟수와 사유:
- 생성·변경된 실제 파일과 검사 결과 참조:
- 소요 시간 / 제공된 토큰 사용량:
- 남은 문제와 다음 작업:
```

샘플 기획안, 가짜 승인 또는 실행하지 않은 테스트 결과를 이 보고서의 실제 완료 기록으로 옮기지 않는다.
