# 사용자 기획 검토표와 신뢰성 보완

기획을 읽고 승인할 때 요구사항이 어디에 반영됐는지 확인하기 위한 기능이다. 기획 원문과 함께 승인된 조건·정상 동작·실패 시 동작·확인 사례·남은 문제를 보여준다. 현재는 CLI와 Markdown/JSON 파일을 제공한다. 웹 UI·변경 영향표·팀원 실행은 이번 구현에 포함하지 않았다.

[독서 목록 예시 검토표](acceptance/planning-review-table-20261109/demo-bundle/review.md)를 먼저 보면 결과 형태를 확인할 수 있다. 이 예시는 TEST/STUB이며 실제 Gemini의 품질 평가나 사용자 승인 기록이 아니다.

## 기존 기획의 검토표 내보내기

저장된 `.adtf`와 해당 프로젝트 설정 파일이 있는 폴더에서 실행한다. 아래 설정 파일명은 이전 로컬 시험의 예시이므로 자신의 실제 설정 경로로 맞춘다. CMD와 PowerShell에서 같은 명령을 쓸 수 있다.

```powershell
npm.cmd run supervisor -- review-plan --config "examples/local-my-supervisor-20261109-112551.json" --output "review-local-01"
```

이 명령에는 ADC 로그인이나 `CALL` 입력이 필요 없다. 모델을 호출하거나 사용자 승인·기획 버전·반복 예산을 바꾸지 않는다. 출력 폴더의 부모는 존재해야 하고 출력 폴더 자체는 새 이름이어야 한다. 이미 있는 폴더는 덮어쓰지 않는다.

| 파일 | 내용 |
| --- | --- |
| plan.md | 해당 버전 기획 원문 |
| review.md | 사용자가 읽는 검토표 |
| review.json | 검토표의 구조화 데이터·출처·문제·오류 |
| bundle.json | 마지막에 기록하는 완료 표시와 파일별 SHA-256 |

저장 도중 실패하면 일부 파일만 남을 수 있다. `bundle.json`이 있어야 완성된 묶음이다. 실패한 폴더를 덮어쓰지 않고 원인을 확인한 다음 새 이름으로 내보낸다. 내보내기는 추가 비용이 없는 읽기 전용 기능이다.

## 판단을 읽는 방법

| 표시 | 뜻 |
| --- | --- |
| 반영됨 | 모델이 반영됐다고 판단했고 정상·실패·확인 사례의 현재 기획 원문 근거를 제공함 |
| 누락 | 연결된 누락 지적이나 요구별 missing 판정이 있음 |
| 서로 모순됨 | 해당 요구에 연결된 모순 또는 범위 위반 지적이 있음 |
| 확인 필요 | 근거 부족·미완료 검토·오래된 출처·미해결 전체 경고 등으로 확정 표시를 할 수 없음 |

**반영됨은 실제 프로그램 시험 통과나 최종 사용자 승인이 아니다.** 모델이 실제 문장을 인용해도 그 문장이 판단을 뒷받침하지 못할 수 있다. 표에 제공된 줄 번호는 내보낸 기획 원문 기준이다. 정상 동작·실패 동작·확인 사례의 인용을 함께 읽고 승인한다.

이전에 승인한 기획에는 새 세부 근거 필드가 없어 `확인 필요`가 나올 수 있다. 이는 과거 승인을 취소한 것이 아니다. 승인 기록과 문서 판단 상태는 따로 표시하며 과거 기획/Review를 자동 재작성하거나 유료 재검토하지 않는다. 새 Scope와 이전 기획 출처가 달라도 확정 판단을 재사용하지 않는다.

`report`에도 `userReview`와 `planningErrors`가 포함된다. 검토가 중단됐으면 완성된 이전 pass로 대신하지 않고 현재 상태와 같은 버전의 오류를 보여준다.

## 모델 응답이 잘렸을 때

Writer·일반 Reviewer·반례 Reviewer에서 종료 사유 `MAX_TOKENS`가 오면 `MODEL_OUTPUT_LIMIT`로 구분한다. 부분 응답을 완성된 기획/Review로 저장하지 않고 오류 기록에 보존한다. 정상 완료가 아닌 다른 종료 사유도 중단한다. 종료 메타데이터를 주지 않는 구형 클라이언트/시험 fixture는 기존 파싱 경로를 유지한다.

- 오류/부분 응답: `.adtf/projects/<projectId>/planning/errors/*.json`
- 공급자가 제공한 입력·응답·추론 토큰과 실패 정보: `planning/usage.jsonl`
- Writer 중단: 완성된 새 초안이 없을 수 있다. `report`로 상태를 확인하고 후속 실행을 별도로 결정한다.
- Reviewer 중단: 저장된 초안과 reviewing 상태를 보존한다. 자동 재호출하지 않는다. 기존 `retry-review`의 미사용 재시도·변경되지 않은 출처·원래 예산 여유·이유·유료 확인 조건을 그대로 적용한다.

Reviewer의 출력 한도를8000에서16000으로 늘렸고 SDK 요청은1시도로 제한했다. 논리적 반복 한도는 늘리지 않았다. 출력 한도 증가는 응답 잘림 방지를 보장하지 않으며 실제 토큰 비용이 늘 수 있다. [새 실제 Gemini 시험](planning-review-live-results-20261109.md)에서7개 정상 완료 응답의 형식·근거·Scope 교정을 확인했지만, 잘림 상황의 실제 재현이나 일반적인 품질 향상을 입증한 것은 아니다. 근거의 의미/역할과 공통 검증 규칙에는 보완점이 남았다.

## 근거와 범위 판단의 변경

새 Gemini 검토는 요구별 정상·실패·확인 사례의 줄 번호를 나누어 반환하고, 코드는 실제 원문을 추출·대조한다. 저장 상태 감사도 “어떤 상황인가”의 trigger 근거와 “어떻게 대응하는가”의 근거를 분리한다. 저장값 손상과 읽기 작업 자체의 예외는 다르다. 보수적인 읽기 실패 문구 검사에 맞지 않는 근거는 확인 필요/수정 대상으로 남긴다. 이 문구 검사는 의미상 정답을 증명하지 않으며 표현에 따라 과소·과대 판정할 수 있다.

새 범위 위반 지적은 해결 방법을 구분한다.

| 분류 | 다음 행동 |
| --- | --- |
| revise_plan | 승인 Scope를 유지하며 기획을 수정. 예: 제외된 자동 추천 문단 삭제 |
| change_scope | 승인 요구·제외·제약 자체를 바꿔야 하므로 별도 Scope 변경 승인 |
| clarify | 중요한 제품 선택이 모호하므로 질문 |

이 분류도 모델 제안이므로 틀릴 수 있다. 코드는 제안된 분류를 따라 분기하지만 Scope나 사용자 결정을 자동 변경하지 않는다. 분류가 없는 과거 Review는 기존의 보수적 승인 경로를 유지한다.

## 모델 없이 확인할 예시

```powershell
npm.cmd run planning:review-demo -- --output "review-demo-01"
```

새 독서 목록 사례의 고정 응답을 사용해 실제 어댑터·Controller·검토표 내보내기를 연결한다. 외부 API 요청0회이며 실제 품질 검증이 아니다. 메모리는 기존 `.adtf`와 분리한 임시 폴더에 남고 경로를 출력한다.

## 완료한 비교 기록 검증

기존6쌍의 입력·생성기·평가 결과는 고정 보존한다. 생산 코드가 변경된 지금 옛 생성기를 실행하면 소스 고정 검사에서 차단되는 것이 정상이다. 당시 코드에서 사용한 `run.mjs verify` 대신 아래 독립적인 읽기 전용 검증기를 쓴다.

```sh
node examples/planning-comparison/verify-archive.mjs --run-id local-20261109-162415
```

이 검증기는 원자료와 당시 생성기/설정/라이브러리 해시를 확인하며 현재 생산 코드를 재실행하지 않는다. 완료한 비교를 새 코드로 다시 실행해 기존 결과를 교체하지 않는다. 다음 실모델 품질 검증에는 새 사례가 필요하다.
