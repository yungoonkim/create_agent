# Writer·Reviewer 품질 절차 보완 — 2026-11-08

이 문서는 품질 보완·비교 평가 시점 기록이다. 이후 사용자 승인으로 todo 기획 v4와 작업 지시 인수를 마쳤으며, 최신 상태는 [최종 주제 보고서](supervisor-todo-final-acceptance-20261109.md)를 따른다.

## 문제와 목표

할 일 기획 v1~v4는 Gemini Reviewer가 모두 pass했지만 진행자 점검에서 미정 선택·저장 실패·순서·결정 출처 오류를 발견했다. 사용자는 같은 gemini-3.8-flash에서 품질 편차를 줄이도록 역할 프롬프트, 검토 형식과 코드 통과 조건 보완·반복 검증을 요청했다. 제품 구현이나 팀원 Agent를 추가하는 작업이 아니다.

## 구현

- Writer 시스템 지침: 사용자 선택/위임 설계/미정 사항 출처 분리, 쉬운 이용 흐름 우선, 요구별 정상/실패/검증 기준, 관련 데이터 불변식·현실적 보장, 수정 반영 및 회귀 확인.
- Reviewer 시스템 지침: 변경 요약이나 이전 pass를 그대로 믿지 않고 실제 명세와 원문·Scope·답변 대조. 중요한 미정 사항을 권고로 미루지 않고 사용자 질문으로 분류. 요구/고정 점검표에 근거 위치와 판단을 제출한다.
- 새 Gemini Review는 qualityAssessment v1을 필수 제출한다. Scope requiredFeatures의 모든 ID를 정확히 한 번씩 평가하고 decision_provenance, scope_compliance, behavior_and_errors, data_integrity, acceptance_criteria, revision_resolution, clarity의 7개 점검도 정확히 한 번씩 평가한다.
- 상태는 satisfied/missing/needs_user_input/not_applicable이다. 필수 요구에는 not_applicable을 허용하지 않으며 점검표에서는 data_integrity/revision_resolution만 합리적 비해당 사유를 쓸 수 있다. 의미상 비해당 판단까지 코드가 증명하지는 않는다.
- 모델은 현재 기획의 1-based 근거 줄 번호를 선택하고 코드는 해당 원문을 추출한다. 만족 판정에 빈 근거, 없는 줄, 빈 줄, 중복 참조나 실제 줄과 다른 저장 인용은 거부한다. 원문 위치가 실재한다는 사실과 그 위치가 판단을 충분히 뒷받침한다는 의미 판단은 구분한다.
- 모델이 pass라고 해도 missing은 수정, needs_user_input은 사용자 질문으로 보낸다. 총 반복 한도를 유지하며 잘못된 참조/coverage는 실패 처리한다. 최종 사용자 승인은 별도다.

## 호환성과 저장

이전 Review/fixture는 qualityAssessment가 없어도 읽고 기존 정책을 적용한다. 새 Gemini 응답에서 assessment 누락은 거부한다. 과거 리뷰를 새 프로토콜로 검증된 것처럼 바꾸거나 덮어쓰지 않는다. 코드로 coverage·근거·판정 모순을 제한하지만 모든 의미 오류를 결정론적으로 판정하지는 않는다.

기존 todo 기획 v4와 재고 기획·승인은 그대로다. 기존 기획 반복 4/5를 초기화하거나 새 사용자 결정을 만들지 않았다. 이번 실제 모델 호출은 독립 어댑터 평가이며 Planning 재개나 제품 실행 권한이 아니다.

## 비교 방법

baseline은 커밋 951588b의 원본 Writer/Reviewer 어댑터를 그대로 보존·실행했다. 같은 gemini-3.8-flash/프로젝트·위치/ADC, 기존 출력 한도를 사용한다. 평가 전에 후보와 정답 라벨을 고정했고 모델에게 라벨/결함 이름을 보내지 않았다. 범위·원문·실제 사용자 답변을 입력하며 실행 경로/ledger를 분리했다.

후보 7개: 정상 통제 기획 1개, 기존 사람 점검 기획 v4 1개, 중요한 미정 입력 결정·잘못된 사용자 결정 귀속·시계 우선 정렬·빈 저장값 초기화·commit 후 자동 복구 주장 등 결함 후보 5개다. 각 후보를 각 방식에서 2회 검토했다. Writer 생성 표본과 그 검토는 별도로 실행하며 정답 라벨이 없어 검출률 분모에 넣지 않는다.

1차 enhanced는 원문을 그대로 인용하도록 요구했지만 실제 모델이 요약/다른 입력 문장을 인용해 정상 후보도 형식 검증 실패했다. 원래 결과와 초기 구현 소스를 보존했다. 검증을 완화하지 않고 근거 줄 번호 선택+코드 원문 추출로 보완하고 같은 후보를 재시험했다. 이 과정에서 알려진 결함을 프롬프트 보완에 활용했으므로 평가 세트에 대한 개발 검증이며 독립 통계 일반화 시험이 아니다.

형식 오류는 성공한 결함 검출로 합산하지 않으며 정상 후보를 막은 경우도 별도로 보고한다. 새 프로토콜의 과거 v4 평가 결과가 실제 프로젝트의 기존 Review를 대체하지는 않는다.

## 최종 보완: 통과 전 반례 검토와 유효 줄 번호 제한

첫 점검이 실제로 최종 승인 대상을 허용할 때만, 같은 Reviewer가 **현재 판정 내용을 전달받지 않고** 반례를 찾는 모델 요청을 한 번 더 수행한다. 별도 팀원이나 새 Agent Runtime이 아니다. 미정 선택·중요 결함이 이미 발견됐다면 두 번째 요청을 생략한다. 반례가 나오면 정식 Review에 이슈/질문을 반영한다. 두 번째 호출이나 파싱이 실패하면 첫 pass를 반환하지 않는다.

논리적 기획 반복 횟수는 기존대로 유지하지만 한 Reviewer 절차에서 모델 요청은 최대 2회다. ledger의 reviewStage=assessment/challenge로 구분하며 실제 호출 수를 따로 집계한다. 새 Reviewer는 MEDIUM thinking을 명시하고 각 단계 출력 한도를 8,000으로 제한한다. 기존 기본 설정의 단일 호출과 비교한 결과이므로 프롬프트 문구만의 효과로 주장하지 않는다.

줄 번호 선택에서도 모델이 빈 줄을 선택한 실패가 나왔다. 최종 응답 스키마의 evidenceLines enum을 현재 기획의 실제 비어 있지 않은 줄 번호로 제한했다. 디코딩 제한과 별개로 코드에서도 범위·중복·인용 정합성·전체 coverage를 재검증한다. 임의의 잘못된 근거를 근처 문장으로 추측 보정하지 않는다.

형식 실패는 별도 열이며 차단 성공에 합산하지 않는다. 최종 9회 차단의 실제 설명을 읽어 주입된 결함과 일치함을 확인했다. 미정 입력 결정은 질문, 잘못된 사용자 결정 귀속/시계 정렬/commit 이후 자동 복구 주장은 수정으로 보냈다.

**남는 실패:** 빈 저장 문자열을 첫 실행으로 취급하고 빈 목록으로 덮어쓰는 후보가 최종 두 번 중 한 번 pass했다. 초기 점검과 독립 반례 단계 모두 놓쳤다. 이 규칙은 같은 문서의 잘못된 JSON/손상 보존 규칙과 충돌하도록 주입했으며, 의미 판단의 불안정성을 보여준다. 반복 두 번·기존에 알던 문제 세트이므로 일반 정확도 90%, 통계적 유의성이나 모든 주제의 품질 보장으로 해석하지 않는다.

## Writer 표본

기존/강화 Writer가 같은 원문·Scope·답변으로 작성한 미승인 표본을 별도 보존했다. 강화 표본은 이용 흐름, 요구별 정상·실패·수락 예시, 사용자 답변 출처와 설계 제안을 구분해 작성했다. [최종 Writer 표본](acceptance/planning-quality-challenge-20261108/writer-enhanced.md)을 최종 프로토콜로 다시 검토한 [결과](acceptance/planning-quality-bounded-20261108/writer-sample-final-review.json)는 REQUEST_USER_APPROVAL이다. 이는 **사용자가 승인했다는 뜻이 아니라 검토 후보로 제시할 수 있다는 판정**이다. 표본에 정답 라벨이 없어 위 검출률에는 합산하지 않았으며 Writer 품질의 통계적 개선도 주장하지 않는다.

## 호출량과 비용 관련 근거

최종 고정 후보 14회 검토에서 실제 모델 요청 기록은 **21개**, 기존 방식은 **14개**였다. 최종은 입력 131,999 / 출력 22,178 / reasoning 48,075, 기존은 입력 63,784 / 출력 2,470 / reasoning 24,752로 기록됐다. 근거 출력과 추가 반례 검토 때문에 토큰·시간이 증가했다. 달러 비용은 추정하지 않는다.

중간 실패와 재시험·Writer 표본을 모두 포함한 모델 요청 기록은 **94개(성공82/실패12)**다. [전체 ledger](acceptance/planning-quality-bounded-20261108/all-usage.jsonl)의 제공·기록된 합계는 입력470,294 / 출력100,451 / reasoning181,079 / 호출 시간 합계2,328,222ms다. 초기 후처리 실패 10행은 토큰 지표가 기록되지 않았으므로 이 합계를 청구 총량이나 하위 HTTP 재시도 횟수로 보지 않는다. 새 Reviewer는 응답 후 프로토콜 실패에도 제공된 토큰을 보존한다.

[첫 실행](acceptance/planning-quality-20261108/summary.json), [줄 번호 실행](acceptance/planning-quality-references-20261108/summary.json), [반례 실행](acceptance/planning-quality-challenge-20261108/summary.json)과 각 초기 구현 소스·호출 원문도 보존해 최종 성공만 골라 보고하지 않는다. 실행 시간은 manifest/ledger의 UTC 시각을 따른다. 모든 평가 전후 `.adtf` 프로젝트/승인 파일의 해시·파일 수가 동일함을 확인했다.

## 코드 검사

타입 검사와 전체 **128개 테스트 통과**(기존119+신규9). 근거·coverage 거부, pass 우회 차단, 질문/한도 경계, Controller 저장 및 legacy 호환과 새 Gemini 강제 조건을 검증했다. 런타임 종속성은 추가하지 않았다.
